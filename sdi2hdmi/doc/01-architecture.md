# sdi2hdmi — 架构设计

纯 PL 的 SDI → HDMI 转换器。目标板 **FMQL30TAI**（复旦微，实为 Zynq-7030 `xc7z030ai` 器件）。
本文是设计正本，写清楚**为什么这么接**。数字与出处见 `doc/02-verification.md`。

---

## 一、为什么另起一个工程，而不是改 fpai_demo_fpga

厂商交付里**已经有**一条能用的 SDI → HDMI：
`S:\work\WCIS\fdw\20260916\fpai_demo_fpga`，其 `rtl/display/frame_to_ps_largebuf.v:606`
实例化了 `uihdmitx`。但那条路的走向是

```
SDI → AXI → PS DDR → PS → 显示缓冲 BRAM → HDMI
```

**一张纯视频的图绕 CPU 走了一整圈**。代价直接体现在占用上（`位流构建与SDI信号检测.md` §5.1 / §6.8.10）：

| 指标 | fpai_demo_fpga（去掉 NPU 后） | 本设计预算 |
|---|---|---|
| MMCM | **5 / 5（100%）** | 3 / 5 |
| WNS | +0.072 ns（等于零余量） | 见 `dist/timing_routed.rpt` |
| BRAM | 76.5 / 265（28.9%） | 约 20 / 265 |
| LUT | 16 668（21.2%） | 见 `dist/utilization_routed.rpt` |

MMCM 用满是**硬约束**：再加一个时钟资源就得重排，而那条设计现在连一根时序余量都没有。

## 二、720p60 不是保守，是硬件上限

这是本设计最重要的一条结论，和厂商 demo 的实际行为不一致。

手册（FMQL30TAI 完整版 §4.21）自陈 HDMI 输出是 **IO 逻辑实现**，HR bank 时钟上限 **710 MHz**：

- 1080p60 → 像素时钟 148.5 MHz → TMDS **742.5 MHz** → **超出 710M，部分显示器闪屏**
- 720p60 → 像素时钟 74.25 MHz → TMDS **371.25 MHz** → 在上限内

而厂商 demo 跑的是哪个？`frame_to_ps_largebuf.v:219-232`：

```verilog
cmos_clkgen_742_5 u0 (
    .clk_in1 (cam_clk_use),        // 148.5 MHz，来自 SDI 恢复时钟
    .clk_out1(cam_clk_use_148_5),
    .clk_out2(cam_clk_use_742_5),  // → BUFIO → OSERDESE2 PCLKX5
```

`cmos_clkgen_742_5.xci` 的 `CLKIN1_PERIOD = 6.734 ns` = **148.5 MHz**，
`CLKFBOUT_MULT_F = 5` → VCO 742.5 MHz。`hdmi_out_clk = cam_clk_use` = 148.5 MHz。
再对照 `frame_to_ps_largebuf.v:290` 的注释
「color_bar.v generates for VIDEO_1920_1080: 2200 x 1125」：

> **厂商 demo 实际输出的是 1080p60 / 742.5 MHz TMDS —— 正好是手册说会闪屏的那一档。**
> wiki 里「演示输出定 720p60」记的是**手册规格**，不是 demo 的实际行为。

`OSERDESE2` 的 `CLK` 与 `CLKDIV` 关系（`rtl/display/oserdese2_10to1.v:93-94`）
在 `DATA_WIDTH=10` DDR 模式下是 **5:1**，这决定了上面的算术，没有第二种接法。

## 四、时钟预算

| 时钟 | 输入 | 输出 | 实现 | 器件原语 |
|---|---|---|---|---|
| `sys_clk` | 200 MHz (C8/C7) | 27 MHz | 厂商 clk_wiz | MMCM/PLLE2 ×1 |
| `mgtclk` | 156.25 MHz (R6/R5) | 148.5 MHz | 厂商 clk_wiz | MMCM/PLLE2 ×1 |
| `hdmi_mmcm` | 148.5 MHz | **74.25** MHz（像素）+ **371.25** MHz（串行） | 本设计 | MMCM ×1 |
| BUFIO | 371.25 MHz | → OSERDESE2 CLK | 本设计 | BUFIO ×1 |

**合计 3 个 MMCM，器件有 5 个。** GT 的 QPLL 不占 MMCM。

MMCM 配置：`CLKFBOUT_MULT_F=5, DIVCLK_DIVIDE=1` → VCO **742.5 MHz**，在 7 系列
-1 档的 600~1200 MHz 区间内；`CLKOUT0_DIVIDE_F=10` → 74.25 MHz，
`CLKOUT1_DIVIDE=2` → 371.25 MHz。厂商的 `cmos_clkgen_742_5` 跑的是同一个 742.5 VCO，
所以这个配置是已知能出的。

BUFIO 不能省：OSERDESE2 的 `CLK` 要和喂串行数据的 fabric 相位对齐，
BUFG 做不到这件事。

## 五、两处对厂商 RTL 的改动（各一处，都标在文件里）

**1. `rx_sdi.v` 增加 `mgtclk_148_5_o` 输出**

HDMI 时钟**不能**挂在 `cam_clk` 上。`rx_sdi.v:368`：

```verilog
assign cam_clk = rx0_locked ? rx_usrclk : sys_clk_200m;
```

`rx_usrclk` 对 3G-SDI 是 148.5 MHz、对 HD-SDI 是 74.25 MHz，还会因为未锁定
被切到 200 MHz。拿它当像素时钟，等于**输出制式跟着源走**，而且一掉锁就没时钟。
所以把恒定的 148.5 MHz 引出来，一根 assign，不动接收器行为。

**2. 其余厂商 RTL 逐字复制（唯一的例外是 `sdi_status.v`，那本来就是我们自己写的）**

`rtl/vendor/sdi/` 与 `rtl/vendor/display/` 下的厂商文件全部原样拷贝，包括 `vidgen_ntsc.v`
／`vidgen_pal.v`／`multigenHD*.v` 这些本设计不用但会被 `x7gtx_sdi_wrapper.v`
引用的测试图发生器。改动越小越容易说清哪里出的问题。

两个容易记混的点：

* `rx_sdi.v` 上除了上面那个 `mgtclk_148_5_o`，还有**上一轮 bring-up 留下的**
  `sdi_status_bus`（160 位状态/实测几何导出）与 `u_sdi_status` 实例化。
  那是 [[位流构建与SDI信号检测]] 那轮的产物，本设计只是继承——**它不改接收器行为**，
  而且正是它给出「真实 1080p 源实测 1920×1080」这条板级证据（见
  `doc/02-verification.md` 第四节第 5 小节）。
* `rtl/vendor/sdi/sdi_status.v` **不是厂商文件**，是本工程自己写的测量模块
  （文件头 `Project : SDI auto-detect / live-capture bring-up`），放在 vendor 目录里
  只是顺手；改它不影响「厂商 RTL 未动」这条口径。

## 六、重采样：为什么是「行缓冲 + 盒式滤波」而不是「帧缓冲」

**算术先摆清楚**：1280×720×16b 的帧缓冲是 14.7 Mbit = **410 个 RAMB36**，
而 xc7z030 只有 **265**。**720p 一帧在 BRAM 里根本放不下。**
一行 1280×16 = 20 480 bit = 1 个 RAMB36，所以只能按行走。

### 滤波定义（精确，不是近似）

```
E(j) = floor( (j+1) * src_w / dst_w )      输出像素 x 取源像素 [E(x-1), E(x)) 的均值
F(k) = floor( (k+1) * src_h / dst_h )      输出行   k 取缩放后行 [F(k-1), F(k)) 的均值
```

`E()`／`F()` 用**分数累加器逐个输出元素走一步**，所以**没有乘法器也没有除法器**。
`h_take`／`v_take` 存 `E(x)-E(x-1)`，`h_got`／`v_got` 数已累加的个数，两者相等即收口。

两种真实源都是精确的：

| 源 | E() | take | 结果 |
|---|---|---|---|
| 1920×1080 | 1,3,4,6,7,9,… | 2,1,2,1,2,1 | 奇数位取 2 像素均值 |
| 1280×720 | 1,2,3,4,5,… | 1,1,1,1,1 | 逐点透传 |

**抽头封顶 2**。源超过 2×输出宽高就会截断并拉 `overflow_q`，而不是悄悄缩错。
`take` 最小取 1，保证滤波器永远有进展。

### 只支持缩小，不支持放大

这是**有意的取舍，不是 bug**。上面那套走法是「每个输出元素数源元素」，
`take` 被强制 ≥1，所以它产出的输出元素数**不可能多于**消费的源元素数。
放大需要「消费 0 个源元素的输出元素」，那会破坏一拍一个输出元素的结构。
所有实际 SDI 制式都 ≥ 1280×720 输出，所以放不进支持范围。
（`tb_scaler_720.v` 里遇到源小于输出会直接打印 `SKIP` 并说明，而不是刷一百万条 mismatch。）

### 两条行缓冲，轮换角色

```
W  像素通路写它
P  推送级读它
每完成一行输出就交换：P <= W, W <= ~W
```

两个角色**任何时刻都在两块不同缓冲上**，所以每块只要 1 写口 + 1 读口，
就是普通双口 RAM。

如果只要一块：平均要读的那一行和推送要读的那一行是同一块，两个读口打架。

> **实测**：即使加了 `(* ram_style = "block" *)`，Vivado 仍然推断成分布式 RAM
> （`RAMD64E 4800`）。资源上完全够（总 LUT 12.06%），
> 要紧的是时序——布线后的读数见 `doc/02-verification.md`。

### 垂直平均踩过的坑（留档）

第一版把垂直 2 抽头写成「和**上一条已发布输出行**求平均」。错的：
`v_take=2` 时那条已发布行覆盖的源范围完全不同，结果是一整行一行的纵向拖影。
**正确做法是同一个缓冲、同一个像素下标做读-改-写**——第一折存值，第二折读回同一地址
求平均。双口 BRAM 原生支持（读口在同一拍返回写前值），所以既不需要第三块缓冲，
也不需要对整行跑第二遍。

## 七、跨时钟域：跨的是「一整行」

跨的不是像素，是整行。两个理由：

1. 1280×16 = 20 480 bit，行槽很便宜（本设计用 8 槽）；
2. 行是天然单位——**写侧在 1280 个像素全部落位之后才释放槽位**，读侧不可能读到半行。

指针用**格雷码**跨，每步只变一位，接收侧无论边沿落在哪里都采到一致的值。
异步 FIFO 必须**每个方向一条链**，各自用**消费它的那一侧的时钟**：
写指针进读域供 `empty`，读指针进写域供 `full`。
共用一条链就是跨域用错，工具会报（实测 −3.857 ns），而且是真 bug 不是误报。

### 读侧必须每 750 个行槽都取一次行

一帧是 **750** 个行槽（`V_ACTIVE` 720 + 消隐 30）。
读侧在**每个行槽边界**取一个行，需求就是**每 1650 rclk 一个行** ——
这正好是像素时钟能供的最快速率。生产者只要不超过这个速率就行。

> 曾经写成 `claim_now = (hcnt == H_TOTAL-1) && in_vact`，只在有效区取行。
> 那样一帧只取 **720** 次，即每 **1718.75** rclk 一个，
> 比生产者的 1650 rclk **慢 4.17%**，行槽占用必然缓慢爬到上限。
> 实测：连续 728 行之后写口开始丢数据，丢了 220 160 个像素，
> 而生产者还在继续送（供了 4500 行，DUT 的写指针卡在第 8 行不动）。
>
> **去掉 `&& in_vact` 之后，失败方向反过来了**：供不上时读侧**缺行**
> （`stalled` 拉高、重复上一行，可数可见），而不是**多写**（静默毁画面）。

### 写口没有反压，所以溢出必须可见

生产者是 SDI 像素流，**不能停**。写口满了只能丢。
丢一个，生产者的像素计数器和 DUT 的写指针就**永久错开**，之后每一行行号都是错的。

所以 `hdmi_out` 有两个状态输出：

| 信号 | 含义 |
|---|---|
| `stat_dropped` | 因为写口满而被丢弃的像素计数 |
| `overflow` | 粘滞标志，一旦丢过就置位 |

**这是不可靠流程能做的唯一一件事**：把「静默毁画面」变成「能数到」。
握手防不住（源不能停），加深也防不住（速率亏空是无界累积的），
只能让它可见。`sim/tb_hdmi_out.v` 第二级就是故意超速，断言这两个信号必须动。

真饿死时（30 fps 源），`hdmi_out` **保持光栅时序、重复上一行**，
画面冻结而不是撕裂，`stalled` 拉高报出来。

输出级是**两级流水**：行槽是块 RAM，读延迟一拍，`rgb` 再寄存一拍，
所以 `hs/vs/de` 也必须延迟两级才和数据对齐。只延一级会差整整一个像素。

> ✅ **已验证**（2026-10-16）：`hdmi_out` 要求生产者每 1650 rclk 供一个行，
> 而 `scaler_720` 每帧产 **720** 行；两者一起跑过端到端仿真（`tb_e2e` + 校机
> Verilator 真实视频），稳态**720 供 / 720 耗 / 0 丢弃**，光栅 1650×750 恒定。
> 完整契约（**两条**等式：active 窗口 + 帧周期）与边界表见
> `doc/02-verification.md` 第三节与第四节第 4 小节。
>
> ✅ **帧边界对齐已修（2026-10-17）**：`hdmi_out` 里做**一次性消隐插入**。
> 写侧每个 `frame_start` 随该帧第一条推送的行走上发一个标记（`scaler_720.out_frame`，
> 两级同步进 rclk 域）；读侧在标记到达时采样光栅行号 `p`，**只在这一帧**多插
> `(p + ALIGN_EPS) mod 750` 行垂直消隐（`ALIGN_EPS = 4`，**只拉长、不缩短**）。
> 死区 `p ∈ {744..747}` 不动（校正量 0/1/748/749，1 行的目标不值得用 749 行的代价去换），
> 目标 `p = 746`；拉长期间取行照发（`in_extend`），环被抽干、被跳过的内容落在
> 显示帧边界上，肉眼不可见。校正一次后两边周期相等 ⇒ `p` 落进死区 ⇒ **只校正一次**，
> 代价是一帧变长（≤ 16.7 ms）。
>
> 修之前实测的窗口只有 **约 ±7 行**（8 个行槽给的上界 ±8 行 = ±26 400 camclk），
> 越界后每帧丢/重复 `约(偏差 − 7)` 行、**稳定横带且不自愈**——那是上板阻塞项，
> 历史读数见 `doc/02-verification.md` 第四节第 3 小节。修完 16 个相位点全部
> `dropped 0 / held 0`（同节第 3b 小节），独立复核（xsim，连续源）见同处。
> 相关坑：测试台「等输出帧」的等待会把源停住（`doc/03-flow.md` 坑 32）、
> 新 CDC 要配靶向假路径（坑 34）。

## 九、明确没做的事

写下来免得被当成已完成：

| 项 | 状态 | 原因 |
|---|---|---|
| **SD-SDI（576i/480i）** | **明确不支持** | SD 路径上的下变换器 `dru` 是**加密网表**（头部 `XlxV80EB` 而非 EDIF 文本），非工程流程读它会让 Vivado 在 RTL 优化阶段直接崩掉（日志截断、退出码 −1），不读它又卡在 `DRC INBB-3` 黑盒。本设计用行为替身 `dru_standin.v` 把 SD 路径保持空闲，**HD/3G 不受影响**。取舍理由见 wiki [[SDI转HDMI转换器]] 第六节第 2 条 |
| 隔行（1080i）场合并 | **未做** | `rx_sdi` 出来的 `cam_vs` 是垂直**有效**电平，没有场标志。要合并得动 `frame_convertor` |
| 上采样 | **不做** | 见 §6；要支撑得改滤波结构 |
| 4K / >1440 行 | **不做** | 抽头封顶 2，会拉 `overflow_q` |
| 音频 | **未做** | SDI 音频在 `smpte_sdi` 核内部，EDIF 拿不到 |
| EDH / ANC 数据 | **拿不到** | 同上，要换裸串并行接收器，是另一个工程量 |
| OSD / 菜单 | **未做** | — |

厂商自己在 `ai7030_edif_top.v:115-117` 留了这条注释：

// LED_MON=1: led[0]=rx_usrclk 在闪(GT 参考时钟/恢复时钟), led[1]=rx0_locked(SDI 真的解出码流)
