## 一、仿真：`scaler_720`

自检测试台 `sim/tb_scaler_720.v`。判据是**独立黄金模型**：
测试台用最朴素的嵌套循环按 `E(j) = (j+1)*src_w/dst_w` 独立算出应有的输出，
再和 DUT 逐像素比。黄金模型不是从 DUT 抄的。

```
powershell -NoProfile -ExecutionPolicy Bypass -File .\sim\run_sim_scaler.ps1
```

| 用例 | 源 → 输出 | 读数 |
|---|---|---|
| 1:1 透传 | 1280×720 → 1280×720 | `PASS: 1280x720 output matches the golden box filter exactly` |
| 2:3 缩小 | 1920×1080 → 1280×720 | `PASS: 1280x720 output matches the golden box filter exactly` |

```
ALL CASES PASSED
```

配套读数（缩小用例，源开窗 2210×1129，4 帧）：

```
=== SRC 1920x1080 -> DST 1280x720, 4 frames (raster 2210x1129)
    E(0..5) = 1 3 4 6 7 9
    F(0..5) = 1 3 4 6 7 9
=== captured 2160 lines, stat_lines=2160, src_w=1920 src_h=1080
=== locked_q=1 overflow_q=0 push_overrun=0
=== checking captured lines 1440..2159
```

- `overflow_q=0`：抽头没有超过封顶值 2。
- `src_w/src_h` 与输入一致：几何测量正确。
- `push_overrun=0`。**老读数这里是 1，而且曾经被当作本测试台的正常现象解释掉了 ——
  那是假的**，它是一个每行都置位、什么都报的假报警，见第三节。

**同一组读数在 Verilator 下完全一致**（`PASS` 同句、`push_overrun=0` 同值）。
`tb_scaler_720` 在 Verilator 下曾长期被认为是「跑不起来」（时间 0 就 `$finish`），
真相是默认 plusarg 选了一个比输出还小的源，走进了 SKIP 分支 —— 见 `doc/03-flow.md`。

**测试台驱动的是 `rx_sdi` 真正产生的那种光栅**，不是随便一种能过判据的光栅：
`cam_hs` 在**每一条行**上（含垂直消隐行）都会拉高，`cam_vs` 与第一条有效行的数据窗口同拍上升。
这两条都是硬约束，理由写在该文件的 raster driver 里，也是第三节三个真 bug 的成因。
**测试台自己也踩过三个坑**，见 `doc/03-flow.md` 第三节。
**先确认判据本身能过，再去追 DUT**；再进一步：**先确认测试台能产生那个 bug**。

## 二、仿真：`hdmi_out`（行槽 FIFO + 720p60 光栅）

自检测试台 `sim/tb_hdmi_out.v`。

```
powershell -NoProfile -ExecutionPolicy Bypass -File .\sim\run_sim_hdmi_out.ps1
```

```
=== frames driven            : 14
=== pixels compared          : 12902417
=== lines compared           : 10081
=== hold (back-pressure) px  : 1280
=== raster timing errors     : 0
=== sync polarity errors     : 0
=== torn line errors         : 0
=== payload data errors      : 0
=== stat_frames (DUT)        : 14
=== stat_dropped (DUT)       : 6051040
=== overflow (DUT)           : 1
PASS: raster exact, sync positive, CDC intact under both rates
```

测的东西：

| 项 | 判据 |
|---|---|
| 光栅时序 | 与独立写的黄金模型**逐像素**比，14 帧共 12 902 417 次比较，不是数个数 |
| 同步极性 | 单独查**电平**，所以负极性版本不可能混过时序检查 |
| CDC 完整性 | 每行自带行号与像素号，读侧逐像素反解，坏行/半行/重行/丢行都躲不过 |
| 背压 | 生产者故意快于消费者，FIFO 饱和，读侧必须保持光栅并重复上一行 |
| 溢出上报 | 故意超速后 `stat_dropped` 必须增长、`overflow` 必须置位 |

**这一节值 5 个 RTL 真 bug**，全部是综合和时序报告看不出来的。

### bug 1：同步极性反了（点不亮显示器）

```verilog
hs <= in_hsync ^ HS_POL[0];     // HS_POL 默认 1
```

`HS_POL=1` 的定义是**正极性**（`color_bar.v` 同样定义），XOR 把它取反成了负极性。
核对链路：`uihdmitx.v:78-79` 把 `HS_i` 接进蓝色通道 TMDSEncoder 的 `C0_I`，
而 `TMDSEncoder.vhd` 的控制符号表里 `C0=1/C1=0` 才是行同步有效 ——
所以 `HS_i=1` 必须表示「同步有效」。

写成 XOR 在 `HS_POL=0` 时恰好等价，**只有正极性这一种配置会暴露**。
输出负极性同步，显示器收不到行同步，不锁。

### bug 2：`vcnt` 没和 `hcnt` 联动（光栅彻底错乱）

原写法两个计数器各自比自己的终值：

```verilog
hcnt <= (hcnt == H_TOTAL-1) ? 0 : hcnt + 1;
vcnt <= (vcnt == V_TOTAL-1) ? 0 : vcnt + 1;   // ← 和 hcnt 无关
```

`vcnt` 于是按自己的速度空跑。实测：驱动 8 帧时 `stat_frames` 报 **13 200**
（9 900 000 / 13 200 = 750，即 `vcnt` 每 750 拍归零一次而不是每 750×1650），
场同步早出现 1650 倍。

### bug 3：RGB565→RGB888 绿通道多拼了 1 位（颜色全错）

```verilog
rgb <= {ram_q[15:11], ram_q[15:13],   // R: 5+3 = 8   ✓
       ram_q[10:5],  ram_q[10:8],    // G: 6+3 = 9   ✗ 超了 1 位
       ram_q[4:0],   ram_q[4:2]};    // B: 5+3 = 8
```

总宽 **25 位塞进 24 位端口**，Verilog 从高位截断，红色之后每个通道整体错一位。
测试台表现为：解出来的像素号每像素 +2 而不是 +1 —— 这就是「字段错位」的样子。

### bug 4：同步器触发器没复位（综合干净的空画面）

`w_gray_s1/s2`、`r_gray_s1/s2`、`w_gray_r1/r2` 全都没有复位。
上电是 X → 传播进 `w_full` → `w_en && !w_full` 在仿真里恒假 →
**行槽一个字节都没写进去**，读出来全是 0。

**综合完全不会报错**（没复位的触发器不是综合错误），位流和时序都干净，
只有仿真能抓到。

### bug 5：取行门控导致 4.17% 速率亏空（静默溢出、画面永久错位）

```verilog
wire claim_now = (hcnt == H_TOTAL-1) && in_vact;   // ← 这个 && 是根因
```

一帧是 750 个行槽。`in_vact` 只在 720 行内为真，所以读侧**每 750 个行槽只取
720 次**，即每 1718.75 rclk 取一个行槽；而生产者是每 1650 rclk 供一个行槽。
**生产者比读侧快 4.17%**，行槽占用必然缓慢爬到上限。

而写口在满时是 `w_en && !w_full` —— **直接丢数据，没有反压**：
SDI 像素流不能停，于是丢一个就永久错开一格，之后每一行的行号都是错的。

`sim/dbg_hdmi_out.v` 量到了完整过程：

```
RATE  window 17: w_en=51200 (duty 38%) blocked=0  producer_lines=40  dut_line_starts=40  depth=0
DROP   first dropped write
RATE  window 18: w_en=51200 (duty 38%) blocked=29440 producer_lines=40  dut_line_starts=17  depth=7
=== dropped writes        : 220160
=== dut w_bin final       : 8
=== producer w_line final : 4500
```

生产者供了 4500 行，DUT 的写指针卡在第 8 行不动。

#### ⛔ 上面的「改法」是错的，已回退

我当时的结论是「去掉 `&& in_vact`，每 750 个行槽都取一次行」，
并把它当成第 5 个 bug 写进了 wiki。**这个结论建立在一个节拍设错的测试台上，
而且「修复」本身是错的。** 端到端仿真（第三节）把它证伪了。

错在哪：

`tb_hdmi_out` 的生产者被设成每 3300 camclk 产一行（= 1650 rclk）。
而带 `&& in_vact` 的消费者一帧只取 720 个行槽，平均每 **1718.75** rclk 一个。
**生产者快了 4.17%**，所以溢出。

**那 4.17% 是测试台的错，不是设计的错。** 我却拿它当证据去改设计，
把正确的东西改坏了。端到端实测的真实契约是：

| | cam_clk | rclk |
|---|---|---|
| 源帧 1125 × 2200 | 2 475 000 | 1 237 500 |
| hdmi_out 帧 750 × 1650 | 2 475 000 | 1 237 500 |
| **hdmi_out 有效区 720 行** | 2 376 000 | **1 188 000** |
| **scaler 输出 720 行**（摊在 1080 个有效源行上） | 2 376 000 | **1 188 000** |

生产者的 720 行**恰好**落在读者的 720 个有效行槽里，
两者在垂直消隐的 30 行里一起闲着。`&& in_vact` 正是对的。
去掉它之后读者每帧多要 30 个没人产的行槽，亏空逐帧累积，
端到端实测每帧仍在丢 **298 240 / 6 ≈ 38.8 行**。

**这一条是本轮最贵的教训**，写在这里而不是角落里：

> **测试台的错误不只是产生假通过，它还会诱导出真的设计回归。**
> 我用一个节奏不对的激励去量「设计稳不稳」，得到「不稳」，
> 于是改了设计 —— 改动本身又制造了一个更难查的问题（启动瞬态溢出），
> 而**原始证据始终是错的**。
>
> 正确顺序是：**先证明测试台的节拍和真实生产者一致，再去动设计。**
> 判断「测试台对不对」的标准不是「它报没报错」，而是
> **「它测的激励和真实场景是不是同一个契约」**。

### 配套加的两个输出

`stat_dropped`（丢弃像素计数）与 `overflow`（粘滞标志）。
**这个失败模式原本是静默的**，而不可反压的写口不可能靠握手避免它，
所以必须让它可见 —— 否则就是「时序全绿、位流正常、画面慢慢烂掉」。

> ⚠️ **当前位流里没有这个检测。** 顶层只把它接成内部网、没有消费，
> 综合直接把它优化掉了 —— 查 `post_synth.dcp`：
> `get_cells -hier -filter {NAME =~ *stat_dropped*}` 返回 **0 个单元**。
>
> 所以现在的状态是：**RTL 有、仿真验过、位流里没有**。
> 要接灯就得先查板级引脚表找空闲引脚，接上之后它才真正存在。
> 记在第七节。

### 测试台自己踩的坑

这一节所有「DUT 有 bug」的判断，最后有**六个**落在测试台或构建脚本上。
每一个都伪装成硬件故障：

| 坑 | 表现 | 真因 |
|---|---|---|
| `strict` 初值写成 `1` | 仿真开头 17 个像素误报 | 主程序在**释放复位之后**才把它清 0，那时消费者已经出第一行了 |
| `c_line_hold` 声明成 1 位 | 1000 万次「撕裂」误报 | 拿 1 位比 `rgb[23:19]`（5 位），非零行号全部判不等 |
| 极性期望取错流水深度 | 10 514 次误报 | `hs` 是两级，期望却取了一级的 `pat_d1`，差一拍 |
| `THROTTLE` 写成 parameter | 第二级根本没超速 | 注释说「全速冲」，参数固定，溢出路径**从未被走到** |
| 节流方向搞反 | 「无背压」阶段记了 733 440 个保持像素 | 空闲 2560 拍比读侧**慢**，FIFO 是被抽干而不是填满 |
| **生产者按平均节拍配** | 既丢 281 801 又饿 225 280 | 真实契约是**突发**：720 行连续每 1650 rclk，然后消隐期停。均匀节拍在突发期太快、在整帧上太慢 |
| **拿平均节拍的证据去改设计** | 制造了一个真回归 | 见上面那条 ⛔ |

**规律**：断言写错时报出来的数越大越像真的。
`733 440`、`10 514`、`1 075 167` 这几个数，每一个看起来都像设计有毛病。

## 三、端到端：SDI 帧 → scaler_720 → hdmi_out → 720p60 光栅

自检测试台 `sim/tb_e2e.v`。

```
powershell -NoProfile -ExecutionPolicy Bypass -File .\sim\run_sim_e2e.ps1
```

**这是前面两个测试台加起来都替代不了的一层**：它验证的是两个模块**之间**的契约，
也就是「谁供多少行、什么节拍、相位对不对」——
这类问题两个模块各自单测时都看不见，因为它们各自的判据都成立。

链路用的是**真实 3G-SDI 时序**：

```
2200×1125 光栅 @ cam_clk 148.5 MHz（有效区 1920×1080）
      │
      ▼  scaler_720  ──► pix_valid / pix_last / pix_data[15:0]
      │
      ▼  hdmi_out     wclk = cam_clk, rclk = cam_clk/2（MMCM 二分频）
      │
      ▼  捕获 hs/vs/de/rgb888，与独立黄金模型逐像素比
```

黄金模型和 `tb_scaler_720` 用的是同一套盒式滤波数学，但**在这个测试台里重新实现了一遍**，
且源图案带逐行斜坡，所以每一行都唯一可辨。

### 读数

修掉下面三个真 bug 和两个测试台自己的错之后的读数：

```
=== scaler locked    : 1   measured 1920x1080
=== scaler lines     : 3600          （稳态每帧 720 行）
=== stat_dropped     : 0
=== overflow         : 0
=== scaler overflow_q: 0   push_overrun 0
--- content check, one frozen frame ---
=== frame phase (golden row for capture row 0) : 718
=== rows exact at that frame phase             : 720 of 720
=== rows at an inconsistent phase              : 0
=== PASS: 720 of 720 captured rows exact against golden, line order exact, no data lost
```

**xsim 与 Verilator 同判**：两边都报 `frame phase = 718`、`720 of 720`、`0 inconsistent`、
同一句 `PASS`。两个仿真器给出同一个帧相位，比各自说「通过」更有说服力 ——
相位是算出来的，不是判决出来的。

- **内容**：捕获的每一行都精确等于黄金模型对应行，且落在**同一个**帧相位上。
- **供需**：稳态每帧 720 行 / 720 次取行 / 0 丢弃。
- **行槽占用**：全程 0～2 个槽（8 个），余量很大。

### ⚠️ 先撤回：上一轮记录的那次 `PASS` 从未成立

上一版这里写的是 `line-order slips 0` + `PASS: end-to-end content exact on every frame`。
**那句 PASS 是假的。** 内容失败计数 `line_miss` 当时是 `compare_frame` 的**局部变量**，
判据读的是 `pre_fail` 和 `seq_bad` —— 一个读不到的计数器不是判据。
把 `line_miss` 提到模块级并接进判据之后，xsim 和 Verilator **一致**报：

```
=== rows exact vs golden    : 0 of 720
=== FAIL: 720 rows matched no golden row, 0 of 720 rows exact
```

两个仿真器从来没有分歧。**分歧只在「判据读不读那个数」之间。**

### 三个真 bug：几何测量，全在 `scaler_720.v`

它们都只在「真源」的光栅下才暴露，而且**每一个都会让画面出不来**。

**① `frame_start` 清 `lines_in_frame` 与 `line_start` 递增撞在同一拍**

`cam_vs` 的上升沿**必须**和第一条有效行的 `cam_hs` 上升沿同拍 —— 这不是约定，
是被 `rx_sdi.v:357` 的 `cam_data_en = cam_vs & cam_hs` 逼出来的：
晚一拍那条行就没有 `data_en`，源帧永远少一行。

**这条同拍关系是板子定的，不是从 RTL 读出来的。** `frame_convertor.v:58` 在 `rx_eav`
上用 `rx_ds1a[7]` 生成 `YCbCr422_vsync`，而 10-bit TRS 里这一位是 V 不是 F，
所以 RTL 本身定不了相位。板实测几何是 1920×**1080**，而晚一行的 `cam_vs` 只能量出 1079
⇒ 相位就是（或早于）同拍。整条相位轴在仿真里扫过，见第四节第 5 小节。

而老代码把两者写在**同一个 always 块的先后两条赋值**里：`frame_start` 清零、`line_start` 递增，
后面那条赢。于是**清零永远不生效**，计数器跨帧累加：

| | 实测 |
|---|---|
| 六帧后 `lines_in_frame` | **6479**（= 6×1080 − 1，不是 1080）|
| `src_h` | 垃圾 |
| `locked_q` | 永不置位 ⇒ **上电黑屏** |

修法：两者在**一个分支里**解决，同拍时种 1 而不是清 0
（和 `sdi_status.v:203` 处理自己高度计数器一个写法）。

**② `lines_in_frame` 没被 `in_vs` 门控 ⇒ 测出 1125 行**

`cam_hs` 在**每一条行**上都会上升，包括 45 条垂直消隐行 ——
`frame_convertor` 在每个 SAV 都重启水平计数器，而消隐行同样带 SAV。
所以按 `in_hs` 上升沿数行数得 **1125**（≠1080），垂直方向被拉伸 4%。
修法：`line_start && in_vs` 才计数。`in_vs` 是垂直**有效**电平，恰好覆盖有画面的那些行。

**③ `src_w` 从 `px_in_line` 锁存 ⇒ 读到 0**

`px_in_line` 是「当前行已收到的有效像素数」。有效区结束后的**第一条消隐行**会把
`line_start` 触发一次，那一行 `in_de` 恒 0，于是 `px_in_line` 被重载成 0；
等到下一帧 `frame_start` 去读它时，读到的就是 0 ⇒ `locked_q` 永不置位。
**没有任何一个活计数器在那个时刻还留着宽度**，必须在**有像素的那一行的行尾**锁存。
修法：新增 `src_w_meas`，在 `line_end && px_in_line != 0` 时锁存；`src_w`/`h_src_w`/`locked_q`
都改从它来。

**顺带修掉一个假报警**：`push_overrun` 写在 `else` 分支里、条件是 `pub_evt && locked_q`，
而 `pub_evt` 正是**启动**那次推送的事件 —— 那一拍 `push_go` 还是 0，走的就是 `else`。
于是这个标志**每行都置位**，在一路一次溢出都没有的流上报溢出。
挪进 `if (push_go)` 分支后为 0。**一个永远读满的表读不出任何一个信号。**

### 为什么这三个 bug 之前查不到：测试台在驱动一块硬件产生不出来的光栅

| 测试台干的事 | 真板上是什么 | 掩盖了什么 |
|---|---|---|
| `src_de` 与 `src_vs` **独立驱动** | `cam_data_en = cam_vs & cam_hs` | 「vs 低而 de 高」在真板上**根本无法表达**。正是这个自由度让下面两件事成了可选项 |
| `in_hs` 被有效高度门控，消隐行上没有 | 每行（含消隐行）都有 `in_hs` | ② 和 ③：门控后测出 1080，真板测出 1125；`px_in_line` 也不会被消隐行清掉 |
| `in_vs` 的上升沿挪到 line 0 **有效像素之后**（`VS_RISE_X = 2000`）| 与第一条有效行的 `in_hs` 同拍 | ①：这正是为了躲开同拍撞车。**躲开撞车的代价是丢掉整个判据** |

第三行值得单独说。`cam_vs` 晚到 ⇒ `scaler_720` 的垂直游走从**源第 1 行**起算 ⇒
输出第 k 行由源第 k+1 行构成 ⇒ **整帧下移一行**。
在「判据坏了」的前提下这完全看不出来；判据修好之后，行比对**怎样都过不了**，
因为每一行的内容都对，只是错了一行。

> **通则：修 bug 之前，先确认测试台能产生这个 bug。**
> 这一轮挖出的 8 个「DUT bug」里有 7 个是测试台/脚本的问题。这次反过来了 ——
> 测试台的「规避」掩盖了 3 个真 bug，并且让判据在整轮里说不出话。

### 帧相位：`hdmi_out` 的行槽环有一个固定偏移，不是 0

`hdmi_out` 是 8 个行槽的**环**，读端的帧边界是它自己的 `vsync`，**行槽里没有行号**，
所以显示帧相对生产者的第 0 行必然有一个固定偏移（= 环的占用）。
1080p60 → 720p60 实测 **2 行**（修前读数），且**恒定**：两个帧周期都恰好 1 237 500 拍
（1125×2200 cam_clk 与 750×1650 rclk），占用不变。
代价是显示帧的头两行是上一帧的最后两行 —— 肉眼不可见。

> **对齐修复后这个占用变成恒定的 1 行**：全量套件的 10 个相位 `phaseErr` 列**全是 1**，
> xsim `tb_e2e` 报 `capture row 0 = golden row 719`（= 向后 1 行），两个独立测试台一致。
> 修前它随起始相位在 2/5/8… 之间变，修复后对齐循环把两个帧边界钉在一个固定关系上，
> 占用对所有相位都一样。模型本身允许**任意恒定**偏移，所以判据不用改。

所以判据改成：**在最佳帧相位上必须逐像素全等**，且**相位不许自己漂移**
（漂移 = 滚动画面，那才是真故障）。要求相位为 0 是要求一个这套结构给不出来的东西。

### 端到端挖出来的两件事

**① `scaler_720` 的输出行没有上限（真 bug）**

`v_step` 由 `v_frac`/`v_src_h` 算出，**从不看 `out_y`**；
而 `scaler_720.v` 里 `out_y <= out_y + 16'd1` 没有上界。
于是垂直游走冲过输出帧的末尾，继续交换缓冲、继续翻转 `pub_tog`，
一直跑到**源帧**结束才停。

实测：源是 2200×1125 时，每帧推出 **779 行**，而 `DST_H` 只有 720。
多出的 59 行把行槽灌满 —— 实测每帧丢弃 `450 839 / 6 = 75140 px ÷ 1280 = 58.7 行`，
和 59 吻合到小数点后一位。

**单模块测试台抓不到这个**：`tb_scaler_720` 只检查**已经推出来的那些行**对不对，
推多推少它不管。

改法是给 `out_y` 加上界：到 `DST_H` 之后游走照常推进相位（保证下一帧起点正确），
但不再宣布新行。

**② 启动瞬态：把测量帧的垃圾数据喂进了不可反压的 FIFO**

`scaler_720` 需要一帧来测源几何。在那之前它的水平游走以 `h_src_w = 1` 起步
（`scaler_720.v:300`，模块自己在 `:58-59` 也说明了这点），吐出**数值上无意义**的行。

改法是把顶层写口用 `scaler_locked` 门控：

```verilog
wire pix_valid_gated = pix_valid && scaler_locked;
```

`scaler_locked` 只在 `frame_start` 翻转（`scaler_720.v:302`），不会在帧中间跳变，
所以不可能截断半行。代价是上电到锁定之间显示器是黑的 ——
**这是正确行为**，严格好过显示一张正在悄悄损坏的画面。

效果：`stat_dropped` 从 298 240（全部集中在第一帧）变成 **0**。

### 端到端测试台自己踩的六个坑

| 坑 | 表现 | 真因 |
|---|---|---|
| **判据能对零报 PASS** | scaler 一行都没出，`locked=0`，却报 `PASS` | 捕获缓冲全是 0，而 `gold[0][0]` 也恰好是 0 —— **拿两个 0 比 0 等于什么都没验** |
| **判据读不到的计数器** | 720 行内容**全错**，仍报 `PASS: content exact on every frame` | `line_miss` 是 task 局部变量，判据读的是 `pre_fail`/`seq_bad`。**读不到的计数器不是判据。**修好后才暴露出上面的三个真 bug |
| 源 `cam_hs` 没做垂直门控 | 测出 1125 行而非 1080 | 消隐行里 `in_hs` 也是高，`line_start` 多触发 45 次 |
| `cam_vs` 与 `cam_hs` 同拍上升沿 | 测出 6479 行，`locked` 永不置位 | `scaler_720` 在 `frame_start` 清零 `lines_in_frame`（:305）、在 `line_start` 递增（:357），**后写的赢，清零被覆盖** |
| **为了躲开上面那条而挪 `cam_vs` 相位** | 「修好」了，然后整轮判据失效 | 同拍**是硬件的既有条件**（`cam_data_en = cam_vs & cam_hs`），不是可以商量的约定。把它挪到有效像素之后，垂直游走就从源第 1 行起算，输出第 k 行由源第 k+1 行构成 —— **测试台绕开的是一个真 bug，代价是丢掉了整个判据** |
| 把同一个 `cap` 缓冲比了 6 遍 | 看起来像 6 帧证据 | `cap` 是单帧循环缓冲，逐帧索引比较的是同一份数据 |

前两条是这一整轮最要紧的：**如果只比对内容，一个完全不工作的 DUT 也能 PASS；**
**如果内容比对的结果没人读，它同样什么都算不上。**
所以现在所有前置条件都单独断言：`locked` 必须置位、必须有行推出、
几何必须等于 1920×1080、黄金模型和捕获缓冲都**不许全零**。

第四条那格原来写的是「正确做法是让 `cam_vs` 成为完整帧级方波、只是上升沿相位后移」——
**那句话是错的**，而它正是把这一轮带偏的原因。`cam_vs` 在上电后的第一条有效行之前变高，
在最后一条有效行之后变低，中间必须**连续**为高（不能每行翻转）；
而它的上升沿**必须在第一条有效行的 `in_hs` 上升沿之前或同拍**。
「完整帧级方波」对，「相位后移」错：同拍这条约束来自 `rx_sdi` 的数据使能，
改掉它等于给 DUT 喂一帧比真实源少一行、而且行内容整体错位一行的激励。

## 四、真实视频、极限用例与行槽环的对齐（校机，Verilator；2026-10-16 首轮，2026-10-17 补 3b/3c：修复与实测）

本机 xsim 只跑到「合成图案 + 几帧」的规模，答不了三个问题：真实视频的**帧间差异**、
长时间运行会不会**累积失配**、以及**源和光栅的帧边界对不上时会怎样**。这一节在**校机**上跑：
Verilator 5.050 + C++ 测试台（`sim/vlt_top.v` + `sim/harness.cpp`），源是真实的
H.264 解码帧（`data/frames/bbb.rgb565`：Big Buck Bunny 1920×1080；
`data/frames/parkjoy.rgb565`：Park Joy 1920×1080p50，都是 RGB565 原始序列）。
这一轮**最重要的结论在第 3 小节**：环有 8 个行槽 ⇒ 上界 ±8 行，实测干净区约 ±7 行，
而板上的源相位是任意的——**这是上板前的阻塞项**。
跑法与坑记在 `doc/03-flow.md` 第六节；本机构建 Verilator 是不行的（校机才有）。
校机上的 `sim/harness.cpp`、`sim/vlt_top.v`、`rtl/scaler_720.v`、`rtl/hdmi_out.v`
与工程**逐字节一致**（md5 已核），所以这一节的读数对应的就是工程里这份 RTL。
判据本身做过**确定性对照**：同一个二进制连跑两遍、再从同一份源码重新构建跑一遍，
三次逐字节相同（那次对照是为了排除「相位表结果随机」这种可能，见 3. 小节的 ⚠️）。
套件脚本 md5：`suite_school.sh` = `7bb5d2c4…`、`suite_school_window.sh` = `cae9491b…`。
> **2026-10-18 注**：这两个 md5 是**校机那一份**的。脚本已入库到 `sim/`，入库时改了两行
> 与机器绑定的路径（`cd /d/yzd/sdi2hdmi` → `cd "$(dirname "$0")/.."`；`rtl/*.v` → `rtl/sdi2hdmi/*.v`），
> 所以 `sim/` 里的正本是 `suite_school.sh` = `07621e0d…`、`suite_school_window.sh` = `4c668976…`。
> 改动只碰路径、没碰判据与用例，上面的读数仍由 `7bb5d2c4…` 那一份产生。

判据：**每一帧显示内容逐像素等于规范模型**，允许一个**恒定的**帧相位偏移
（行槽环的占位无法与生产者对齐），相位一旦漂移就算错。所以「滚动」会 FAIL，
「整体下移 2 行但不动」会 PASS。

> ⚠️ **除非特别说明，下面第 1、2、4、5 小节的每个用例都跑在测试台的默认源相位上**
> ——也就是源的第 0 帧和光栅的第 0 帧**同时**从复位释放点开始。**真板上这个相位不存在**
> （SDI 是自由运行的外部输入），而相位差要落在 **约 ±7 行**（环给的上界是 ±8 行）以内才干净。
> 所以那几节的 PASS 证明的是「**对齐之后**逐像素正确」；对齐本身的问题见第 3 小节。

### 1. 真实视频：30/60 帧逐像素通过

| 源 | 帧数 | 结果 |
|---|---|---|
| `bbb.rgb565`（Big Buck Bunny 1080p H.264） | 30 | ✅ `PASS: 30 real output frames pixel-exact` |
| `bbb.rgb565` | 60 | ✅ 同上 |
| `parkjoy.rgb565`（Park Joy 1080p50 素材） | 12 | ✅ `PASS: 12 real output frames pixel-exact` |

> 素材只是「内容」：测试台一律按 **1080p60 的 2200×1125 光栅** 驱动（`cam_clk` 固定
> 148.5 MHz），所以 50 Hz 那份素材也是当 60 Hz 光栅喂的。要验「源真是 1080p50 光栅」，
> 走下面的 `--geom2` 边界表。

**这一条第一次跑是 FAIL，但错在判据、不在 DUT。** 2345/921600 像素不符，
`[bisect] scaler stream : 0 of 921600 pixels differ` —— 缩放器流本身一个像素不差，
问题出在显示帧的**帧相位模型**：实测相位偏移是 2 行，而这 2 行**跨帧边界**，
显示帧最上面 2 行是**上一帧**的最后 2 行（`gbring` 那套单帧循环移位模型
把第 0 行对到本帧第 718 行，于是永远差 2 行）。修掉后 30/60/12 帧全过。

> **合成图案看不见这个 bug**：图案是**逐帧不变**的（种子固定），
> `golden(f) == golden(f-1)`，所以任何忽略上一帧的模型都能过。
> 只有真实视频的帧间差异能把它暴露出来。这条是「为什么必须找真实源」的实证。

### 2. 极限图案与长跑：12 + 2 全过

### 3. 事件恢复（**修前**）：解锁/换几何能恢复，复位留下永久损伤（同一个相位窗口问题）

> **这一小节的 ❌ 是修前的状态**（2026-10-16）。修复之后（2026-10-17）三个复位用例
> **全部恢复**：过渡期之后逐像素全对，复位只留下一次性的过渡（几何锁要重量一帧）。
> 见第 3b 小节实测 3 与第 3c 小节（过渡期里那次失败比较是测试台窗口开窄了）。
> 下面这份记录保留，因为它就是「为什么必须修」的证据。

| 事件 | 结果 |
|---|---|
| 源解锁 2 帧再锁回 | ✅ 12 帧逐像素通过（重新锁定时先重测几何，见下） |
| 几何 1920×1080 → 1440×1080（光栅 2200×1125 不变） | ✅ 通过 |
| **中途复位（`--reset-frame`）** | ❌ **永久 23 行/帧损失，20/20 帧全错** |
| **复位后再解锁一次（12-13 帧）** | ❌ **不恢复**，16/18 帧仍错 |
| **复位后再换一次几何** | ❌ 不恢复，18 帧仍错 |

复位那一行是这一轮最重要的发现。数据（24 帧长跑，复位在第 6 帧）：

```
[diag] src  7: rows  +720  dropped +336378  held +336640 | src_h 518 ... locked 0   <- 复位后第一帧
[diag] src  8: rows  +720  dropped  +29702  held  +29440 | src_h 1080
[diag] src  9: rows  +720  dropped  +29440  held  +29440
...
[diag] src 27: rows  +720  dropped  +29440  held  +29440   <- 跑完 24 帧，一帧没变
FAIL: 25 problem(s), 20 frame(s) mismatched
```

`29440 px = 23 行`。**每一帧都丢 23 行、同时又有 23 行是重复的，然后永远停在这个状态**：
`src_w 1920 / src_h 1080 / locked 1` 全部正常，只有画面不对。
对照实验（同样 24 帧、不复位）：`dropped 0 / held 0`——但**那只是因为测试台默认让源和光栅同时起跑**，
见下面「这一轮先得出了一个错误的结论」那一段。

中途复位之所以必然落进这个状态：复位把源的帧相位挪到了一个**环吸不住**的位置
（这一例稳态损失 `dropped +29440` = 23 行/帧，按「偏差 − 7」反推相位差约 30 行
= 99 000 camclk，正好落在第 4 小节相位表里 100 000 那一点上），和那一小节是同一个机制。
「再解锁一次也救不回来」也是同一个道理——**解锁并不会把相位搬回窗口里**。

**故障位置是干净的**——`reset` 用例的 bisect 输出：

```
[bisect] scaler stream :      0 of 921600 pixels differ   <- scaler_720 与写侧一个像素不差
[bisect] hdmi capture  : 72630 of 921600 pixels differ   <- 全部差异在行槽环这一侧
[bisect] => the scaler stream is exact; the difference is downstream (hdmi_out / the ring)
```

> ⚠️ 最后那行结论**当时是反的**：harness 里的判据写成 `if (sb != cb)`，
> 于是「写侧 0 差异、显示侧 72630」这种最典型的下游故障，它偏偏打印
> `=> the scaler stream is already wrong; hdmi_out is not the one to fix`。
> 数据一直是对的、**结论行**是错的，已改成 `sb > 0` 才算写侧有错（2026-10-16）。
> 这一轮记在 `doc/03-flow.md` 坑 31：**判据打印的结论也要能被它自己的数字支持**。

机制：显示侧的帧边界和写入侧（源）的帧边界是两个各自自由的节拍，
环只有 **8 个行槽**，所以吸收能力的**上界**是 ±8 行 = ±26 400 camclk
（读侧一行 = 1650 rclk = 3300 camclk）；**实测可用窗口还要小一点，约 ±7 行**：
干净区到 6.1 行（20 000 camclk），而整 8 行（26 400 camclk）那一点已经 FAIL。
偏差超过它，环满时写侧丢行、环空时读侧重复行；
丢行会把流**提前**，于是系统**自己往回走**——但只走到刚出窗口的位置为止，
于是损失**稳定**下来，**再也不会回到 0**。

**这条窗口是量出来的，不是推的**（`sim/suite_school_window.sh`，16 个相位，
每个跑 12 帧、取**后 4 帧**的稳态）：

| 源落后光栅的相位 | 折算成行 | 稳态丢弃 / 重复 | 判定 |
|---|---|---|---|
| 0 / 1 000 / 5 000 / 10 000 | 0 / 0.3 / 1.5 / 3.0 | 0 / 0 | ✅ PASS |
| 20 000 | 6.1 | 0 / 0 | ✅ PASS |
| **26 000 / 26 400** | **7.9 / 8.0** | **1 280 / 1 280（1 行）** | ❌ FAIL |
| 30 000 | 9.1 | 2 560 / 2 560（2 行） | ❌ FAIL |
| 50 000 | 15.2 | 10 240 / 10 240（8 行） | ❌ FAIL |
| 100 000 | 30.3 | 29 440 / 29 440（23 行） | ❌ FAIL |
| 1 237 500（半个帧周期） | 375 | 30 720 / 30 720（24 行） | ❌ FAIL |
| 2 400 000 | 727 | 20 480 / 20 480（16 行） | ❌ FAIL |
| **2 465 000（= −10 000）** | −3.0 | 0 / 0 | ✅ PASS |
| 2 474 000（= −1 000） | −0.3 | 0 / 0 | ✅ PASS |

三条读数：**窗口就是「环的槽数 − 1」那一档**（20 000 = 6.1 行干净、26 000 = 7.9 行就脏、
26 400 = 整 8 行也脏）；
**损失随偏差增大**，但**有上界**（约 24 行/帧）不无限涨；
**窗口是对称的**（`2 465 000 = −10 000` 干净、`2 448 000 = −27 000` 脏）。

> ⚠️ **这一轮先得出了一个错误的结论，必须撤回。**
> 第一、二轮套件（用的是更早的一个 `obj_harness/harness` 二进制）的相位表是
> **8 个点全部 PASS、0 损失**，于是写下「上电路径实测干净」。
> 用当前源码重新生成二进制之后，同一张表变成**只有相位 0 干净**，
> 而且**确定性可复现**（同一个二进制跑两遍、以及从同一份源码重新构建，
> 三次结果逐字节相同；`sim/suite_school_window.sh` 就是为此写的）。
> 那次「全过」是**旧二进制**给出的假 PASS：它的 8 行读数**逐项相同**
> （连 `held 924159` 都一样），而 `held 924159` 正好是相位 0 的值——
> 也就是那 8 次跑的大概率都是相位 0，旧构建没有按 `--start-phase` 换激励。
> 教训：**判据的输入有没有真的进到 DUT，要和判据的输出一起看**。
>
> 更关键的是**测试台默认的那个相位本身就不物理**：`--start-phase 0` 时，
> 源的第 0 帧和光栅的第 0 帧是**同一个复位释放点同时开始**的
> （harness 里两者都由 `rst_n` 释放驱动），相位差天然约等于 0 行 ⇒ 必然干净。
> **真板上做不到这件事**：SDI 源是自由运行的外部输入，FPGA 配置完、光栅先跑起来，
> 源是后来才锁上的，**相位是任意的**。
> 也就是说这一节里所有 PASS 的用例（真实视频、12 种图案、60 帧长跑）
> 都是在**板子产生不出来的对齐相位**下跑的——和坑 17 是同一个毛病，
> 只是这次犯的是相位，而不是 `vs`/`de` 的组合。

**所以上板会看到什么**（当前 RTL）：画面**不滚动**，但有**稳定的横带**——
每帧丢/重复 `约(偏差 − 7)` 行（1～24 行，0.1%～3.3%；
`7` 就是上面量出来的窗口那一档 = 槽数 8 减 1，与窗口表逐点对得上：9.1 行 ⇒ 2 行、15.2 行 ⇒ 8 行、30.3 行 ⇒ 23 行），
横带的位置和宽度**恒定**。这是「不能上板」级别的问题，不是「上板后再调」。

**结论：这个对齐机制是上板前的阻塞项，不是可选项。** 最小做法是在 `hdmi_out` 里让读侧光栅的帧边界
跟写侧的帧标记走：写侧每个 `frame_start` 发一个标记（跨时钟域两级同步）,
读侧发现自己和标记差得超过行槽深度时，**把当前这一帧拉长（或缩短）一次**，
之后两个边界同相、永久锁住。代价是一次性的**一帧长度**变化（≤ 16.7 ms，显示器
最多丢一帧，看不到撕裂），约 20 个触发器 + 一个计数器，不占 BRAM。
**校正一次就够了**：两边时钟同源（一个 MMCM 出 148.5 与 74.25/371.25 MHz），
锁上之后不会自己漂。**验收判据就是上面那张窗口表**：16 个相位全部要
`dropped 0 / held 0`、全 PASS（测试台已经准备好了）。**结果见第 3b 小节。**

### 3b. 修复与实测：一次性消隐插入（2026-10-17）

**机制**（`hdmi_out.v` 的 `align_sum`／`align_want`／`align_take`／`v_extra`）：

写侧（camclk 域）

- `scaler_720` 每帧**在推送第一条行的那一拍**发一个标记（`out_frame`，由 `frame_start` 打拍），
  它跟行槽数据一起过 CDC —— 所以「这一行属于哪一帧」不会错位；
- 读侧两级同步（`wf_s1/s2/s3`），标记到达沿采样当前光栅行号 `p = vcnt`。

读侧（rclk 域）

```
add = (p + ALIGN_EPS) mod V_TOTAL          ALIGN_EPS = 4，V_TOTAL = 750
```

- **只拉长、不缩短**：`v_extra` 从 `add` 递减到 0，期间 `vcnt` 停在 `V_TOTAL−1`
  （`in_extend`），行槽取行照发（`claim_now` 在 `in_extend` 里也成立），
  被跳过的内容落在**显示帧边界**上、`de = 0`，肉眼看不到；
- **死区**：`2 ≤ add ≤ 748` 才动手。跳过 `add ∈ {0, 1, 749}`：0/1 是「已经在目标上」，
  749 是「为了 1 行去拉长 749 行」。**`add = 748` 会做**（相位早 2 行，一帧双倍长把它正好
  落到目标上）⇒ 收敛后的相位是 `p = 746`（= `V_TOTAL − ALIGN_EPS`），或者 745/747
  那两种「修它的代价正好是跳过的那一档」；
- 拉长期间到达的标记一律忽略（`vcnt` 被停住，采到的 `p` 没有意义），
  帧计数 `stat_frames` 也只在 `v_extra == 0` 时累加 ⇒ **下一次标记重新测量**；
- 两边帧周期本来就严格相等（1125×2200 camclk = 750×1650 rclk，同一个 MMCM）⇒
  校正一次之后距离不变 ⇒ **只校正一次**。上电自启动、失锁重锁后自动重来（源丢了就不再发标记）。

**为什么只能拉长**：缩短要从可见光栅里切行。更硬的一条理由是速率：
读侧一行占 3300 camclk、写侧按每帧 720 行的节奏供行；把帧切短到 `< 750` 行，
读侧会在**比一帧短的时间内**仍取满 720 行，于是环被抽干到**可见的 active 区**里——
那不是一次性的帧边界修正，而是把一截横带永久留在画面里。
（`v_cut` 方案是这一轮做完分析后否掉的，别重新捡回来。）

**实测 4：本机 xsim 的独立复核（连续源，三个起始相位）**

校机那套是 Verilator + C++ harness；本机 `sim/tb_e2e.v` 用一条**同构但独立**的激励路径
复核同一件事：`+hold=<源行数>` 把源**在消隐里**推迟 N 行再起跑
（1 源行 = 2200 camclk = 2/3 光栅行），之后源仍是连续的 1125×2200、**没有插入时间**
—— 是相位移动，不是「等输出帧」那种把源停住的假相位（对照 3c ①）。三个相位：

| `+hold` | 折算相位 | 第一次校正 | 拉长次数 | 稳定窗口后的新拉长 | 最后干净标记的 want | 逐像素 | 稳态丢弃 |
|---|---|---|---|---|---|---|---|
| 0 | 0 行 | 4 行 | 1 | 0 | 0 | 720/720 行 | 0 |
| 1091 行 = 2 400 200 camclk | 727.3 行 | **731 行** | 1 | 0 | 0 | 720/720 行 | 0 |
| 1113 行 = 2 448 600 camclk | 742.0 行 | **746 行** | 1 | 0 | 0 | 720/720 行 | 0 |

后两行的相位对着校机证据跑的 2 400 000 / 2 448 000（只差 200 / 600 camclk，同一组折算行）：
**两个仿真器、两套测试台给出同一个校正量**，`731 = 727 + 4`、`746 = 742 + 4` 与公式一字不差。
「最后干净标记的 want = 0」是收敛点的正面证据：循环不是「停手」而是**停在死区里**
（`want ∈ {0, 1, 749}` 才合法），这条现在直接写进了 xsim 判据。
启动瞬态照旧是一次性的：h1091 在校正落地前丢 19200 px（15 行）+ 一次 ring overflow，
h0 / h1113 为 0；稳定后逐帧 `+720 行 / +720 取行 / +0 丢弃`，环占用恒 1 行
（`frame phase 719`，与校机 10 个相位的 `phaseErr = 1` 一致）。

> 这一小节的两个读数是在同一轮里被修正的，都属于「监看会撒谎」这一类：
> ① 最初打印的 `settled want` 读的是**打印时刻**的 `align_want` —— 自由运行的光栅行号、
> 任意瞬间的值，看着像「收敛到别处」；判据里也根本没有读收敛相位。现在监看在
> **标记到达那一拍**采样、拉长期间的标记（`p` 没有意义）跳过，并把「最后一个干净标记的
> `want` ∈ 死区」写进 PASS/FAIL。② 旋钮第一版**单位没换算**，三个不同 hold 全是相位 0
> 且全绿 —— 完整复盘见 `doc/03-flow.md` 坑 36。

### 3c. 测试台侧的两个假象（都在校机 harness 上踩到）

**① 等待循环把源停住 ⇒ 极限环。** 修好之后第一次跑 2 400 000／2 448 000 两个相位，
结果是**每帧都重新拉长一次、幅度还每次都对**（`steadyDrop 28160`＝22 行/帧、
`steadyHeld 920320`、`wrongpx 920309`；15 帧里 15 次 stretch）。原因在 harness 的
「驱动一帧 → 等一个输出帧完成」，而那个「等」只推时钟、不驱动源：对齐机制把一帧拉长到
~1481 行时（实测最长 746 行 ⇒ 1496 行；算术上限是 1498 行），750 行的驱动窗口里可能一个输出帧边界都没有，等待于是变成最长 16 ms 的**源停机**，
源一停，它的帧边界相对光栅就**在时间上挪了**，挪掉的距离正好是刚校正掉的那段 ⇒ 下一帧
测出来还是同一个 `p`。**测量对、装载对、相位不动**，这就是环境把输入又造了回来。
改成「帧背靠背驱动 + 比较最新一个完整输出帧 + 没有新输出帧就不比较」之后，
同一张表 16/16 全过。完整记录见 `doc/03-flow.md` 坑 32。

**② 比较被推迟之后，事件窗口要跟着加宽。** 比较的对象从「恰好这一帧的输出」
变成「最新一个完整输出帧」，于是**比较可以滞后驱动最多 2 个源帧**（黄金搜索范围是
`f / f-1 / f-2`）；再加上复位会把几何锁打掉（重新量一帧）。事件窗口只留 1 帧时，
复位用例**只有一次比较**失败（`FAIL frame 5`，即 `f = 9`，复位在帧 6；
`best per golden 1278/1278/1278` —— 1278 px 正好是一行的量级，典型的「比较落在了过渡帧上」），
而它之后的每一帧都逐像素通过 —— 这正是「过渡期比较」的签名，不是设计没恢复。
窗口加宽到**事件长度 + 4 帧**（2 帧比较滞后 + 2 帧余量）后，三个复位用例全过。

### 4. 契约的精确化：两条等式，不是一个

这一轮把「光栅必须匹配」说清楚了。显示侧要的是**两条**都成立：

```
active 窗口 = 有效行数 × 总宽度  = 1080 × 2200 = 2 376 000 camclk   （720 行 × 3300）
帧  周期   = 总行数   × 总宽度  = 1125 × 2200 = 2 475 000 camclk   （= rclk 1 237 500）
```

对 1080 行的源，这两条**联立只有一个解：2200 × 1125**，也就是 1080p 标准消隐。
测出来的边界（`--geom2` 切到该光栅，10 帧，切后比较）：

| 切到的光栅 | active 窗口 | 帧周期 | 结果 |
|---|---|---|---|
| 1920×1080×2200×1125 | 2 376 000 ✅ | 2 475 000 ✅ | ✅ 逐像素通过 |
| 1440×1080×2200×1125 | 2 376 000 ✅ | 2 475 000 ✅ | ✅ 逐像素通过（水平消隐变宽而已） |
| 1920×1080×2250×1100 | 2 430 000 ❌ | 2 475 000 ✅ | ❌ 430/720 行错，丢 121 600 / 重复 1 057 279 px |
| 1920×1080×2200×1200 | 2 376 000 ✅ | 2 640 000 ❌ | ❌ 找不到一个相位能对上任何一行，丢 264 960 / 重复 1 524 500 px |
| 1920×1080×2376×1125 | 2 566 080 ❌ | 2 673 000 ❌ | ❌ 找不到相位，丢 268 800 / 重复 1 955 860 px |
| 1280×720×1650×750 | 1 188 000 ❌ | 1 237 500 ❌ | ❌ 找不到相位，丢 1 154 772 / 重复 1 170 345 px |

> 上表的丢/重复计数是 **2026-10-17 那一轮**（harness 改成连续驱动之后）的读数，
> 与 10-16 首轮的数字不同 —— 变了的是「一个用例里跑了多少模拟时间」，
> 因为旧的等待循环会顺带多推几百行时钟。**判定与结论一字未变**：
> 每一条都是「行错多少」这个更硬的量在说话（第一行 430/720 是最能说明问题的那条：
> 帧周期完全正确，光栅边界错，于是一整幅画面里有 430 行对不上）。

**帧周期对上不够**（第三行：帧周期 ✅ 而 active 窗口 ❌）。
**反过来 active 窗口对上、帧周期不对也不行**（第四行）。
所以这本书写的「帧率不匹配时是丢帧/保持」只是**周期**那一半；
真正决定画面撕裂的是 active 窗口那一半。

> ⚠️ **WNS 从 +0.116 ns 掉到 +0.016 ns**，因为端到端那轮改了三处 RTL
> （`scaler_720` 的 `out_y` 上界、`claim_now` 恢复 `in_vact`、顶层写口门控），
> 布局跟着挪了。**16 ps 的余量等于「几乎贴线」**：
> 换 Vivado 版本、换约束顺序、或者再动一点逻辑都可能翻负。
>
> 这不是「达标了就不用管」，而是**余量已经薄到必须记下来**。
> 真要加功能或再改结构，这一条要重新盯。
> （对齐修复后重跑是 **+0.026 ns** —— 第 7 步，结论不变：还是薄。）

### 收敛过程：七步，每一步都改了真东西

| | WNS | 失败端点 | 改了什么 |
|---|---|---|---|
| 起点 | −5.278 ns | 2 538 | — |
| 第 1 步 | **−0.360 ns** | 8 | 行缓冲落进块 RAM（见下） |
| 第 2 步 | −3.667 ns | 153 | 修一个**真的** CDC bug（工具抓到的） |
| 第 3 步 | **+0.027 ns** | **0** | 修 XDC 未生效 |
| 第 4 步 | −0.008 ns | 1 | 修 `cam_clk` 域复位没本地同步 |
| 第 5 步 | **+0.116 ns** | **0** | 补厂商 QPLL 复位跨域假路径 |
| 第 6 步 | +0.016 ns | **0** | 端到端那轮的 RTL 改动挪动了布局（见上注） |
| 第 7 步 | **+0.026 ns** | **0 / 13 526** | 对齐修复 + 它自己那条假路径（新 CDC，见下） |

### 第 1 步：行缓冲落不进块 RAM

八个独立数组 + `case (w_slot)` 写口的写法，Vivado 推断成分布式 RAM，
`ram_style="block"` **被静默忽略**（综合报告里明明白白 `RAM64M => RAMD64E: 800 instances`）。
最差那条路径 **77.08% 是布线**，不是逻辑。

改成 Vivado 认得的教科书模板：**一个数组**、地址拼接、读写各一个 always 块。
块 RAM **0.5 → 8.5 tiles**，LUT **7 903 → 3 358**。

### 第 2 步：工具抓到一个真的 CDC bug

```
Slack (VIOLATED) : -3.857 ns
SRC: u_hdmi_out/r_gray_s2_reg[1]/C
DST: u_hdmi_out/r_bin_reg[1]/CE
```

原写法把**一个**同步器组放在 `wclk` 域，`empty` 因此是 wclk 域的信号，
却被 **rclk 域**的 `r_bin` 当使能用。异步 FIFO 必须**每个方向一条链**，
各自用**消费它的那一侧的时钟**。已改成两条独立链（`w_gray_r1/r2` 在 rclk 域）。

> **这一条值得单独记**：它不是工具误报，是真的跨域用错。
> 假警告可以压制，真 bug 压掉就埋雷了。

### 第 3 步：假路径从来没生效过

修完 CDC 后 −2.788 ns 仍在。查下来是：**`open_checkpoint` 不重新读 XDC**。

`impl_only.tcl` 早期版本只手动重放了 REQP 降级，**漏掉了 CDC 假路径**，
所以它在综合阶段存在、在实现阶段等于不存在。修法是在 `open_checkpoint` 之后
`read_xdc` 整份约束。

顺带修了一处写法错误：假路径原来按 pin 过滤且写的是 `/Q`，
而报告里时序路径的源是寄存器**时钟脚** `/C`，所以一条都没匹配上。改成 cell 级过滤。

### 第 4 步：复位没在它服务的那个域里同步

```
Slack (VIOLATED) : -0.008 ns
SRC: rst_sync_reg[2]/C
DST: u_hdmi_out/mem_reg_1/ENARDEN
Requirement 5.000 ns, data path 6.417 ns
logic 0.266 ns (4.1%), route 6.151 ns (95.9%)
```

`cam_clk_rst_n` 原来直接取 `rst_n_sys`，也就是 **sys_clk_200m 域**的同步器输出，
直接当 `cam_clk` 域的复位用。两个问题叠在一起：跨域（复位相对 cam_clk 异步），
以及**高扇出** —— 它要驱动整个写侧，最关键是行槽块 RAM 的 `ENARDEN`。

**95.9% 是布线**，几乎全是单条网的走线问题，不是逻辑深度问题。
改成在 `cam_clk` 域本地再同步一级（异步置位、同步释放），
见 `rtl/sdi2hdmi_top.v`。`ENARDEN` 现在由本域寄存器驱动，走线短了。

### 第 5 步：厂商 GT 的 QPLL 复位跨域

```
Slack (VIOLATED) : -0.028 ns
SRC: rx_sdi_inst/SDI0/SDI/GTX_CTRL/RXRST/pll_reset_reg/C
DST: rx_sdi_inst/gtxe2_common_0/qpll_reset_r_reg/D
```

第 4 步改布局，把这条**原本就过**的路径挤过了线。两个时钟无关联：

```
clk_out1_sys_clk   37.037 ns  (27 MHz)
clk_out1_mgtclk     6.734 ns  (148.5 MHz)
```

27 MHz 和 148.5 MHz 没有有理比，**本来就不该被当数据路径计时**，
放多少布局技巧都没意义。`qpll_reset_r_reg` 是厂商 GTX common 封装里的
复位同步器（异步置位、同步释放），正是那种不该计时的结构。

加了一条**只框住这两个寄存器**的假路径。框宽了会把接收器里真正同步的部分
也一起停掉检查 —— 这条约束是为去掉一个跨域，不是给一片区域开免检。

> **必须说明白**：这条路径以前也是过的，但余量从来不是真的，只是碰巧。
> 它一直缺约束，只是布局没动到它而已。

### 5.4 剩余的唯一一条时序余量说明

`u_scaler/out_x_reg/C → u_scaler/lb*/DP` 按 **5.000 ns（200 MHz）** 计算，
因为 `rx_sdi.v:368` 用的是
`cam_clk = rx0_locked ? rx_usrclk : sys_clk_200m` —— **被复用的时钟**。
3G-SDI 下 `rx_usrclk` 实为 148.5 MHz（6.734 ns），所以真实余量还要大一截。

**真正的修法是停止复用时钟**，那是改厂商接收器的活，本工程没做，记在这里。

### 第 6 步：端到端那轮的 RTL 改动（2026-10-16）

三处功能修复（第四章第一、二小节：`scaler_720.out_y` 上界、`claim_now` 恢复 `in_vact`、
顶层写口门控）本身不是时序改动，时序上是**布局被动挪动**：+0.116 → +0.016 ns。
记在这里是为了让 WNS 的演化不断线——**改功能一样会吃掉余量**。

### 第 7 步：对齐修复（2026-10-17）—— 一次新 CDC，一条新假路径

对齐机制给写侧帧标记加了一条**新的跨时钟**：`scaler_720.out_frame`（camclk 域）
→ `hdmi_out` 的 `wf_s1`（rclk 域）。本工程的约束风格是**靶向 `set_false_path`**、
不用一刀切 `set_clock_groups`（理由见第 3、5 步：靶向约束只去掉「本来就没有相位关系」
的那条路径，不给一片区域开免检），所以这条新 CDC 要**自己那条**：

```tcl
set_false_path -from [get_cells -hier -filter {NAME =~ *u_scaler/out_frame_reg*}] \
               -to   [get_cells -hier -filter {NAME =~ *u_hdmi_out/wf_s1_reg*}]
```

只切**跨越**的那一段；`wf_s1 → wf_s2 → wf_s3` 是同一域里的同步器级，照常计时。
`constrs/sdi2hdmi.xdc` 第 158-167 行，注释写明了为什么不切整片。

结果：**WNS +0.026 ns、WHS +0.083 ns、失败端点 0 / 13 526**。
新假路径**确实生效**：没有 `17-55`／`no valid objects` 告警，
`wf_s1` 也不再出现在 `timing_routed.rpt` 的路径里。
假路径最危险的状态是「写了但一个单元都没匹配上」（第 3 步踩过），这一条两次都验了。
