## 二、外部规格与公开实测（E1，非本板）

| 项 | 数值 | 来源 |
|---|---|---|
| PS DDR 理论峰值 | DDR3-1066 × 32 b = **4264 MB/s** | Zynq-7000 DS188（1066 Mb/s 上限）；本板 PCW 就是 32 b @ 534 MHz CL7 = DDR3-1066 |
| 4 个 HP 口实测合计 | 1510 MB/s ＝ DDR 可用带宽的 **35%** ⇒ 可用约 4300 MB/s | UG1145 |
| DDR 实测（CPU 侧，顺序 8 B 访问） | 读 656 / 写 2046 MiB/s | JBLopen 裸机基准（-2，800 MHz） |
| **GP0/GP1 数据宽** | **32 bit**（`M_AXI_GP0_WDATA[31:0]`） | IP 生成 HDL |
| **GP0/GP1 AWLEN** | **4 bit ⇒ 单次突发最多 16 拍** | IP 生成 HDL |
| **S_AXI_HP2 数据宽** | **64 bit**（`S_AXI_HP2_WDATA[63:0]`） | IP 生成 HDL |
| **S_AXI_HP2 AWLEN** | **4 bit ⇒ 单次突发最多 16 拍（128 字节）** | IP 生成 HDL |
| S_AXI_HP2 AWID | 6 bit（厂商位流只用 ID=0） | `ps_ai_processing_system7_0_0.v` |
| HP 口 AWLEN | 公开资料说可到 256 拍，**本芯片的 PS7 IP 只放出 4 bit** | 公开工具/学术资料 vs 实测 IP |
| CPU→FPGA（GP1 方向，250 MHz） | 读 312 / 写 492 MiB/s | JBLopen |

**结构性事实**（UG585 + 厂商 2026-10-12 客户说明）：

- `S_AXI_HP0..3` 是**PL 当主机、PS DDR 当从机**的直连高带宽通路，
  PL→PS DDR 走这里；`M_AXI_GP0/GP1` 是 PS 当主机的口。
- **两边都能双向搬数据** —— PL 写 PS DDR 用 `S_AXI_HP*`，
  PS 读 PL 寄存器用 `M_AXI_GP*`，两条路都合法，只是方向不同。
- 本文档原来在这里写过"PL→PS DDR 只能走 GP0/GP1"，是错的（见 §一 的更正框），
  写帧器因此挂到了 PS 的主机口上、整条通路被综合器剪掉
  （`设计说明.md` §6.18）。
- 厂商自己的写帧器 `frame_to_ps_largebuf` 挂 `S_AXI_HP2`，
  本设计照抄这条通路，并照抄端口属性。

### S_AXI_HP2 的硬上限

```
100 MHz × 8 byte/拍 = 800 MB/s
```

本设计的 AXI 主机跑在常驻的 `clk_100m`（不是像素时钟，理由见
`设计说明.md` §3.2），一拍 64 bit。

**但它通常不是瓶颈**：像素接口只有 16 bit，74.25 MHz 下最多产出
`74.25 MHz × 2 byte = 148.5 MB/s`，口是像素口的 **5.4 倍宽**。
所以真正要量的不是"口有多宽"，而是"在突发开销和应答延迟下还能送出多少"。

## 三、实测方法

`sim/tb_sdi_stream_wr.v`（2026-10-15 重写）+ `sim/run_bench.ps1`（套件跑法）。

另有一条独立的 CSR 测试台 `sim/tb_sdi_cap_regs.v`：它不量带宽，量的是寄存器
语义（同一入口，`-Only REGS`，52 项检查）—— 三个 CSR 级 bug 就是它抓的，
见 `设计说明.md` §6.23–§6.26。本文档剩下的部分只管像素链这条。

**三级链整条进仿真**——打包 → 异步 FIFO → AXI 写帧器，两边各自一个时钟，
结构和顶层一一对应（顶层多出来的只有 PS7 和恢复时钟本身），
免得"分开测都对、拼起来坏"。

```
px_clk = 74.25 MHz（或 200 MHz 兜底）    sdi_px_pack -> sdi_px_afifo
ax_clk = 100 MHz                         sdi_px_afifo -> sdi_stream_wr -> AXI 从模型
```

| 参数 | 含义 |
|---|---|
| `AW_LAT` | AWVALID 起来后 N 拍才给 AWREADY |
| `W_LAT` | WREADY 每 N 拍拉一次（真实占空比，不是虚假的"恒 1"） |
| `B_LAT` | 收到 WLAST 后 N 拍才回 BRESP |
| `CYCLES` | 观察窗口（100 MHz 拍数） |
| `RING_BYTES` | 环形缓冲大小，0 = 关回绕；可以小到 16 B（两个拍） |
| `PX_DUTY` | 每 N 拍给一个像素；≥100 = 每拍都给（最坏情况） |
| `PX_MHZ` | 像素时钟 74（正常）或 200（失锁兜底那条路） |
| `RST_MID` | 在途事务没排空就复位（厂商文档的 L4 场景） |

像素源是**连续 +1 的 16 bit 序列**。校验器本身也验过会失败：
把字节序对调，它立刻刷屏报错（一个永远 PASS 的检查比没有检查更危险）。

检查项全部写进一行 `CHECK ...`，跑完由脚本汇总：

| 检查 | 看什么 |
|---|---|
| `data` | WDATA 内容：字内四段连续（`wdata[63:48]==wdata[47:32]+1` …）；字间 上一拍最高段 +1 == 本拍最低段（只在没丢像素时成立） |
| `marker` | 帧标记那一拍的地址 == `frame_start_addr`（层次引用直接比对） |
| `frames` | `frame_cnt == 标记个数` |
| `axi` | 协议：WVALID 提前撤销 / 实际拍数 ≠ AWLEN+1 / AWVALID 期间地址跳变 / WLAST 之后还有拍 |
| `ring` | 所有写地址都落在 `[buf_addr, buf_addr+ring_bytes)` 内（含回绕） |
| `drain` | 停像素后 `idle==1 && inflight==0 && FIFO 残留 < 16 字` |
| `quiet` | 排空之后再等 200 拍，一拍都不许再写 |
| `ovf` | FIFO 满丢过字 ⇒ 写帧器的 `err_stat[0]` 必须置起来 |

> `ovf` 这一条 2026-10-15 才补上。**原来测试台把 `px_overflow` 硬接 `1'b0`**，
> 等于"丢字要报错"这条通路从来没被验过；现在用两级同步器把
> `drop_lo != 0` 的粘滞电平送进写帧器，和顶层 `sdi_cap_cdc` 的做法同构，
> 并且像素域（`drop_seen`）和 AXI 域（`err0_seen`）各自记一笔再比对。

跑法（xvlog/xelab/xsim 取 Vivado 2018.3）：

```powershell
powershell -ExecutionPolicy Bypass -File sim\run_bench.ps1           # 默认 5 个 B_LAT 套件 + REGS
powershell -ExecutionPolicy Bypass -File sim\run_bench.ps1 -Full     # 全 19 个 + REGS
powershell -ExecutionPolicy Bypass -File sim\run_bench.ps1 -Full -Only RING_16
powershell -ExecutionPolicy Bypass -File sim\run_bench.ps1 -Only REGS   # 只跑寄存器块
```

> 参数写在 `bench.txt`（脚本每次覆盖）而不用 `+testplusarg`：Windows 上
> `xsim.bat` 的参数转发会把 `B_LAT=12` 拆开，报 `Expected a switch but found 12`。
>
> `-Only` 里写 `W_LAT_*` / `RING_*` / `PX_*` / `RST_MID` 时必须同时带 `-Full`——
> 这些套件只在 `-Full` 下注册。**脚本原来在这种情况下会打印一句空泛的
> "ALL PASS"**（其实一个套件都没跑），2026-10-15 补了 `NO SUITES RAN` 判据。

## 四、实测结果（2026-10-15，64 位 HP2 版，19 个套件全 PASS）

> 另有一条不量带宽的 CSR 测试台（`REGS`，52 项检查，全 PASS）——
> 读通道死锁、`FPS_X100` 恒 0 这类问题只有它能看见，见 `设计说明.md` §6.26。

### A. 主结果

| 套件 | 吞吐 | 相对 1080p30 | 丢字 | `err_stat` |
|---|---|---|---|---|
| `B_LAT_1 / 8 / 32 / 64 / 127` | **150.91 MB/s** | **121.3%** | 0 | 0 |
| `PX_MHZ_200`（失锁兜底源） | **400.00 MB/s** | 321.5% | 0 | 0 |
| `W_LAT_1` | 150.91 MB/s | 121.3% | 0 | 0 |
| `W_LAT_2 / 4` | 148.00 MB/s | 119.0% | 0 | 0 |
| `W_LAT_8`（WREADY 12.5% 占空比） | 100.00 MB/s | 80.4% | 11226 | `0x1` |
| `RING_0 / 4096 / 128 / 33554432` | 150.91 MB/s | 121.3% | 0 | 0 |
| `RING_1000 / 64 / 16`（环小到 16 B） | 147.97 ~ 148.00 MB/s | ~119% | 0 | 0 |
| `PX_DUTY_8`（每 8 拍一个像素，不丢） | 18.50 MB/s | 14.9% | 0 | 0 |
| `RST_MID`（在途复位） | 150.90 MB/s，复位后自恢复 | 121.3% | 0 | 0 |

口径：1080p30 有效像素需求 = 1920×1080×30×2 = **124.4 MB/s**；
74.25 MHz 像素源供给上限 = 74.25 M × 2 B = **148.5 MB/s**，
打包成 64 bit 拍之后按字节数是 **150.91 MB/s**（拍边界与帧边界对齐的关系）。
`clk_100m` 域 64 bit × 100 MHz 的硬上限是 **800 MB/s**。

### B. 三条硬结论

1. **吞吐与 BRESP 延迟无关**：`B_LAT` 从 1 到 127 拍（74.25 MHz 下 1.7 µs），
   吞吐**一模一样**（150.91）。在途 8 个突发的水线把这层不确定性整个吃掉。
2. **AXI 侧余量极大**：实测 150.91 只是 800 MB/s 硬上限的 19%；
   像素源换成 200 MHz 兜底时能到 **400.00 MB/s**（50%），说明瓶颈确实在像素源，
   不在 AXI 口。
3. **停像素之后是"排空"，不是"立刻空闲"**：最坏（`B_LAT=127`）要 **93 拍**
   才 `idle`，此刻 FIFO 里还剩 **≤15 个字（120 字节）**——那是一个没发完的突发。
   ⇒ `IDLE` **不能用"FIFO 空"来判断**（见 §五）。

### C. W 通道反压（唯一会掉数据的场景）

`W_LAT=1` 全速；`W_LAT=2`（占空比约 50%）仍够 1080p30；
`W_LAT=8`（12.5%）时从设备把吞吐限到 ~100 MB/s，**丢 11226 个字**、
`err_stat[0]` 置位，但**地址不乱、AXI 协议全合法**——宁可丢也不写错，这个取舍是刻意的。

### D. 复位（厂商文档的 L4 场景）

`RST_MID`：在途事务没排空就拉低 `rst_n`，之后写帧器**自己起来**，
0 个 AXI 协议错误、0 个数据内容错误。⇒ 软件侧复位流程不需要为 PL 另做照顾。

### E. 那次"18 个套件全绿"补的是哪两块

19 个套件里，真正补上**新判据**的是两处：
`PX_DUTY_8`（不丢像素模式，字间连续性才严格成立）和 `ovf`
（丢字必须报错）。没有它们，"协议全对、吞吐漂亮、数据是错的"这类问题
和"报错通路根本没接上"这类问题都不会被发现（§六 ⑥⑦ 的教训）。

> ⚠️ 门级（综合后网表）复核**尚未对新链重跑**：`sim/run_gl_bench.ps1` 这套流程
> 是为上一版 32 位链写的。新链的异步 FIFO 是 2 × RAMB36，
> 门级复核要连原语模型一起重搭，列在待办里（下面历史节的 ⑤ 号 bug
> 说明为什么这件事必须做，不能在行为级就算完）。

## 四·历史：32 位 GP0 版（2026-10-14）的数据

> 下面这批数是**上一版设计**（32 位、挂 `M_AXI_GP0`、像素 FIFO 在 `cam_clk` 域
> 同拍直读）测出来的。数字本身可信，但**口径已经不是当前设计**：
> 当前设计一拍 64 bit、走 `S_AXI_HP2`、中间多了一级异步 FIFO。
> 留在这里是为了记住"当时量过什么、怎么量的"，以及 ⑥ 号 bug 的判据怎么来的。
> **引用数值请用上面那一节。**

### A. BRESP 延迟（B_LAT，32 位版）

MAX_OUT = 8，W 通道恒 ready：

| B_LAT | 吞吐 | 协议检查 | 溢出 |
|---|---|---|---|
| 1 | **148.50 MB/s** | PASS | 无 |
| 8 | 148.50 MB/s | PASS | 无 |
| 16 | 148.50 MB/s | PASS | 无 |
| 32 | 148.50 MB/s | PASS | 无 |
| 64 | 148.50 MB/s | PASS | 无 |
| 96 | 148.50 MB/s | PASS | 无 |
| **127** | **148.50 MB/s** | PASS | 无 |

**完全不受 BRESP 延迟影响**，一直到 127 拍（74.25 MHz 下 1.7 µs）。
`inflight` 从 0 涨到 4，说明流水确实在工作。

⇒ **PS DDR 控制器的应答延迟不需要预先知道**，这个不确定性已经被设计吃掉了。

### B. W 通道反压（W_LAT）

| W_LAT | WREADY 占空比 | 吞吐 | 相对 1080p30 | 协议检查 | 数据校验 |
|---|---|---|---|---|---|
| 1 | 100% | 148.50 MB/s | 119% | PASS | PASS |
| 2 | 50% | 132.00 MB/s | 106% | PASS | PASS |
| 4 | 25% | 69.88 MB/s | 56% | PASS | PASS |
| 8 | 12.5% | 37.12 MB/s | 30% | PASS | PASS |

⇒ 要扛 1080p30，`WREADY` 可用的时间比例得 **≥ 约 60%**。
不够时 `ERR.FIFO_FULL` 置位并丢数据，**但 AXI 协议始终合法、地址不乱**——
宁可丢也不写错，这个取舍是刻意的。

> **这张表曾经是危险的。** 跑它的时候 `gcyc`（WREADY 占空比的来源）
> 只声明没自增，`(gcyc % W_LAT) == 0` 恒真，**W_LAT 实际没生效**，
> 测出来的会是四档全 148.50。修复后重跑，数值和上表**完全一致**——
> 说明这组数是在 `gcyc` 还正常时测的，可信；但工具那之后一直是坏的。
> 教训见 `设计说明.md` §6.17：**测试台本身也要回归**。
>
> "数据校验"这一列是新加的（`设计说明.md` §6.15）。加它之前，
> 这一格里跑的是**丢了一半像素**的 RTL，而且四项全绿。

### 结论

| 口径 | 数值 |
|---|---|
| GP0 端口硬上限 | 297 MB/s（74.25 MHz × 4 B） |
| 像素源供给上限 | 148.5 MB/s（74.25 MHz × 2 B） |
| **本设计实测吞吐** | **148.50 MB/s ＝ 像素源的 100%** |
| 1080p30 有效像素需求 | 124.4 MB/s（1920×1080×30×2） |
| **余量** | **1.19×** |

**AXI 通路不是瓶颈**：进多少像素就写出多少，一个字节不差。
瓶颈只可能出现在 W 通道被 DDR 长时间反压时。

> ⚠️ 上面这句"一个字节不差"，在加数据校验之前是**假的**。
> 当时的 RTL 实际发出的是 `{像素, 16'h0000}`，每两个像素只送出一个，
> 148.50 MB/s 里有一半是零 —— 但吞吐统计只数字节，数字照样漂亮。
> 见 `设计说明.md` §6.15。

两者完全一致，**FIFO 确实落在块存储上，存取的数据也是对的**。

## 五、历史：多突发 vs 单突发（32 位版）

> 同样是上一版的对比；结论对现在的设计一样成立，数值属于上一版。

同一份测试台，只改写帧器：

| 写法 | B_LAT=1 | B_LAT=16 | B_LAT=32 | B_LAT=64 |
|---|---|---|---|---|
| 单突发（等 B 再发下一个 AW） | 152 MB/s | 130 MB/s | 90 MB/s | 55 MB/s |
| 多突发 MAX_OUT=8（本设计） | **148.5 MB/s** | **148.5** | **148.5** | **148.5** |

单突发时吞吐**完全由一个查不到的延迟决定**——运气好够，运气差一点就黑屏。
多突发把它变成常数。

## 六、历史：32 位版仿真挖出的七个 RTL bug

> 这一节属于**上一版 32 位链**（它的打包器和像素 FIFO 已经被
> `sdi_px_pack` + `sdi_px_afifo` 取代）。留下的价值在**判据**：
> ①②④⑤ 说明"理想模型下的仿真会漏掉什么"，⑥⑦ 说明"不看数据内容会漏掉什么"。
> 当前版本的 bug 清单在 `设计说明.md` §6.1–§6.20（最新两条是 §6.18 方向错、
> §6.19 时钟没定义、§6.20 应答通道方向写反）。

前五个是"理想模型下完全看不见、真实硬件上直接黑屏"的那一类。
后两个（⑥⑦）更靠后一层：**协议全对、计数器正常、吞吐漂亮，只有数据是错的**。

**没有做这次仿真，位流出来也是废的。**

| # | 症状 | 根因 | 谁抓到的 |
|---|---|---|---|
| ① | 8 个突发后彻底死锁 | `WLAST` 在握手前被无条件撤掉 | 协议检查 |
| ② | 静默写坏数据 | `level` 用错位宽做减法 | 协议检查 + 目视 |
| ③ | 水位跑到 8000+ | FIFO 满时仍递增 `wp` | 环回绕检查 |
| ④ | 少发一拍 | 到齐就撤 `WVALID` | 协议检查 |
| ⑤ | RTL 仿真原理上抓不到 | 像素 FIFO 被综合成块 RAM | **只能门级仿真** |
| ⑥ | **丢一半视频数据** | `acc` 高/低半用反，`{像素, 0}` | **WDATA 内容校验** |
| ⑦ | 每复位多一个全零拍 | `q` 复位后没预取 | **WDATA 内容校验** |

### ① WLAST 在握手之前就被撤掉 → GP0 端口死锁（最严重）

`m_axi_wlast <= 1'b0;` 写在 always 块开头**无条件执行**。
AXI 要求 `WDATA/WLAST` 保持到 `WREADY` 握手为止。一被拉低的那一拍，WLAST 就被清了，
从设备**永远看不到突发结束**，于是永远不回 BRESP，`inflight` 涨到上限后
**写帧器彻底死锁——实测 8 个突发（512 字节）之后一个字节都不再写**。

`WREADY` 恒为 1 时最后一拍同拍收走，所以这个 bug 在理想模型下根本不会触发。
真实 DDR 控制器只要拉低过一次 WREADY 就会踩到。

### ② `level` 用错位宽做减法 → 静默的数据损坏

```verilog
wire [12:0] level = {5'd0, wp} - {5'd0, rp};   // wp/rp 只有 9 bit
```

FIFO 空了且两个指针都绕过去时会出现 `rp > wp`，在 13 位里做无符号减法
得到的是 −256 的补码 **8176** 而不是 256。后果不是水位显示难看，
而是 `fill_ok` / `can_read` 全部误判成立，于是拿 `mem[rp]` 里的**陈旧数据**
当有效数据写进 PS DDR。修法：`wire [FD:0] level_n = wp - rp;`（天然模 2^(FD+1)）。

### ③ FIFO 满时仍然递增 `wp` → 水位失控

原来是"满了就丢这一拍，但 `wp` 照旧递增"。`level` 越过 DEPTH 之后
`fifo_full` 永远不再成立，指针与水位就此失配（仿真里见过 `level` 跑到 8000+）。
修法：满的时候连指针一起不动。

### ④ `send_cnt` 到齐就撤 WVALID → 少发一拍

AXI 规定 WVALID 拉起后握手成立前不得撤销。原写法在
`send_cnt == burst_len` 时直接跳 S_IDLE 并清 WVALID，
最后一拍若还没被收走就被**静默丢弃**——少 4 个字节，整帧错位。
`WREADY` 恒为 1 时看不出来。修法：只在 `w_slot_free`（即真的握手了）时才收尾。

### ⑤ 像素 FIFO 被综合成块 RAM（最隐蔽：RTL 仿真原理上抓不到）

FIFO 是组合读的 `wire [31:0] fifo_head = mem[rp]`，整个 FWFT 靠它。
单独综合 `sdi_stream_wr` 实测，Vivado 把它推断成了 **RAMB18E1**
（`Block RAM Tile 0.5 / RAMB18 1`，`BRAMCELL RAMB18E1 mem_reg`）。
**RAMB18E1 没有异步读口**，落成块 RAM 后 `fifo_head` 晚一拍，
`can_read` 在 FIFO 明明有数据时判成空，写帧器停摆。

RTL 仿真为什么抓不到：行为级的 `reg [31:0] mem[0:255]` 数组**天然就是组合读的**，
仿真模型不体现综合推断。仿真全绿（148.50 MB/s、AXI PASS、环回绕全过），
硬件坏掉。

改法：显式 `(* ram_style = "distributed" *)` 钉住 —— 分布式 RAM 按构造就有异步读口。
实测代价：`LUT as Distributed RAM` 112 个，全设计 1460/78600 LUT，可以忽略。

`build.tcl` 现在会检查实现后的 `LUT as Distributed RAM`，
32 位宽的 FIFO 至少要 32 个 LUT，掉到 0 直接报 ERROR。

详细推导见 `设计说明.md` §6.12。

### ⑥ 像素打包写反了半边 —— 丢一半视频数据（最严重）

```verilog
mem[wp[FD-1:0]] <= {px_data, acc[31:16]};   // 取高 16 位
acc              <= {16'd0, px_data};       // 存进低 16 位
```

`acc[31:16]` 永远是 0，于是**每两个像素只送出一个**，另一半的 AXI 带宽全是零：

```
beat = 01030000
beat = 01050000
beat = 01070000        <- 相邻两拍是 0103 / 0105，隔一个丢一个
```

而协议检查、`err_stat`、`beats_written`、吞吐 MB/s **四项全绿**——
零也是字节，吞吐统计只数字节，数字照样漂亮。

**判据**来自"像素源是连续 +1 递增"这个事实：

- **字内**：`wdata[31:16] == wdata[15:0] + 1`
  （与丢不丢像素无关，永远成立，能抓字节序写反、读到垃圾、两半重复）
- **字间**：`wdata[15:0] == 上一拍的 wdata[31:16] + 1`
  （抓陈旧、重复、跳过、乱序；只在不丢像素时成立，
  测试台新增 `PX_DUTY` 参数来构造不丢像素的条件）

配套改动：像素计数器改成**只在像素真的送出时递增**，
这样无论 `PX_DUTY` 多少，WDATA 都是连续的 +1 序列，判据才成立。

**校验器本身也验证过会失败**：把字节序对调，它立刻刷屏报错。
一个永远 PASS 的检查比没有检查更危险。

### ⑦ 每复位一次，AXI 上先冒出一个 `32'h00000000`

`q`（FIFO 读口预取寄存器）原来只在 `w_take` 时更新，
而第一个 `w_take` 发生在**已经发掉一拍之后** ——
所以 `q` 还是复位值 0，第一个突发发出去的就是全零。
软件按像素数统计的话，从这里开始整体错位。

修法是加 `q_valid`，允许发数据之前先预取一次：

```verilog
if (w_take || (!q_valid && can_read)) begin
    rp      <= rp + 1'b1;
    q       <= mem[rp[FD-1:0]];
    q_valid <= 1'b1;
end
```

判据用 `can_read`（`level >= 2`），保证要读的位置确实写过 ——
块 RAM 读没写过的地址会给随机内容，行为级数组会给你 0，
两边"看起来"不一样。

> ①②④⑤ 是同一个家族：**仿真用的都是"最理想的那个模型"**。
> ①②④ 是我自己写的从设备模型太宽松（WREADY 恒为 1），
> ⑤ 是 Verilog 的数组语义太宽松（组合读）。
> ⑥⑦ 是第三类：**根本没有检查在看数据内容**。
> 共同点：光靠"RTL 仿真通过"不足以保证这类性质被保住。

## 七、还没测的（必须上板）

仿真的从设备模型是**我按 AXI 规范写的**，不是真的 PS DDR 控制器。
上面这些数回答的是"我们的 master 够不够快、会不会死锁、会不会写错"，
**不能替代板上实测**。

上板后要拿的真数：

| 要测的 | 怎么测 | 为什么重要 |
|---|---|---|
| `S_AXI_HP2` 实际吞吐 | `BEATS` 寄存器增量 ÷ 时间 | 真实 PS DDR 控制器的效率 |
| 真实 BRESP 延迟 | 用 ILA 抓 `AWVALID→BVALID` | 验证 §4B 的流水在真链路上也成立 |
| 真实 WREADY 占空比 | ILA 抓 `WVALID/WREADY` | 验证 §4C 的 50% 门槛 |
| 帧率 / 幅面 | `MEAS_W/MEAS_H/FPS_X100` | 确认源格式 |
| **像素内容对不对** | 软件把一帧读出来看是不是梯度 | **历史节 ⑥ 号 bug 只有这样才看得出来** |
| 排空行为 | 停源之后读 `STATUS.IDLE`，再看 `BEATS` 还涨不涨 | 判空握手是复位流程的前提 |

**判据**（一拍 = 64 bit = 8 字节，一拍装 4 个像素）：

- `BEATS` 每秒增量 ≥ **15.55 M**（= 124.4 MB/s ÷ 8 B/拍 = 1920×1080×30 ÷ 4 像素/拍）
  才算跑满 1080p30。
- `ERR.FIFO_FULL` 不置位 = 没丢数据；置位了说明 WREADY 长期不给。
- 停源后 `STATUS` 必须出现 `IDLE=1 && INFLIGHT=0`，且此刻 `FIFO_LEVEL ≤ 15` 拍
  （一个没发完的突发留在 FIFO 里是**正常**的，见 §4B-3）。

> ⚠️ 最后一行是这次补的。原来四项里没有任何一项能发现"丢一半像素"——
> 因为 `BEATS` 统计的是拍数，零也是一拍。
> **判据应该落在"有效像素数"上，不是"写出去的拍数"上。**
