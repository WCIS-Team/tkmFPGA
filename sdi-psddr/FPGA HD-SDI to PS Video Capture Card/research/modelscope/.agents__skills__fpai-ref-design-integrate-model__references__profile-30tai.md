# 30TAI FPAI Reference-Design Profile

Load this file only when `platform_profile` is `30tai`. Treat 30TAI as
ZG/ZG330/Zhuge, not as a reduced 100TAI configuration.

## Frozen identity and current support

| Axis | 30TAI contract |
| --- | --- |
| Canonical profile | `30tai` |
| Accepted product aliases | 30TAI, ZG, ZG330, Zhuge |
| JSON target evidence | `ai_target` contains `zhuge` or `zg330` |
| CMake selector | `-DTARGET_CHIP=ZG` |
| Compile definition | `USE_ZG330_BACKEND` |
| Device/backend | `ZG330Device` / `zg330::ZG330Backend` |
| Typical device URL | `axi://zg330aiu?npu=0x40000000&dma=0x80000000` |
| Released reference line | Icraft 3.36.1 functional BY/ZG branch |
| Typical multi-PLin topology | Two logical sources; explicit physical ports |

The current repository has ZG source/config/model coverage only where the root
`README.md` and selected example agree. Detect-track and CFT bundles are BY-only
today; a generic `TARGET_CHIP=ZG` option does not create a ZG model or bitstream
contract for them.

For a model-free `examples/0_datapath` target, JSON target evidence is not
applicable. Select this profile from the ZG board identity,
`-DTARGET_CHIP=ZG`, `USE_ZG330_BACKEND` and the ZG device/backend path; do not
create a placeholder JSON merely to satisfy the profile table.

## Graph and runtime contract

- Derive `viewExcept(op_ids)` from the exact ZG JSON and physical ImageMake
  boundary. Never copy another JSON's IDs, including INT8/FP16 variants of the
  same model name.
- Create the per-slot ZG Session through the example's verified
  `initSession("zg330", viewed_network, device, ocm_option, mmu, speedmode,
  compressFtmp)` path. Keep parsed YAML and graph-required capabilities visible
  in initialization diagnostics.
- Treat the current Icraft 3.36 ZG `forward()` completion as insufficient for
  CPU/DetPost consumption: wait for every output Tensor before `device.reset(1)`.
  Change this only with a frozen runtime/model/bitstream A/B correctness test.
- Preserve `waitForReady()` at asynchronous ImageMake and other proven hardware
  operator boundaries. NPU output waits and ImageMake waits are separate
  contracts.
- Use one ordered scheduler for the single blocking NPU core. Do not create
  competing forward threads to emulate parallel compute.

## Physical topology and memory

For the current multi-PLin reference, compile-time `CAMERA_COUNT` is normally
two. `camera.active_ports` selects the actual connected SDI/ImageMake ports in
logical source order and its length must equal `CAMERA_COUNT`; model paths,
buffers and VPU sinks use that same logical order. `SLOT_NUM` is buffer depth,
not camera count.

Use explicit `auto_free` and power-of-two alignment. Camera, display and general
PS-DMA chunks normally use 128-byte alignment; ETM, weight, FTMP or other
page-level allocations remain 4096 bytes when their hardware contract requires
it. Preserve PL-to-PS invalid-frame handling and ImageMake timeout evidence.

## Build and evidence boundary

Configure each selected example in a fresh ZG directory, for example:

```bash
cmake -S . -B build/skill-30tai -DTARGET_CHIP=ZG
cmake --build build/skill-30tai --target <exact-target> --parallel <jobs>
```

Record artifact, cross-build, board initialization, one-frame correctness,
functional, performance and stability evidence independently. A BY build or a
different ZG JSON does not satisfy any of these gates.

## Isolation rules

- Do not select BY/Buyi/QL100 models, backends, Session partition rules or
  four-camera performance targets.
- Do not select WL/Wolong/WL170 libraries, compiler assumptions or board
  prerequisites.
- Do not remove ZG output Tensor waits because a measured BY path omits them.
- Do not promote 30TAI evidence to 100TAI or 400TAI in a combined report.
