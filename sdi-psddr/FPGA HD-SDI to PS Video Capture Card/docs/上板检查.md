# 上板检查与排障

本轮交付到 **RTL + 寄存器 + 驱动 + 位流**，尚未上板验证。本页是上板时该看什么、
怎么判的清单，避免重走之前那几条弯路。

---

## 一、上板前：三个硬件前提

### 1. 跳线（用眼睛查，最便宜也最容易漏）

这块板**只有一个 GT bank（bank112）**，PCIe / SFP / SDI / SMA 四种接口共用，
靠板上跳线片选。手册（悟净完整版 §4.5 / §4.22）原文：

> GT 模块只有 2 路时钟，故采用片选的方式确定进入 GT 时钟的频率……
> **J27 选择 SDI 使用的 148.5M 还是 SMA 的时钟进入 bank112 的 CLK1**
> ……当 **J26 的 GTX_LANE_SEL0~3 连接高电平**时，选择 SDI 的接口

RTL 侧也对得上：`k7_sdi_rxtx.v` 里 `.CPLL_REFCLK_PORT("REFCLK1")`。

**跳线不在 SDI 位，位流再怎么改都是 0 帧。**

### 2. 摄像机输出格式

这台摄像机（wiki `ProgrammableLogic/pldev`）**同时有 1 路 HD-SDI 和 1 路 CVBS 模拟输出**。

2026-10-10 那次"SDI 口 0 帧"的实测结论是 `VERDICT: NO FRAMES`，当时归因为位流/硬件。
**实际上根因在源端**：期间用 OBS 改过摄像机设置，疑似把输出切成了 CVBS，
而 CVBS 那路没接板子。**摄像头上的物理重置按钮不会恢复 OBS 菜单里的设置**，
所以"按重置没用"是预期行为。

上板前如果方便：**OBS 里显式固定 1080p30，不要用 Auto**。Auto 会跟随显示器
EDID 变，把分辨率和帧率一起改掉。

> **做不到这一步也能上板。** 这正是把判据从 PL 挪到软件的原因：
> 不管源端是 CVBS、还是格式不对、还是干脆没信号，硬件都会照写，
> 软件从 `STATUS` / `RX_*` / `MEAS_*` 一眼就能分辨是哪一种。
> `SIG_LOCKED = 0` 但 `BEATS` 在涨 → 问题在源端；`BEATS` 也不涨 → 问题在板子。

### 3. GT 参考时钟引脚变体

| 变体 | 引脚 | 命令 | 说明 |
|---|---|---|---|
| **lite** | `R6` / `R5` | `build.bat`（默认） | **厂商交付包里生效的那一对** |
| full | `U6` / `U5` | `build.bat full` | 完整版标注的那一对 |

这两对是**两个独立的 XDC 文件**（`gt_refclk_lite.xdc` / `gt_refclk_full.xdc`），
构建时选一个。**不要在同一个 XDC 里做字符串替换切换**——
第一版用 `split $t ""` 试过，把 4 KB 的约束放大到 13 MB，
Vivado 以 `EXCEPTION_ACCESS_VIOLATION` 崩掉。

**先用 lite**，只有在"换 full 也全灭"时才需要重新怀疑。

## 二、换位流：只有一条路

板上三条 PL 位流运行时重载通道**已实测全部失效**（详见 wiki
`技术文档/PL位流重载通道失效`），而且**用厂商自己那份已知可用的位流做对照同样失效**。

| 通道 | 结果 |
|---|---|
| U-Boot `fpga loadb` | `Command 'loadb' failed: Error 1` |
| Linux `fpga_manager` sysfs | `Timeout waiting for PCFG_DONE` |
| 出厂 `uEnv.txt` 的 `loadbit` | `fatload mmc 0:2` 根本读不到（分区 2 是 ext4） |

**唯一可用路径：BOOT.bin 替换 + 重启。**

1. `BOOT.bin` 的构成：**FSBL + user.bit + bl31.elf + u-boot**（手册原文）。
2. 替换时**只换 bin，其余文件不动**（手册原文）。
3. 落到 **p1 分区（FAT16）**。注意 `uEnv.txt` 里那条 `loadbit` 写的是
   `fatload mmc 0:2`，分区号是错的。
4. 断电重启。

**这一步要用的文件（2026-10-15 已备好）：**

| 文件 | 位置 | md5 |
|---|---|---|
| 新位流 | `sdi-cap\dist\sdi_cap_lite_20261015_230629.bit` | `01712DB8DE9329ABB4706781A83AFB19` |
| 可直接替换的 BOOT.bin | `S:\work\WCIS\sdi-cap\dist\BOOT_sdi_cap_20261015_230629.bin`（7,023,040 B）| `03AB070C241D17C5BC912EE713CD81E8` |

- **拼法**：`boot-splice.py`，从**板上当前 BOOT.bin 的原样备份**
  （`board_BOOT.bin`，md5 `ACA4612B…`）里只换位流那一段：
  槽位 `0x2D9F0`、位流 `5,979,868` B（`--slot 0x2D9F0 --size 5979868`）。
- **槽位不是猜的**：拿已知能启动的上一次拼接做交叉核对 ——
  `BOOT_status_export.bin`（md5 `0F4F00E1…`）的槽内 ==
  `ai7030_lite_pd1_20261012_211546.bit` 的字节交换版（逐字节 TRUE），
  两次用同一个槽位 / 同一组长度。
- **本机没有**与模板里"当前驻留位流"相等的 `.bit` 文件，所以这次用不了
  `--ref` 自动定位；取而代之的就是上面那条交叉核对，外加"槽外字节逐字节未动"
  的检查。
- **没做什么**：真机验证。换入重启之前，这个文件的确定性只到"拼接正确"；
  "能不能启动"要等重启后看灯（§二点五五）。工具与背景见 wiki
  `技术文档/BOOTbin位流替换手术`。

## 二点五、出位流之后、上板之前：构建验收（2026-10-15 新增）

**这一节是补出来的。** 2026-10-15 那两个位流"构建成功、DRC 0 错、时序全过"，
但都是废的：一个 GP1 接口方向写反（寄存器读写会挂死），
一个六个跨域控制/状态信号悬空（`ENABLE` 传不到像素域，一帧都写不出来）。
同一天又在 CSR 块里挖出三个：读通道 `ARREADY` 死锁、`FPS_X100` 恒 0、
`CTRL` 读回位号错 + `ROW_BYTES` 少一半。
**这五类问题综合不报 error、时序报告更漂亮**（悬空的输入反而"更好收敛"），DRC 也不管。
能看见它们的只有下面四处。

### 0. 仿真：三条链全绿（最便宜的一道，先跑它）

```powershell
cd sim
powershell -ExecutionPolicy Bypass -File run_bench.ps1 -Full   # 行为级两条链
run_gl_bench.bat 200000                                        # 门级（综合后网表，慢，几分钟）
```

| 测试台 | 判据 |
|---|---|
| `tb_sdi_stream_wr`（19 套件） | 每个套件 `data marker frames axi ring drain quiet ovf` 全 PASS，末尾 `ALL PASS` |
| `tb_sdi_cap_regs`（1 条，52 项检查） | `REGS RESULT: PASS`，且 xvlog/xelab 无 WARNING |
| `run_gl_bench`（门级，`sdi_stream_wr` 网表 + UNISIM） | `data/axi/ring/drain/quiet/ovf` 全 PASS，关键数字与行为级 `B_LAT_32` **逐项相同**（`设计说明.md` §6.13）|

**为什么把它放在第一位**：CSR 那三个 bug 就是这条链抓出来的，代价几十秒；
放上板要花一次 `BOOT.bin` + 重启 + 插线，而且症状是"读不动"，
很容易误判成软件或驱动的问题（见 `设计说明.md` §6.23–§6.25）。
像素链的 19 个套件里，`W_LAT_8`（WREADY 压到 12.5%）是唯一会掉数据的场景，
它的 `ovf=PASS` 是"丢字时 `ERR_STAT[0]` 确实置起来了"的判据 —— 这条通路
在 2026-10-15 之前**从来没被验证过**（测试台把它硬接 `1'b0`）。

### 1. 综合日志：`8-xxxx` 警告必须逐条过一遍

| 警告 | 含义 | 判据 |
|---|---|---|
| `8-6104 Input port 'x' has an internal driver` | 端口方向写反（输入口被内部逻辑驱动）| **必须 0 条**，而且要看是哪个模块 |
| `8-2900 ignoring illegal expression in output port connection` | 输出口接了常量/拼接，整条表达式被丢掉 = **网线断了** | **必须 0 条** |
| `8-689 width (32) of port connection ... does not match` | 位宽不匹配（截断，可能歪打正着也可能出事）| 必须 0 条 |

查法（`build_impl_*.log`）：

```powershell
Select-String -Path build_impl_*.log -Pattern '8-6104|8-2900|8-689|internal driver|illegal expression'
```

**判据不止"数量"**：`8-2900` 里报的文件/行号必须**指向厂商文件**（那是预先存在的），
指向 `rtl/` 下的自研文件的，一条都不能留。

### 2. 网表：按网查驱动/负载（`probe6.tcl`）

布线后打开 `impl_1/sdi_cap_top_routed.dcp`，按**网**查（不是按网名猜、不是按端口路径查）：

| 七个跨域信号 | `p_enable` / `p_rearm` / `p_rearm_cam` / `px_overflow` / `wr_idle` / `starving` 都必须**有驱动** |

## 二点五五、换位流之后：先看灯，再看寄存器

（灯的定义见第三节。）
**顺序不能反**：位流一坏，寄存器读出来可能全是 `0xDEADBEEF` 之类的假象，
或者干脆读不动 —— 那时你会去查软件，而问题在 PL 里。
`sdi_cap` 的驱动在 `sdi_cap_open()` 里读一次 `ID`，读不到就报 `bad magic`，
这一条就是"先看灯"的软件版等价物。

---

厂商在 xdc 注释里留了专门给这件事准备的调试指示（`ai7030_edif_top.v` 的
`LED_MON=1`）。本工程把它接到实际的两颗灯上：

| 灯 | 引脚 | 信号 |
|---|---|---|
| `led[0]` | **J1** | 恢复时钟心跳（`rx_usrclk_cnt[25]`，恢复时钟在跑就慢闪）|
| `led[1]` | **M6** | `rx0_locked` —— SDI 传输帧锁定（电平）|

> **映射出处（2026-10-16 更正）**：厂商 `ai7030_edif_top.v:118` 是
> `assign led = {led3, led1}`，其中 `led3 = rx0_locked`、`led1 = rx_usrclk_cnt[25]`；
> 拼接式里 `led3` 在高位 ⇒ **`led[1]`=M6=锁定、`led[0]`=J1=心跳**，
> 与厂商自己那行注释（`led[0]=rx_usrclk…、led[1]=rx0_locked…`）一致；
> 厂商 xdc 也把 `led[0]` 钉在 J1、`led[1]` 钉在 M6。本工程 RTL 同向。
> 此前文档写成"J1=锁定"，是把 `{led3, led1}` 的位序读反了。

| J1（心跳）| M6（锁定）| 含义 | 下一步 |
|---|---|---|
| 灭 | 灭 | GT 没锁、恢复时钟也没活动 —— 参考时钟/输入层面 | 查跳线、查 `BOARD_VARIANT`、查摄像机输出 |
| **闪** | 灭 | GT 有恢复时钟但**传输帧没锁上**（无有效 SMPTE 流/格式不认）—— 常见于源端输出模式被改（例如 CVBS）| **不影响搬运**：先看 `BEATS`/`FRAME_CNT` 有没有在动，再读 `RX_MODE`/`RX_FAMILY` 看它认成了什么；源端期望的种类不是硬件门控条件 |
| 闪 | 亮 | 全链路通 | 往下走到 PS 侧 |

> ⚠️ J1 闪**不能证明链路上真有信号**。它是自由运行计数器的第 25 位，
> GTX 在无有效输入时也可能输出漂移的恢复时钟，计数器照样闪。
> **真正有意义的判据是 M6。**

> 附（2026-10-11 那条现场记录的重新读法）：当时按错的映射记成
> "M6 闪、J1 灭 ⇒ GT 锁了、格式认不出"。按正确映射，同一对读数应读成
> "锁定在抖（M6 闪）、心跳被打断（J1 灭）"——更像 GT 在
> 锁定/失锁/复位循环里（与"源端无有效信号"方向一致），但这一条
> **待下次上板重看**再定论。

**这三个组合正好定位故障层**，先看灯再动软件，能省掉一大段盲查。

## 三点五、要复位/重配置 PL 之前：先排空（厂商文档点名要求）

厂商《PS-PL AXI HP 接口：事务计数与复位语义》里 L1/L3/L4 三种场景
都要求先把接口排空再动 PL，而**PS 侧根本没有在途事务计数**，
判空只能问 PL。本设计为此加了 `WR_IDLE = 0x74` 的 bit0
（`inflight == 0 && 状态机回空闲`，单 bit 两级同步过来）。

顺序不能颠倒：

1. 关 `CTRL.ENABLE`（`sdi_cap_stop()` 已经会自动等排空）
2. 轮询 `0x74` bit0，**连续 3 次为 1** 才认排空
3. 之后才允许复位 AXI_HP / 重配置 PL

厂商 L1 的流程还强调：**断言复位必须排在"重新连通"之前** ——
即 `AXI_HP_RST_CTRL` / `FPGA_RST_CTRL` 要先拉低，再去接
`USER_LEVEL_SHIFT`，否则另一侧可能挂在半通不通的状态上。

> 本设计属于厂商文档里的**"设计2"**（复位取自 PS 的 `FCLK_RESET0_N`，
> 时钟取自管脚/GT），PS 复位会把 PL 连带复位，这一档不需要额外动作。
> 但上面"先排空再动 PL"仍然适用于**只重配置 PL**、或
> **软件主动复位 PL 逻辑**这两种情况。

## 四、PS 侧判读

```sh
# 1) 确认位流在位（软件不做任何事，纯计数）
cat /sys/class/fpga_manager/fpga0/state      # 期望 operating
cat /sys/class/fpga_manager/fpga0/firmware   # 期望 ai7030_top.bit

# 2) 确认程序在位
./demo 10 sdi_frame.pgm
```

`demo` 的输出逐条对照：

| 输出 | 含义 |
|---|---|
| `bad magic` | 位流没加载，或基址对不上（期望 `0x53444943`） |
| `signal : no lock` | M6 是灭的（LED 映射见第三节），回到第三节 |
| `signal : SDI transport LOCKED` + `geometry : 1920x1080 (valid)` | ✅ 硬件侧通了 |
| `frame rate : 29.97 fps -> class ~30` | 帧率识别正确 |
| `frame rate : 0.00 fps` | `MEAS_FPER` 还没出来，等两帧 |
| `errors : 0x1 FIFO_FULL` | 软件读得比 PL 写得慢，丢过 FIFO 里的旧数据 |
| `errors : 0x2 AXI_RESP` | AXI 写响应不是 OKAY，看地址配错没有 |
| `frames` 一直不涨 | `BEATS` 涨但 `frames` 不涨 = 有像素但没有 vsync；两者都不涨 = `ENABLE` 没置位 |

> **没有 `GATE` 这个错误了。** 旧版本会按 `SEL_FPS` 门控帧率、不匹配就丢帧，
> 那正是黑屏的直接原因。现在的设计不做任何门控，`EXP_FPS` 只用于对比，
> 结果看 `FPS_MATCH`。

`demo` 的命令行需要显式给出缓冲区物理地址：

```sh
./demo 10 frame.pgm 0x<udmabuf 的物理地址> 33554432
```

### 内存预算

PS DDR 只有 1 GB，内核启动后 Linux 实际可分配约 **745 MB**，`CmaFree` 更少。

| 配置 | 需要 |
|---|---|
| 单缓冲 1080p | 4.15 MB |
| 8 帧环形 | 33 MB |

**别在 1 GB 的板子上开大环形缓冲。** `RING_BYTES = 0`（单缓冲）是最省的选择：
`FRAME_CNT` 递增告诉软件换帧了，读慢就覆盖。

## 五、帧格式核对

落盘的帧是 **Y'CbCr 4:2:2 8 bit/分量，16 bit/px，小端**：

```
地址 = FRAME_ADDR + y * ROW_BYTES + x * 2

uint16:  [15:8] = Y'      [7:0] = Cb 或 Cr
4:2:2 —— 色度在偶数像素上重复
```

所以：

- **PGM/Y 单通道可以直接存**（取每像素第 0 字节），不需要任何色彩转换，
  `sdi_cap_dump_pgm()` 就是这么做的。
- 要 RGB 得自己做 4:2:2 → 4:2:0 → 4:2:4 或直接按 YCbCr 解释。
- 这是**逐字节等于 SDI 上收到的内容**（`frame_convertor.v` 取 `rx_ds1a`/`rx_ds2a`
  的高 8 位），不是 RGB888。厂商 demo 那条链路给的是 RGB888（24 bit/px，
  带宽是本方案的两倍）。

---

## 六、已知没做的事

| 项 | 原因 |
|---|---|
| 帧率转换（25↔30） | 按约定本轮只做模式选择与上报 |
| 内核驱动（`/dev/video*`） | 板上没有 PL 设备模型；本轮走 `/dev/mem` + udmabuf |
| 真 crossbar | 见设计说明 §5.2 的取舍说明 |
| PL DDR 帧缓冲 | **PL DDR 2 GB 不在 `/proc/iomem` 的 System RAM 里，Linux 用不到**，
  所以帧必须写 PS DDR |
| 上板验证 | 本轮交付到出位流为止 |

## 七、最后提醒：寄存器全对 ≠ 功能对

本轮最严重的一个 bug 是**每两个像素只送出一个**，另一半的 AXI 带宽全是零。
而下面这些**全部显示正常**：

- 寄存器 `ID` / `VERSION` 读出来完全正确
- `STATUS.ENABLE` / `BUSY` / `SIG_LOCKED` 全对
- `BEATS` 在涨，吞吐算出来 148.50 MB/s，正好"够 1080p30"
- `ERR_STAT = 0`
- AXI 协议检查 PASS

**没有一个寄存器能报出这件事。** 零也是一拍，也是一个字节。

所以真正能发现它的只有一件事：**把一帧读出来看内容**。
`§五 帧格式核对` 里的 PGM 导出就是干这个的 —— 别只看它能不能生成文件，
要看里面的像素是不是连续的梯度、有没有隔一个就是零。

同样的道理适用于别的"数字漂亮但内容错"的 bug。
判据要落在**有效数据**上，不要落在**计数器**上。
