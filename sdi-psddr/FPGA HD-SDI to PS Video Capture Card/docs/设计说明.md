> 板子：FMQL30TAI（复旦微 悟净），器件 `xc7z030ffg676-2`，Vivado 2018.3

---

## 零、一句话说清这个块做什么

**SDI 口进来什么像素，就往 PS DDR 写什么像素。**

不做的事（这些是刻意不做的，不是没做完）：

- 不判断格式、不判制式
- 不按帧率门控、不丢帧
- 不等一行收满、不等一帧收满才写
- 不缩放、不转色彩空间、不滤波
- 接收器没锁定也照写

帧和帧之间是连续的，中间没有空洞。格式解释是软件的事。

### 为什么是这个定义

最初的版本做成了"采集卡"：幅面要配 1920×1080、帧率要选 25/30、
不匹配就把帧丢掉、还要等 `sig_locked` 才开火。结果是**源端格式认不出
就什么都不给 PS，黑屏**——而"黑屏"这个现象恰恰是排障时最需要看到数据的情况。

现在的定义：硬件只负责搬运和**如实上报**，黑屏时软件仍然能拿到原始字节流，
并且从寄存器知道到底是"没信号"、"没锁定"、"认不出格式"还是"像素在进但没人读"。

## 一、需求澄清

需求原文（wiki `ProgrammableLogic/pldev`）是**摄像机的输出规格**，不是采集卡的：

| 项 | 要求 |
|---|---|
| 视频分辨率 | 1920×1080 FULL HD 1080P |
| 视频帧率 | PAL: 1080P25；NTSC: 1080P30 |
| 视频接口 | 1 路 HD-SDI 高清数字接口 |
| 视频输出标准 | HD-SDI SMPTE 292M 兼容，默认输出 1080p25/30fps |
| 可调输出格式 | 1080P30、25 |

**那台摄像机同时有 1 路 HD-SDI 和 1 路 CVBS 模拟输出。**
2026-10-10 那次"SDI 口 0 帧"的现场判断是 `VERDICT: NO FRAMES`，
当时归因为位流/硬件。根因在源端：期间用 OBS 改过摄像机设置，疑似切成了 CVBS，
而 CVBS 那路没接板子。**摄像机的物理重置按钮不会恢复 OBS 菜单里的设置。**

> 现在的设计不依赖这一步做对：CVBS 也好、格式不对也好，
> 只要 GT 出得了数据就会写进 PS DDR，软件从寄存器就能看出是哪一种情况。

**PAL/NTSC 不是 HD-SDI 的概念。** PAL（720×576/50Hz）、NTSC（720×486/59.94Hz）
属于 **SD-SDI / SMPTE 259M**；HD-SDI（SMPTE 292M）里对应的是 1080p25/30/50/60。
所以"PAL→1080P25、NTSC→1080P30"在实现上就是帧率识别，而**识别是上报给软件的，
不在 PL 里做门控**。

## 二、硬件前提

| 事实 | 影响 |
|---|---|
| 板上只有一个 GT bank（bank112），PCIe/SFP/SDI/SMA 共用，靠**跳线片选** | 跳线不在 SDI 位就永远 0 帧。用眼睛查 |
| 手册 §4.5：J27 选 SDI 用的 **148.5M** 进 bank112 的 CLK1 | 与 RTL 的 `.CPLL_REFCLK_PORT("REFCLK1")` 一致 |
| SDI 输入均衡器 **LMH0344**（125 Mbps~2.97 Gbps） | 前端不用自己做均衡 |
| GT 参考时钟引脚两对：`R6/R5`（lite，厂商交付包里生效）、`U6/U5`（full） | 选错 = GT 拿不到参考时钟。`build.bat full` 切换 |
| **三条 PL 位流运行时重载通道已实测全部失效** | 换位流只能 **BOOT.bin 替换 + 重启** |
| PS DDR 1 GB；**PL DDR 2 GB 不在 `/proc/iomem` 的 System RAM 里** | 帧必须写进 **PS DDR**。这决定了整个架构 |

```
  (板载)        (板载)        (GT)      (PG071 v3.0)   ┌──────────────┐
                                       ▲             │ Y'CbCr 4:2:2 │
                                  x7gtx_sdi_control  │ 8bit/分量    │
                                  (位率自动检测)     │ 16 bit/px    │
                                                      │ 74.25 MHz    │
                                                      └──────┬───────┘
                                                             │ rx_usrclk 域
                     ┌───────────────────────────────────────┘
                     ▼
              ┌──────────────┐   只测量，不筛选
              │ sdi_cap_meas │   实测幅面 / 帧周期 / 行帧计数
              └──────┬───────┘

              └──────┬───────┘
```

### 3.1 写数据走 `S_AXI_HP2`，寄存器走 `M_AXI_GP1`

```
S_AXI_HP2  ◄── 写帧器      （PL 当主机，AXI4 只写，目标 PS DDR，64 bit）
M_AXI_GP1  ──► 寄存器块    （PS 当主机，AXI4-Lite，读 + 写，基址 0x8000_0000）
M_AXI_GP0      不用
```

**★ 这是 2026-10-15 修掉的一个方向性错误 ★**

原来写帧器挂在 `M_AXI_GP0` 上。可 `M_AXI_GP0` 是 **PS 的出口**（PS 当主机、
PL 当从机），它的 `AWVALID / AWADDR / WDATA` 是这个黑盒的**输出**；
而我们要的是数据从 PL 流向 PS DDR，需要的是**反方向**的口。
综合器不会因此报错，只会把它当成"输入端口在内部还有驱动"：

```
WARNING: [Synth 8-6104] Input port 'wr_awvalid' has an internal driver
                       [.../rtl/sdi_cap_ps.v:221]
```

后果不是"写错地方"，而是**整条写通道从网表里消失**：

- 网表里 `u_wr/m_axi_*` 每一个引脚都不存在 —— 写帧器被优化掉了；
- `net u_ps/wr_awvalid` 上只有一个引脚 `u_ps/u_ps7/M_AXI_GP0_AWVALID`；
- 连 FIFO 都没有了（跟着死路径一起被优化），§6.13 那个
  "FIFO 综合到哪里去了"的悬案就是同一件事，不是两个问题。

PL 要把数据写进 PS DDR，唯一正确的通路是 `S_AXI_HP0..3`。
厂商自己的写帧器 `frame_to_ps_largebuf` 挂的就是 `S_AXI_HP2`
（`fpai_demo_fpga/rtl/ps_ai_peripheral.sv`）；本设计照抄这条通路，
连端口属性（`AWID=0`、`AWCACHE=4'b0011`、`AWQOS=4'b1111`、
发送能力使能拉低）也一并照抄。

**为什么寄存器仍然走 `M_AXI_GP1`**：那本来就是 PS 当主机、PL 当从机的口，
方向和用途都对。两个口各挂**一个**从设备，全是直通线。

**不用同一个口做地址译码**，是因为译码有个先有鸡还是先有蛋的问题：
要决定走哪条路得先看 PS7 驱动的地址，可那个地址正是两个从设备地址的
多路选择结果。第一版写成了

```verilog
assign gp0_awvalid = gp0_awvalid & ~sel_reg_wr;   // 对 output 端口自赋值
```

综合会过，`opt_design` 才报

```
[DRC MDRV-1] Net u_ps/aw_hold_a[7]_i_3_n_0 has multiple drivers:
       u_ps/u_ps7/inst/PS7_i/MAXIGP0AWVALID, and u_ps/aw_hold_a[7]_i_3/O
```

两个口分开就没有这个问题：每个口只有**一个**功能，没有译码、没有多路选择、
没有自赋值、没有反馈环。代价是软件用两个基址，这个代价远小于一个会挂死的
译码器。

### 3.2 为什么 AXI 主机跑 `clk_100m`，不跑像素时钟

| 方案 | 结论 |
|---|---|
| 数据通路跑 50 MHz | **50 MHz × 16 bit = 800 Mbit/s < 1.19 Gbit/s**，光带宽就不够 |
| **AXI 主机跑 `clk_100m`（64 bit 一拍）** | **800 MB/s 上限**，1080p30 只要 124.4 MB/s，**6.4 倍余量** |

代价是像素要跨一次域（65 bit × 1024 的双时钟 FIFO），换来的东西比带宽重要：
**`cam_clk` 不是一根稳定的时钟。**

```verilog
// rx_sdi.v:395
assign cam_clk = rx0_locked ? rx_usrclk : sys_clk_100m;
```

GT 失锁它会**换源、变频**（74.25 MHz ↔ 100 MHz）。AXI 接口上压着在途事务时
换时钟，正是厂商 2026-10-12 客户说明里 L3/L4 那类**挂死**场景：PS 侧等一个
永远不会回来的响应，PL 侧等一个永远不会来的 WREADY。
把 AXI 侧放到常驻的 `clk_100m` 之后，`cam_clk` 再怎么折腾都碰不到 PS 侧接口 ——
最坏情况是 FIFO 里进了垃圾，而垃圾照样写得进去、写得完。

> 第一版把 AXI 主机放在 `cam_clk` 上（理由是"不用跨域"），除了上面这条，
> 还叠加了 §3.1 的方向错误。两件事是独立的，任何一个单独存在都会让
> 写通道不通。

### 3.3 突发与 FIFO

| 项 | 数值 |
|---|---|
| 像素输入 | 74.25 M 像素/s × 16 bit = **148.5 MB/s** |
| AXI 一拍 | **8 byte**（64 bit 主机，一拍 4 个像素） |
| 需要 | 74.25 M / 4 = **18.56 M 拍/s** |
| 带宽上限 | 100 MHz × 8 B = **800 MB/s**（每拍一个 beat 算） |
| 单次突发上限 | HP2 的 `AWLEN` 只有 **4 bit → 最多 16 拍 = 128 字节** |
| 未完成突发上限 | **8**（`inflight` 计数，硬上限） |
| FIFO | 1024 拍 × 65 bit = 8 KB BRAM（约 13.8 µs 缓冲） |
| FIFO 满 | 记 `ERR.FIFO_FULL`，**绝不反压 SDI 接收器**（那会让 GT 失锁），只丢字 |

突发长度 = `min(16, FIFO里有的, 到环尾还剩的拍数)`，三者取最小。
环尾那个突发自动截短，所以不会写出环。

16 拍很短（1080p 一行 3840 字节 = 30 次突发），但吞吐仍然够。**关键是允许
多个突发同时在飞**：AW 通道不等 BRESP，8 个未完成突发把从设备的响应延迟
整个盖住。实测（`docs/AXI速率实测.md`）：

```
BRESP 延迟 1 / 8 / 32 / 64 / 127 拍 —— 吞吐完全不变，都是 150.91 MB/s
（像素源 74.25 MHz 给多少写多少，AXI 侧 6.4 倍余量用不满）
```

**突发长度必须锁存**（`burst_len_q` 在起突发时取一次，之后不再看实时水位）。
否则 FIFO 排空会让 `send_cnt < burst_len` 提前为假，发出去的 W 拍数
少于 `AWLEN+1`，从设备会一直等 W —— **端口挂死**。

### 3.4 帧边界怎么给

PL 不切帧，只在 vsync 上升沿**给当前这一拍打一个标记位**（FIFO 的第 65 位）。
这个标记跟着数据一起穿过异步 FIFO，写帧器发出带标记的那一拍时，
把**那一拍的地址**记进 `FRAME_ADDR`。

```verilog
// sdi_px_pack.v：vsync 来了先挂一个粘滞位，贴在下一个凑齐的 64 bit 拍上
if (frame_start) vs_flag <= 1'b1;
...
w_data <= {vs_flag, acc[63:16], acc[15:0]};   // 标记位 + 4 个像素
```

这样做的好处：`FRAME_ADDR` 与真正写进 DDR 的数据**严格对齐**（±1 拍 = 8 字节），
不需要把 vsync 脉冲单独跨域 —— 单独的跨域脉冲要么有抖动、要么要打帧号，
都会引入"帧标记与实际数据差几个 µs"的裂缝。

软件轮询 `FRAME_ADDR`：值变了就是一帧开始。帧长自己用 `MEAS_W`/`MEAS_H` 算
（`ROW_BYTES = W*2`，`FRAME_BYTES = H*W*2`）。

读帧时**必须处理环形回绕**：行会跨环尾，`sdi_cap_grab()` 已经按行处理了。

> FIFO 满的时候丢的是**整拍**（8 字节，含标记位一起丢）。丢一拍就是丢 4 个像素，
> 顺序不会乱：读指针、写指针都不动，只是那一拍没写进去。

### 3.5 时钟：`cam_clk` 的兜底时钟必须是 100 MHz 不是 200 MHz

`rx_sdi.v` 里 `assign cam_clk = rx0_locked ? rx_usrclk : sys_clk_100m;`
—— GT 没锁定时像素时钟退回 100 MHz（`clk_wiz_0` 的 clk_out1）。
（更早的版本退回的是 200 MHz，那时序关不掉。）

**为什么 200 MHz 关不掉，而且不是优化能救的：**

```
时钟路径 4.239 ns / 周期 5.000 ns
  PS7 FCLK -> BUFG -> PLLE2 -> BUFG -> cam_clk 复用 LUT -> BUFG -> FF
```

光时钟就吃掉 85% 的周期，留给数据的只有 0.76 ns；
而当时的数据路径是 8.607 ns（23 级逻辑，其中 CARRY4=14）。
**即使把数据路径优化到零也关不上。**

两处一起改：

1. **`rx_sdi.v` 的兜底时钟改成 `sys_clk_100m`（clk_wiz_0 的 clk_out1）。**
   `cam_clk` 是纯输出，`rx_sdi` 内部没有任何地方用它，换源完全安全。
   未锁定时本来就没有有效数据，兜底慢一点没有任何影响。
2. **把 32 位环算术从"能不能起突发"的判断路径上拿掉**（改成递减计数器
   `ring_left`），见 §6.9。

**★ 2026-10-15 补：这两根时钟以前根本没有时钟对象 ★**

布线后的时序报告里有一句很容易读漏的话：

```
There are 987 register/latch pins with no clock driven by root clock pin:
    u_rx/SDI0/SDI/GTX_i/gtxe2_i/RXOUTCLK (HIGH)
```

987 个寄存器的时钟根是 GT 恢复出来的 `RXOUTCLK`，但 Vivado 从来没给
`RXOUTCLK`、也没给 `cam_clk` 建过时钟对象 —— 也就是整条像素通路
（厂商的 `frame_convertor` / `YCbCr422_2_RGB888`，加上我们的
`sdi_cap_meas` / `sdi_px_pack` / 异步 FIFO 写侧）**完全不在时序分析范围里**。
之前报的 "WNS +0.847 ns" 只是被分析了的那半张网表的结论。
修法见 §6.18。

### 3.6 字节序

小端，**像素到达顺序 = 内存里的字节顺序**。64 bit 拍 n 里：
像素 `4n+0` 在 `[15:0]`，`4n+1` 在 `[31:16]`，`4n+2` 在 `[47:32]`，
`4n+3` 在 `[63:48]`。

所以环形缓冲**逐字节等于 SDI 口收到的内容**（Y'CbCr 4:2:2 8bit）。

> 这一条以前只是"设计意图"，直到 §6.15 记的那个 bug（`acc` 的高/低半用反，
> 实际发出去的是 `{像素, 16'h0000}`）才第一次被真的检查。
> 现在 `tb_sdi_stream_wr.v` 逐拍核对内容：拍内 4 个像素必须连续
> （`wdata[31:16] == wdata[15:0] + 1`，依此类推），不丢字时跨拍也必须连续
> （`wdata[15:0] == 上一拍 wdata[63:48] + 1`）。
> 内容检查比协议检查更能抓住"握手全对、数据全错"这一类问题 ——
> 读指针错、RAMB 读出垃圾、字节序写反，这三类的表现完全一样。

## 四、帧率：只上报，不门控

`EXP_FPS`（旧名 `SEL_FPS`）这个寄存器**不影响数据通路**，只是让软件可以写下
"我期望 25 或 30"，然后读 `FPS_MATCH` 看实测是否一致。

**测量而不是查表**：HD-SDI 的像素时钟恒为 74.25 MHz，1080p 垂直总行数恒为 1125，
但**总水平样点数随帧率变**：

| 制式 | 总水平样点 | 帧率 | 位率 |
|---|---|---|---|
| 1080p23.98 / 24 | 2750 | 23.98 / 24 | 1.485G |
| **1080p25** | **2640** | **25** | **1.485G** |
| **1080p29.97 / 30** | **2200** | **29.97 / 30** | **1.485G/1.001** |
| 1080p50 | 2640 | 50 | 2.97G (3G-A) |
| 1080p59.94 / 60 | 2200 | 59.94 / 60 | 2.97G (3G-A) |

（来源：AMD PG290 Table A-1。）

所以 `fps = 74.25e6 / 实测帧周期`，帧周期由 `sdi_cap_meas` 数出来，
硬件里用 64 拍**迭代除法器**算 `FPS_X100`（组合除法器要 ~4k LUT 且是多周期路径）。
分类用 ±3% 容差，29.97 也归到 30。

**接收器没锁定时 `MEAS_FPER` 不更新**（周期没意义），但行/帧计数照走——
"计数在动但周期不动"本身就是"GT 活着但认不出格式"的判据。

### 5.1 为什么不用 Block Design

这块板的 PS7 配置不是标准件——从厂商的 `ps_ai_processing_system7_0_0.xci`
原样搬来的，已经在 `xc7z030ffg676-2` 上验证过能综合能布局。
在 Tcl 里重新推导那约 200 条 PCW 属性是这个项目最大的风险来源，而收益为零。

采集通路对 PS 的需求只有两条，写出来比脚本化 BD 好读也好改。

### 5.2 为什么用 4:2:2 而不是 RGB888

厂商 demo 链路给的 `cam_rgb[23:0]` 是 RGB888，24 bit/px = 6 MB/帧，
1080p30 下 180 MB/s。`frame_convertor.v` 本身就同时产出 8 bit 的 Y' 和 CbCr，
4:2:2 = 16 bit/px = 4 MB/帧，1080p30 下 124 MB/s，省一半带宽且不占一个 LUT。

为此对 `rtl/vendor/sdi/rx_sdi.v` 做了**纯增量**改动：新增 4 个输出端口
`y422_data[15:0] / y422_vs / y422_hs / y422_de`。厂商的 RGB888 通路**一根线没改**。

## 六、踩坑记录

### 6.1 `split $t ""` 把约束文件放大到 13 MB

最早 `build.tcl` 用 Tcl 字符串替换在**同一个 XDC 里**切 GT 参考时钟引脚变体：

```tcl
proc lrep {t n r} { return [join [split $t $n] $r] }
```

`split $t ""`（空分隔符）把字符串拆成**每个字符**，`join` 再用 needle 拼回去，
文件长度 × needle 长度。**跑两次就是 63² ≈ 4000 倍**：4 KB → 13 MB，
然后 Vivado 以 `EXCEPTION_ACCESS_VIOLATION` 崩掉。

还有隐蔽陷阱：XDC 里那两行是**注释掉的**（`##set_property PACKAGE_PIN U6 ...`），
但注释行**包含**未注释的 needle 字符串，所以替换会"命中"，每次跑都再插一行。

**改法**：不做原地编辑。改成 `gt_refclk_lite.xdc` / `gt_refclk_full.xdc`
两个完整片段，构建时选一个。

### 6.2 processing_system7 IP 的端口名和 BD wrapper 的不一样

照着 BD wrapper 的名字写会全部报 `named port connection ... does not exist`。

| BD wrapper 用的 | IP 真实的 |
|---|---|
| `FIXED_IO_mio` | **`MIO`** |
| `FIXED_IO_ps_clk` / `_srstb` | **`PS_CLK`** / **`PS_SRSTB`** |
| `FIXED_IO_ps_porb` | **不存在**（PORB 在 IP 内部） |
| `DDR_ba` | **`DDR_BankAddr`** |
| `DDR_ck_p` / `_n` | **`DDR_Clk`** / **`DDR_Clk_n`** |
| `DDR_dqs_p` / `_n` | **`DDR_DQS`** / **`DDR_DQS_n`** |
| `DDR_odt` / `DDR_ras_n` | **`DDR_ODT`** / **`DDR_RAS_n`** |
| `DDR_reset_n` / `DDR_we_n` | **`DDR_DRSTB`** / **`DDR_WEB`** |
| `FIXED_IO_ddr_vrn` / `_vrp` | **`DDR_VRN`** / **`DDR_VRP`** |
| `pll_lock` / `ps_clk_out` | **不存在** |

两个容易搞反方向的：

- **`IRQ_F2P` 是 PS7 的输入**（fabric → processor），3 bit（`NUM_F2P_INTR_INPUTS = 3`）
- **`FCLK_RESET0_N` 是 PS7 的输出**（processor → fabric），低有效

端口名不要猜，从 IP 生成的 HDL 里读：module 声明到第一个顶格 `);` 之间。

### 6.3 GP0 的 AXI 字段宽度比想象窄

`M_AXI_GP0_ARLEN` / `AWLEN` 是 **4 bit**（最多 16 beat），不是 8 bit。
`M_AXI_GP0_WSTRB` 在 GP0 上是 **4 bit**（32 bit 数据总线），
8 bit 是 64 bit 总线宽度。

### 6.4 突发长度必须按 AWLEN 的实际上限取

1080p 一行是 `1920*2 = 3840 byte = 960 拍`（32 bit 拍），
GP0 的 AWLEN 只有 4 bit ⇒ **单次突发最多 16 拍 = 64 字节**，
一行要分 60 次突发。

AWLEN 截断**不会报错**，只会静默少写：按 256 设计时，
AWLEN 截成 0xFF 只写了 224 拍，产出的帧每隔一行缺 32 拍。

突发长度必须取 `min(16, 环尾余量)`，而且要在 `S_IDLE` 锁存——
理由见 §6.8 与 `AXI速率实测.md` §6④。
### 6.5 `dru.edf` 不加进工程，opt_design 直接停

```
[DRC INBB-3] Black Box Instances: Cell 'u_rx/SDI0/SDI/GTX_CTRL/NIDRU'
      of type 'dru' has undefined contents and is considered a black box
```

`smpte_sdi` 核在 SD 速率（270 Mb/s）去 stutter 时会例化一个 Data Recovery Unit，
它的实现是加密的 EDIF 网表，旁边那个 `dru.v` 只是端口桩。
`build.tcl` 现在会检查并在缺失时直接 ABORT。

### 6.6 综合报错时先看 `runme.log` 的时间戳

`synth_1` 失败后 `runme.log` 会留在那里。改了 RTL 重跑之前先确认它比你的改动新，
否则会对着上一轮的报错改代码。

### 6.7 GP0 是 32 bit 主机，64 bit 拍会被悄悄截断

Zynq 的 `GP0`/`GP1` 都只有 **32 bit** 数据宽，`AWSIZE` 最大 2（4 byte）。
按 AXI 规范想当然地以为 `AWLEN` 是 8 bit（256 拍）、`WDATA` 是 64 bit，
Vivado **不会报错**，只会把 64 bit 的 `WDATA` 截成低 32 bit ——
**每拍的高 32 位像素凭空消失**，写出去的是隔一个丢一个的帧。

字段宽度要从 IP 生成的 HDL 里读（`M_AXI_GP0_WDATA` 是 `[31:0]`，
`M_AXI_GP0_AWLEN` 是 `[3:0]`），不要凭 AXI 规范推断 —— 
规范描述的是 64 bit 主机的宽度。

同理 `WSTRB` 是 `[3:0]` 不是 `[7:0]`。

### 6.8 突发长度不锁存会把 AXI 端口挂死

`burst_len` 如果在 `W` 阶段继续跟着 FIFO 水位变，FIFO 排空会让
`send_cnt < burst_len` 提前为假，于是发出去的 W 拍数少于 `AWLEN+1`。
slave 会一直等剩下那几拍 W，**GP0 端口从此挂死**，软件看到的现象是
`WR_ADDR` 不再前进但也没有报错。

正确做法：在 `S_IDLE` 决定发起突发时把长度锁存进 `burst_len_q`，
`AWLEN` 和 `WLAST` 判断全部用它。

### 6.9 32 位环算术串在起突发的判断上 → 200 MHz 关不掉

```verilog
offset     = wr_addr_lo - base_lo;        // 32 bit 减
at_end     = offset >= cfg_ring_bytes;     // 32 bit 比
left_b     = cfg_ring_bytes - eff_off;     // 32 bit 减
left_beats = (left_b + 3) >> 2;
burst_want = ...;  fill_ok = ...;  start_ok = ...;
```

两条 32 位 carry chain（16 个 CARRY4）串在"能不能起突发"的判断路径上。
时序报告里那条最差路径正是它：

```
Slack (VIOLATED) : -3.931ns   (clk_out2_clk_wiz_0, 200 MHz)
  Source:      u_wr/wr_addr_lo_reg[1]/C
  Destination: u_wr/send_cnt_reg[11]/CE
  Data Path Delay: 8.607ns   Logic Levels: 23  (CARRY4=14 ... )
```

**改法**：换成递减计数器 `ring_left`（到环尾还剩多少字节），
突发发完时扣减，归零时下一发回环首。判断路径上就只剩寄存器输出的小运算。

配套的两个坑（都是仿真里查出来的）：

- `ring_left` 写成两个 always 块（一个重装、一个扣减）→ 多驱动。
  Vivado 报 `MDRV-1`，仿真里表现为回绕后一直往环外写。
- `ring_left == 0` 时如果算成"剩 0 拍所以发不了"，`start_ok` 恒为假，
  **永远起不了突发，也就永远回不到环首** —— 直接死锁。
- 回绕时若无条件用 `MAX_BURST`，而环比一个满突发（64 byte）还小，
  就会写出环外。`RING=16` 的用例直接越界 4 个字节。
  所以要 `ring_cap = min(16, cfg_ring_bytes/4)`。

### 6.10 `ps/` 的 C 代码没有编译检查过 —— 现在补上，抓到三处

这台开发机没有 `arm-linux-gnueabihf-gcc`，但有 WSL2 Ubuntu（gcc 15.2.0）。
**目标码不同，但语法/类型/接口检查一样有效** —— 抓的是拼错、漏 include、
字段名写错、类型不匹配，这些跟最终跑在 ARM 还是 x86 上无关。
真正跟平台有关的（DMA 一致性、cache 对齐、原子性）仍然只能上板验。

`ps/check_compile.sh` 用 `-Wall -Wextra -Wpedantic -Wshadow -Wconversion` 编。
第一次跑就出三条，全是真问题：

**(a) 缓冲区边界检查会因 32 位回绕而失效**

```c
if (pa < SDI_CAP_DRAM_BASE || pa + len > SDI_CAP_DRAM_BASE + SDI_CAP_DRAM_SIZE)
```

ARM 上 `unsigned long` 是 32 位，`pa + len` **会回绕**：

```
pa = 0xFFFFFF00, len = 0x200  ->  pa + len = 0x100
0x100 <= 0x40000000  ->  通过检查
```

一个明显在 PL 地址空间、根本不是 DDR 的地址，就这么被当成合法的
DDR 起始地址放行，用户拿到一个指向别处的指针。
改法：先判 `pa + len < pa`（无符号回绕），再判上界。

（gcc 同时报 `pa < SDI_CAP_DRAM_BASE` 恒为假 —— 那是对的，
Zynq-7000 的 PS DDR 物理地址从 0 开始。把这个死代码删掉，
留一条 `_Static_assert` 盯着，base 一旦不是 0 就编译失败。
写成对称的样子只会让人误以为这里有检查。）

**(b) `mmap` 的 offset 没做页对齐检查**

udmabuf 给的偏移通常是对齐的，但一旦不对齐，内核返回 `EINVAL`，
`perror("mmap ring")` 只会打一句 "Invalid argument"，看不出是哪里的问题。
自己先查清楚，并且报出实际页大小。

顺带一提：`PAGE_SIZE` 宏在 glibc 里只在 `__USE_MISC` 下从 `<limits.h>` 暴露，
换个 `-std` 或换个 libc 就没了；而且某些配置下页不是 4 KiB，写死 4096 是错的。
所以用 `sysconf(_SC_PAGESIZE)` 问内核。

**(c) offset 从 `uint64_t` 隐式转 `off_t`（有符号）**

`-Wsign-conversion` 报的。当前板上物理地址 < 2^48，实际不会出问题，
但补一句范围检查更省事 —— 万一以后接了 > 2^63 的地址，
`mmap` 会把它当成负偏移。

### 6.11 时钟分组约束：XDC 不是 Tcl，四种写法各错一次

`cam_clk` 是时钟多路选择器（`rx0_locked ? rx_usrclk : sys_clk_100m`），
Vivado 把它拆成两根独立时钟，去算"rx 分支起沿 -> 100 MHz 分支收沿"这种
运行期不可能发生的组合，报出 447 个假违例（最差 **-7.454 ns**）。
要声明三组异步（GT 侧 / PS 侧 / 板载晶振侧）。

| 写法 | 结果 |
|---|---|
| `constrs_1` + 裸 `set_clock_groups`（**最终正确**） | 生效 |
| `constrs_1` + `foreach`/`if` 包裹 | **空操作**。XDC 解析器拒绝 `foreach`，列表是空的，`set_clock_groups` 收到 0 个组 |
| `constrs_2` | **完全没进 run**。`add_files -fileset constrs_2` 只把文件加进*工程*，`launch_runs` 不拷进 run —— 实测该文件在 `sdi_cap.runs/` 下没有任何痕迹 |
| `open_run synth_1` + `read_xdc` | 时序确实好看，但 `impl_1` 子进程读不到 `constrs_1`，DRC 的 `set_property SEVERITY` 没执行，`place_design` 报 2 个 Error |

**★ XDC 不是 Tcl ★

XDC 只认少数几个命令。写 `foreach` / `if` / `puts` 进去，Vivado 报

```
CRITICAL WARNING: [Designutils 20-1307] Command 'foreach' is not supported in the xdc constraint file.
CRITICAL WARNING: [Vivado 12-2242] set_clock_groups: No group specified.
```

**然后继续往下执行。**

最讽刺的一处：我为了"防止约束静默失效"加的"检查每组匹配数并打印"逻辑，
本身就写在 `foreach`/`if`/`puts` 里 —— 于是它既没执行、也没报错，
连"它失败了"都没留下痕迹。排查时在所有日志里 grep `CLOCKGROUPS` 一个字都搜不到，
反而成了误导。**防御性诊断本身要是坏的，等于没有防御。**

所以最终写成一条不带任何控制流的裸命令：

```tcl
set_clock_groups -asynchronous \
  -group [get_clocks -quiet {*RXOUTCLK* *TXOUTCLK* *mgtclk*}] \
  -group [get_clocks -quiet {clk_fpga_0 *clk_wiz_0}] \
  -group [get_clocks -quiet {sys_clk_p *sys_clk}]
```

要么整条生效，要么整条报错。要确认各组匹配了几个时钟，
去报告的 Clock Summary 里数，不要指望 XDC 会打印。

### 6.11b 设计约束和 DRC 设置走两条不同的路

`open_run` + `read_xdc` 那次为什么"时序好了但位流出不来"：

- **设计约束**（引脚、时钟、时钟分组）随 DCP 传递，也随已链接的设计进入子进程
- **DRC 检查的 SEVERITY 是会话状态**，不随 DCP 传递；子进程从已链接的设计起步，
  不重读 `constrs_1`，于是 `set_property SEVERITY` 没被执行

结果是一边好一边坏：时序对，`place_design` 照样被 REQP-52/56 挡住。
混着改这两类东西时，要分别验证，不能只看其中一个变好了就收工。

顺带三个 Tcl 细节，同一轮里连续踩到的：

- `create_fileset` 的选项是 **`-constrset`**，`-constrs_2` 是 fileset 的**名字**不是选项
- `get_filesets` 找不到目标时**只发 WARNING、不抛异常**，`catch {}` 判不出来；
  要用 `llength [get_filesets -quiet ...] == 0`
- 非 project 模式下只建 `constrs_1`，`constrs_2` 必须先 `create_fileset`

还有一条编码教训：**Vivado 的 Tcl 读系统 ANSI 码页**。`build.tcl` 里
`# 注意是 -constrset` 这种**行内**注释，如果带中文，UTF-8 字节被按 GBK 解读后
`#` 没被识别成注释，后面的文本被当成选项参数：

```
ERROR: [Common 17-170] Unknown option '-constrset，不?',
```

整行注释（`#` 在第 0 列）安全，只有**行内**非 ASCII 会出事。
`build.tcl` 现在是纯 ASCII，中文说明留在 `.md` 里。

### 6.12 像素 FIFO 被综合成块 RAM —— 这类 bug RTL 仿真原理上发现不了

**本项目最深的一个 bug，也是最该记住的一条。**

`sdi_stream_wr` 的 FIFO 是组合读的：

```verilog
wire [31:0] fifo_head = mem[rp[FD-1:0]];
```

整个 FWFT（first-word-fall-through）就靠它：读指针指到哪一拍，
下一拍直接发出去，中间没有寄存器。

单独综合本模块，实测：

```
| Block RAM Tile    |  0.5 |     0 |       265 |  0.19 |
|   RAMB18E1        |    1 |
BRAMCELL RAMB18E1 mem_reg
```

**Vivado 把这个 256x32 推断成了 RAMB18E1。而 RAMB18E1 没有异步读口，
只有同步读。** 一旦落成块 RAM，`fifo_head` 就晚一拍，`can_read` 会在
FIFO 明明有数据时判成空，写帧器直接停摆。

### 为什么仿真抓不到

行为级的 `reg [31:0] mem [0:255]` 数组**天然就是组合读的**。
仿真模型不体现综合推断，所以：

- RTL 仿真：148.50 MB/s，AXI 协议检查 PASS，环回绕各档全过 —— 全绿
- 硬件：FIFO 落在块 RAM里，同步读，FWFT 失效

这不是测试写得不够好，是**工具的推断行为离开了语言语义**，
而仿真用的正是语言语义。

### 本项目一共三类"模型比 RTL 更理想"的坑

| 坑 | 模型替 master 做了什么 | 真硬件上会发生什么 |
|---|---|---|
| WLAST 无条件清（§6 ①） | 从设备的 WREADY 恒为 1，最后一拍同拍收走 | 从设备永远看不到突发结束 → 永不回 BRESP → 死锁 |
| `send_cnt` 到齐就撤 WVALID（§6 ④） | 同上 | 最后一拍被静默丢弃，整帧错位 |
| FIFO 落成块 RAM（本条） | 行为级数组是组合读的 | 同步读，FWFT 失效，写帧器停摆 |

**共同点：仿真用的都是"最理想的那个模型"。**
前两个是我自己的从设备模型太宽松，第三个是 Verilog 的数组语义太宽松。

### 怎么防

1. **凡是靠"数组组合读"拿到的东西，都显式 `(* ram_style = "distributed" *)`。**
   分布式 RAM 按构造就有异步读口，不给 Vivado 猜的机会。
   代价：256x32 ≈ 32 个 LUT（实测 112），全设计才用了 1460/78600。
2. **加构建断言。** `build.tcl` 现在会在实现后检查
   `utilization_placed.rpt` 里的 `LUT as Distributed RAM`：
   32 位宽的 FIFO 在 LUTRAM 里至少要 32 个 LUT，掉到 0 就报 ERROR。
   光靠"仿真通过"不足以保证这类性质被保住。
3. **综合后网表仿真（gate-level sim）能抓到；当时没走通，后来在 §6.13 里调通了** ——
   `write_verilog -mode funcsim` 出来的网表需要编译 `unisim_comp.v`，
   加 `-L unisims` 不够（xelab 的库搜索路径问题），最后跑出来全是 `z`（原因见 §6.13 坑一）。
   两条路都保留：RTL 里把意图写死 + 加断言是**日常**手段（快，每轮构建都跑）；
   门级仿真（`sim/run_gl_bench.bat`）是**定案**手段（慢，只在关键节点跑）。

### 6.13 【已收口】FIFO 在全设计里的落点 —— 用综合后网表仿真定案

这一节原来是全设计唯一的未解决疑点（"FIFO 到底有没有真的落成块存储"）。
现在已经用**综合后网表 + 真实 UNISIM 原语模型**跑通并定案，
2026-10-15 又对 64 bit 链路整体重跑了一遍（本轮结果在末尾），结论不变。

#### 结论（分两代，64 bit 版是现行结论）

**32 bit 时代（2026-10-14）**：单独综合 `sdi_stream_wr`（当时 FIFO 还在写帧器里面）：

```
Slice LUTs        321
Slice Registers   274
Block RAM Tile     0.5   ->  RAMB18 = 1（RAMB18E1 only）
```

FIFO 确实落在 `RAMB18E1` 上，且是**寄存读口**（`q <= mem[rp]` 显式写死），
与推断方式无关。修复 §6.15 的两个 bug 之后重新综合，这个结论不变。

**64 bit 时代（2026-10-15，现行设计）**：像素 FIFO 拆成了独立模块
`sdi_px_afifo`（65 bit × 1024，双时钟），读口仍然是显式寄存器
（`rd_data <= mem[rbin]`），落块 RAM / LUTRAM / 触发器行为都一样 ——
**推断问题从"怎么保证落对"变成"不用保证"**。写帧器本身不再含任何存储：
门级综合它的资源是 **311 LUT / 302 FF / 0 RAMB**（即 §6.12 "怎么防"第 3 条
担心的推断麻烦，在现行设计里已被结构消掉）。

全设计的块存储落点（`sdi_cap_top_utilization_placed.rpt`，hp2d 位流）：

```
RAMB36/FIFO*              2      （RAMB36E1 only）
RAMB18                    1      （RAMB18E1 only，厂商链的）
LUT as Distributed RAM    0
```

65 bit × 1024 = 66560 bit，单块 RAMB18E1（18 Kb）装不下；
按实例名查布线后网表（只读探针，`get_cells -hier -filter {REF_NAME =~ RAMB*}`）：

```
RAMB36E1  u_px_fifo/mem_reg_0                  <- 像素 FIFO，就是这两块
RAMB36E1  u_px_fifo/mem_reg_1
RAMB18E1  u_rx/SDI0/VIDGEN/VERT/vrom_out_reg   <- 厂商 VIDGEN 的竖向 ROM
```

**FIFO 的落点就此定案：块 RAM，2 块 RAMB36E1，实例 `u_px_fifo`。**
`build.tcl` 里那条"LUT as Distributed RAM >= 32"的老断言已按此改成**只报告不判决**。

#### 门级仿真怎么跑通（工具链上踩了六个坑，都值得记下来）

**坑一：`unisim_comp.v` 是空壳，不是行为模型。**

第一次失败的表现是"综合后网表所有输出都是 `z`"。真因不是网表坏，是这个文件：

```
S:\apps\Xilinx\Vivado\2018.3\data\verilog\src\unisim_comp.v

//  Module Count : 1089
///// component AND2 ////

```

它是 **retarget 用的空盒子库**。`OBUF`/`IBUF`/`BUFG` 能通过 `xelab`，
因为模块确实存在，但里面什么都不做，输出自然是 `z`。
真正的行为模型在同级的 `unisims\` 目录里（`unisims\OBUF.v` 之类，245 个 `.v`）。

**坑二：`xvlog` 不接受目录参数，也不认 `--quiet`。**

`xvlog <dir>` 报 `File ... cannot be opened for read`；
`xvlog --quiet` 报 `unrecognised option`。只能自己把文件列表分块传进去。

**坑三：编译产物在 `xsim.dir\work`，`rmdir xsim.dir` 会把原语库一起删掉。**

unisims 分块编译完之后，另起一次 `xvlog` 去编 glbl/网表/测试台之前，
如果中间做过 `rmdir /s /q xsim.dir`，之前编好的 LUT6/FDRE/... 全没了，

**坑四：`FDRE.v` 引用了 `glbl`。**

必须把 `data\verilog\src\glbl.v` 一起编进去，并且 `xelab mini glbl`

**坑五（2026-10-15 重跑时遇到）：PowerShell 的 `$Args` 是自动变量，参数被静默吃掉。**

`run_gl_bench.ps1` 里内部函数的参数原来叫 `$Args` —— 那是 PowerShell 的

**坑六（同上）：测试台的两种"理想假设"在门级不成立。**

a) 测试台原来靠**精确字符串替换**把 DUT 实例上的 `#(MAX_OUT(...))` 参数覆盖

b) 测试台有三处窥探 DUT 内部信号（`dut.w_beat_i` / `dut.px_rd_data[64]` /
`dut.beat_addr`）—— 网表里它们要么被优化掉（`w_beat_i` 根本不存在），
要么位宽只剩 `[31:2]`（`beat_addr`）。现行的做法：三处全部换成常量，

19 套件覆盖），其余全部端口级检查原样保留。

### 6.15 像素打包写反了半边 —— 丢一半视频数据，且协议层面完全看不出来

**这是本项目至今最严重的一个 bug**，直到给 `WDATA` 加了内容校验才暴露。

#### 症状

综合、仿真、协议检查全绿，吞吐 148.50 MB/s 看着正好够 1080p30。
但 `WDATA` 实际长这样：

```
beat = 00000000   ← 每复位一次，AXI 上总会先冒出一个全零
beat = 01030000
beat = 01050000
beat = 01070000
```

低 16 位恒为 0，而且相邻两拍携带的是 **0103、0105、0107** —— 隔一个丢一个。

#### 成因

```verilog
mem[wp[FD-1:0]] <= {px_data, acc[31:16]};   // 取 acc 的高 16 位
acc              <= {16'd0, px_data};       // 却把像素存进了低 16 位
```

`acc[31:16]` 因此永远是 0：**每两个像素只送出一个**，
另一个连同 16 位零一起被丢掉，一半的 AXI 带宽全是零。

按真实的像素率算，修复前只有 148.5 MB/s ÷ 2 = 74.25 MB/s = **37.1 M 像素/s**，
而 1080p30 需要 62.2 M 像素/s —— **只有 60%**，实际是跑不满帧的。

#### 为什么所有已有检查都没抓到

| 检查 | 为什么漏 |
|---|---|
| AXI 协议检查 | 握手、突发长度、WLAST 稳定性全对，只是**数据内容**错 |
| `err_stat` | 0。FIFO 没满，BRESP 全是 OKAY |
| `beats_written` | 正常递增，而且它统计的是"拍了多少拍"，不是"多少有效像素" |
| 吞吐 MB/s | 统计的是**写出去的字节数**，零也是字节，所以数字照样漂亮 |
| 环回绕检查 | 只查地址越界，不查数据 |

**这是 §6.12 那一类坑的加强版**：那次是"推断相关的性质 RTL 仿真抓不到"，
这次是"数据正确性根本没有任何检查在看"。

#### 怎么防

给测试台加了 **WDATA 内容校验**，判据来自像素源是连续 +1 递增这个事实：

- **字内**：每个 32 位拍装两个连续像素，必须 `wdata[31:16] == wdata[15:0] + 1`
  —— 与是否丢像素无关，任何配置下都成立，能抓字节序写反、读到垃圾、
  两半重复
- **字间**：`wdata[15:0] == 上一拍的 wdata[31:16] + 1`
  —— 抓陈旧数据、重复、跳过、乱序。**只在不丢像素时成立**
  （测试台新增 `PX_DUTY` 参数，满速下 DUT 会在 FIFO 满时丢像素，
  序列本来就会跳，硬用就是假警报）

配套改动：像素计数器改成**只在像素真的送出时递增**，这样无论 `PX_DUTY`
多少，WDATA 都是连续的 +1 序列，判据才成立。

**校验器本身也必须验证过会失败**，否则就是又一个"永远 PASS"的检查。
反向测试：把 `mem[wp] <= {px_data, acc[31:16]}` 改成 `{acc[31:16], px_data}`
（字节序对调），校验器立刻刷屏报错。

### 6.16 每复位一次，AXI 上先冒出一个 `32'h00000000`

`q`（FIFO 读口的预取寄存器）原来**只在 `w_take` 时才更新**，
而第一个 `w_take` 发生在**已经发掉一拍之后**。
于是每复位 / rearm 一次，`q` 还是复位值 0，第一个突发发出去的就是全零。
软件如果按像素数统计，从这里开始整体错位。

修法是加 `q_valid` 位，允许在真正发数据之前先预取一次：

```verilog
if (w_take || (!q_valid && can_read)) begin
    rp      <= rp + 1'b1;
    q       <= mem[rp[FD-1:0]];
    q_valid <= 1'b1;
end
```

判据用 `can_read`（`level >= 2`），保证要读的那个位置确实写过 ——
这正是块 RAM 与寄存器组的区别，块 RAM 读一个没写过的地址会得到随机内容，
行为级数组则会拿到 0，两边"看起来"不一样。

### 6.17 测试台的 WREADY 占空比曾经失效（`gcyc` 只声明不自增）

`tb_sdi_stream_wr.v` 里：

```verilog
integer gcyc = 0;                                   // 声明了
assign wready = rst_n && wvalid &&
                ((W_LAT == 1) ? 1'b1 : ((gcyc % W_LAT) == 0));
                                                   // 引用了
// 但全文件没有任何 gcyc <= gcyc + 1;
```

`gcyc` 永远是 0，`(0 % W_LAT) == 0` 恒真 —— **W_LAT 从来没生效过，

**任何新扫的数据都不可信**。现在这一列多了一列"数据校验"，

### 6.18 写通道挂错了口：`M_AXI_GP0` 是 PS 的出口 —— 整条通路从网表里消失

**发现过程**（2026-10-15，从"下一个位流有没有用"这个问题一路挖出来的）：

1. 综合日志里有一条容易被刷过去的警告：

   ```
   WARNING: [Synth 8-6104] Input port 'wr_awvalid' has an internal driver
                          [S:/apps/llm/agentwork/sdi-cap/rtl/sdi_cap_ps.v:221]
   ```

   "一个输入端口在内部还有驱动" —— 综合器在说：这个网既被外面驱动、
   又被里面的 IP 驱动。它没有报错，只是把**其中一个**留下。

2. 用 Tcl 探针把综合后的网表翻出来（只读，不改）：

   - `u_wr`（写帧器）的 `m_axi_*` 引脚，**一个都不在网表里**；
   - `net u_ps/wr_awvalid` 上只有一个引脚：`u_ps/u_ps7/M_AXI_GP0_AWVALID`；
   - 全设计搜 `RAMB*` / `mem_reg` / `dist_mem` —— **一个都没有**。

3. 结论：写帧器被优化掉了，FIFO 跟着一起被优化掉了（它的读口没人要）。
   §6.12/§6.13 里"FIFO 落点"的种种猜测全部作废：**它当时压根不存在**。

**根因**：`M_AXI_GP0` 是 PS7 的 **AXI 主机口**（PS 当主机，PL 只能当从机），
它的 `AWVALID/AWADDR/WDATA` 是 PS7 黑盒的**输出**。而写帧器是 PL 的主机、
要往 PS DDR 写 —— 方向完全相反。PL 侧主机被打在 PS 侧主机上，
`AWVALID` 两头都是驱动源，于是 Vivado 判定"内部驱动优先"，把 PL 那半边剪了。

**怎么改的**：写帧器改挂 `S_AXI_HP2`（PL 当主机、PS 当从机，64 bit），
寄存器块继续用 `M_AXI_GP1`。端口属性照抄厂商 `aq_axi_master.v`：
`AWID=0`、`AWLOCK=0`、`AWCACHE=4'b0011`、`AWPROT=3'b000`、`AWQOS=4'b1111`、
`AWBURST=2'b01`；`S_AXI_HP*_RDISSUECAP1_EN`/`WRISSUECAP1_EN` 拉低
（厂商 `ps_ai_peripheral.sv` 就是这么接的）；读通道不接但明确拉死，不悬空。

**验收方法**（这次不靠"看起来对了"）：重新综合后
① `8-6104` 那条警告必须消失；② `u_wr/m_axi_*` 引脚必须出现在网表里；
③ 全设计网表里必须能找到 BRAM（FIFO 真的落下来了）。
三条都在，才算通。

### 6.19 恢复时钟域从来没有时钟对象 —— 987 个寄存器不在时序分析里

**症状**：布线后的时序报告头部（不是摘要表，是前面那段说明文字）写着：

```
There are 987 register/latch pins with no clock driven by root clock pin:
    u_rx/SDI0/SDI/GTX_i/gtxe2_i/RXOUTCLK (HIGH)
```

**含义**：GT 恢复出来的 `RXOUTCLK` 以及由它派生的 `cam_clk`
（`rx_sdi.v:395` 那个二选一选择器的输出）**没有时钟对象**。
Vivado 不认识的时钟 → 相关路径不参与时序分析 → 那 987 个寄存器
（厂商的 `frame_convertor`、`YCbCr422_2_RGB888`，加上我们的
`sdi_cap_meas`、`sdi_px_pack`、异步 FIFO 写侧）从来没被检查过。
之前几轮报的 "WNS +0.847 ns" 只是**被分析了的那半张网表**的结论。

**为什么一直没人发现**：这个"时钟不存在"不报 error、不影响位流生成、
DRC 也不拦。加上它前面还有更响的问题（§6.18 那条通路就是死的），
一路都被别的现象盖着。

**怎么改的**（`constrs/sdi_cap.xdc`）：

```tcl
create_clock -name rx_usrclk -period 13.468 [get_pins -hierarchical -filter {NAME =~ *gtxe2_i/RXOUTCLK}]
create_clock -name cam_clk   -period 10.000 [get_pins -hierarchical -filter {NAME =~ *cam_clk_BUFG_inst/O}]
```

- 时钟源取 Vivado 自己打印出来的引脚名（`u_rx/SDI0/SDI/...`），不靠猜。
- `cam_clk` 的周期取两条候选里**更快**的 100 MHz：锁定时实际是 74.25 MHz，
  属过约束（安全方向）；不锁定时正好就是 100 MHz。
- 分组（`set_clock_groups -asynchronous`）把它们和 PS 侧、GT 参考时钟侧剪开。
  不剪的话 Vivado 会拿 13.468 ns 和 10 ns 求公共周期，
  算出 0.4 ns 这种荒谬的建立要求，刷屏几百条失败。
- 剪开之后再补一条边界要求：

  ```tcl
  set_max_delay -datapath_only 10.000 -from [get_clocks rx_usrclk] -to [get_clocks cam_clk]
  ```

  因为锁定时 `cam_clk` 就是 `rx_usrclk`，像素数据从厂商流水线送进打包器
  是一条**真实的同步路径**（原来要在 13.468 ns 里跑完），不能一剪了之。

**顺带纠正的一处文档错误**：`sdi_cap.xdc` 里原来写着
"Vivado 会把 cam_clk 拆成两根时钟" —— 事实是它一根都没建。
注释已按事实重写。

**验收方法**：新报告里
① `no clock driven by root clock pin` 那句里的名字（原来指向 RXOUTCLK）必须消失；
② Clock Summary 里必须出现 `cam_clk` / `rx_usrclk`，且 `cam_clk`
名下有上千个端点；③ 不能出现 `set_clock_groups: No group specified`。

**实测结果（2026-10-15，`build_impl_hp2d` 布线后）**：

| 检查 | 结果 |
|---|---|
| `cam_clk` | 100.000 MHz，729 个端点，WNS 6.038 |
| `rx_usrclk` | 74.250 MHz，2027 个端点，WNS 8.417 |
| 跨域 `rx_usrclk -> cam_clk` | 298 个端点，走 `set_max_delay -datapath_only`，WNS 7.568，0 失败 |
| 原来那句 | 变成 **TXOUTCLK**（456 个引脚）—— 是 GT **发送侧**内部的寄存器，本设计只收不发，留着无害 |
| 全设计 | `All user specified timing constraints are met`，WNS 2.388 / WHS 0.049，0 失败 |

> 端点数是随构建变化的（hp2b 那版是 cam_clk 377 / 跨域 167），
> 因为这几版之间设计本身在改（§6.20 方向、§6.21 悬空、§6.23–6.25 寄存器块）。
> 判据不是数字大小，而是"这两个时钟在摘要里有名字、端点数量级对得上、跨域那条有约束且不失败"。

> 注意实测里那句"没有时钟的寄存器"没有完全消失，而是从 RXOUTCLK 换成了
> TXOUTCLK。这是**对的结果**：`RXOUTCLK` 下游（我们真正用的那 2000 多个寄存器）
> 已经全部纳入分析；剩的 456 个在 GT 的 TX 通道里，我们没有任何逻辑驱动它。
> 原文"必须消失"写得太绝对，按实测改成"指向 RXOUTCLK 的那句必须消失"。

```
WARNING: [Synth 8-6104] Input port 'm_bready'  has an internal driver
WARNING: [Synth 8-6104] Input port 'm_bresp'   has an internal driver
WARNING: [Synth 8-6104] Input port 'm_arready' has an internal driver
WARNING: [Synth 8-6104] Input port 'm_rdata'   has an internal driver
WARNING: [Synth 8-6104] Input port 'm_rresp'   has an internal driver
WARNING: [Synth 8-2900] ignoring illegal expression in output port connection
```

**网表里的后果**：`u_ps/m_arready` 的驱动是一个 LUT，
而那个 LUT 的输入正是 PS7 自己的 `ARREADY` 引脚 —— **成环，恒 0**。
`RDATA/RRESP/RVALID/BRESP/BVALID` 同理。于是：

- 软件读写寄存器**永远等不到 ARREADY/RVALID/BRESP** → 一读就挂死；
- 写帧器的 B 通道也收不到 `BVALID`，`inflight` 永不下降 → `IDLE` 永不置位。

**根因**：`sdi_cap_ps.v` 的端口声明把**应答方向**写反了。
AXI 主机侧的五个通道方向是"请求出、应答入"，从机侧是"请求入、应答出"，
两张表一旦混用，就会出现"输入口被内部 assign 驱动"这种自相矛盾的写法。
第一版还用了 `gp1_*` 中间 wire + `assign` 往回桥接，把问题藏得更深。

**修法**：方向**逐条抄厂商 IP 的端口声明**（`rtl/vendor/ip/ps7/.../ps_ai_processing_system7_0_0.v`），
并且**全部直连、不经过中间 wire、不用 assign**：

```verilog
// HP2（PL 主机）：BVALID/BRESP/BID 是 PS7 的输出 → 我们的 output；
//                 BREADY 是我们发的 → input
output wire        wr_bvalid,
output wire [1:0]  wr_bresp,
output wire [5:0]  wr_bid,
input  wire        wr_bready,

// GP1（PS 主机）：AWVALID/AWADDR/WDATA/… 是 PS7 的输出 → 我们的 output；
//                 AWREADY/WREADY/BRESP/BVALID/ARREADY/RDATA/RRESP/RVALID
//                 是寄存器块的输出 → 我们的 input
```

PS7 上不用的输出引脚**整段留空**（`.M_AXI_GP1_AWLEN()` …）——
它们的寄存器块是 AXI4-Lite，本来就不需要；反过来**往 PS7 的输出引脚上接常量或
拼接会被综合器整个丢掉**（`[Synth 8-2900] ignoring illegal expression in output
port connection`，第一版就是因此把地址丢成恒 0 的）。

**验收**：重建后 `8-6104` 归零，且网表里
`SAXIHP2BVALID` 的负载落在写帧器一侧、`u_regs` 的 `s_axi_arready` 落在 PS7 一侧
（见 `probe6.tcl` 的 A/B 两节）。

### 6.21 `#(.W(1))` 却按 32 bit 接 —— 六个跨域控制/状态信号悬空

**症状**（综合日志，同一批 8-2900）：

```
WARNING: [Synth 8-689]  width (32) of port connection 'd_bus' does not match
                        port width (1) of module 'sdi_cap_cdc' [sdi_cap_top.v:264]
WARNING: [Synth 8-2900] ignoring illegal expression in output port connection
                        [sdi_cap_top.v:262 / 265 / 271 / 275 / 416 / 419]
```

**根因**：`sdi_cap_cdc` 的参数是 `W`，端口是 `[W-1:0]`。
顶层七处实例给了 `#(.W(1))`，却按 32 位写：

```verilog
sdi_cap_cdc #(.W(1)) u_cdc_en (..., .d_bus({31'd0, cfg_enable}),   // 输入侧：截断，能歪打正着
                                   .q_bus({31'd0, p_enable}));     // 输出侧：★ 整条表达式被丢掉
```

输入侧位宽不匹配只是截断（低 1 位还在），**输出侧接拼接是非法的**，
综合器把整条表达式丢掉 —— 于是七个信号在网表里**没有驱动**：

| 悬空信号 | 后果 |
|---|---|
| `p_enable` | 软件写 `CTRL.ENABLE` 传不到像素域 → **一帧都写不出来** |
| `p_rearm` | `REARM` 传不到写帧器，地址/计数清不了 |
| `p_rearm_cam` | `REARM` 传不到打包器 |
| `px_overflow` | FIFO 满丢字报不出来（`ERR_STAT[0]` 永远 0）|
| `wr_idle` | `WR_IDLE` 状态位永远 0 → 软件判空会**一直等下去** |
| `starving` | `STARVING` 状态位永远 0 |

(pattern: 这类 bug 的共性 —— **参数化模块的位宽拼接**。1 bit 就写 1 bit。)

**修法**：七处全部改成 1 bit 对 1 bit（`.d_bus(cfg_enable)`, `.q_bus(p_enable)`），
`u_cdc_addr` 那条 96 bit 的拼接本来就一致，不动。

**教训（比 bug 本身重要）**：这个 bug **仿真抓不到**（行为级里位宽会自动缩），
**综合不报 error**（只是 warning），**时序报告也正常**（悬空的输入是高阻/常量，
时序反而"更容易过"）。唯一能发现它的地方就是**把综合日志里的 8-xxxx 警告当成验收项读一遍**。
`AXI速率实测.md` §七 里 `ovf` 那条仿真判据，抓的是这条链路的**行为**；
抓这个**接线**问题的只有日志。

### 6.22 指向不存在端口的约束：噪声把真问题盖住

**症状**（每条约束都在报，但没人管）：

```
CRITICAL WARNING: [Common 17-55] 'set_property' expects at least one object. [sdi_cap.xdc:30]
CRITICAL WARNING: [Common 17-55] 'set_property' expects at least one object. [sdi_cap.xdc:31]
CRITICAL WARNING: [Netlist 29-160] Cannot set property 'PACKAGE_PIN', because the
                   property does not exist for objects of type 'pin'
CRITICAL WARNING: [Vivado 12-4739] set_false_path:No valid object(s) found for
                   '-from [get_ports rx_gtx_full_reset]'. [sdi_cap.xdc:115]
```

**根因**：`rx_gtx_full_reset` 是**厂商 top** 的一根输入引脚（E7）。
本设计的 `sdi_cap_top.v` 里没有这个端口（GT 复位由 SDI IP 内部两路复位信号管），
但那三条约束是从厂商约束文件抄过来的，一起抄进来却没人删。

**为什么要当成 bug 记账**：它不改变功能，但它是 **CRITICAL WARNING**。
14 条 CRITICAL WARNING 里躺着这几条，真问题（§6.21 的六个悬空信号）
就更容易被当成"又是那几条老噪声"。**日志噪声是要还的债。**

**修法**：删掉三条；在 `sdi_cap.xdc` 里留下说明（复位来自 PS 的
`FCLK_RESET0_N`，不是顶层端口，所以这条 false path 没有对象）。

**验收**：`sdi_cap.xdc` 相关的 CRITICAL WARNING 归零；
剩下的 `12-508 / 12-4739`（`cam_clk` 那条 `create_clock` 在**综合阶段**找不到引脚）
是已知无害的，见下。

> **关于 `12-508`（综合阶段找不到 `cam_clk_BUFG_inst/O`）**：
> Vivado 在**综合开始前**读约束文件，那时 RTL 还没展开，`cam_clk` 的 BUFG 还不存在；
> 到 **实现阶段**约束会被重新施加（日志里 `INFO: [Timing 38-35] Done setting XDC
> timing constraints`），布线后的时序报告里 `cam_clk` / `rx_usrclk` 都在（见 §6.19 实测表）。
> 结论：这两条警告只出现在综合日志里，**不影响实现**，刻意保留不动 ——
> 把时序约束挪到 impl-only 的 XDC 里能消掉它，但会让"两个阶段看到不同约束"
> 这件事更难解释。

### 6.23 帧率寄存器恒为 0：商算对了，取错寄存器

**症状**：`FPS_X100`（`0x1C`）永远读出 0，于是 `FPS_CLASS` 永远"未知"、
`FPS_MATCH` 永远是"未指定档"。**数据通路完全不受影响** ——
它是一条纯诊断通路，所以板子上不看帧率就永远发现不了。

**根因**：64 拍移位减法除法本身是对的，但最后一步取错了值：

```verilog
// 老写法（错）
fps_shifted = {1'b0, fps_rem[62:0], fps_quo[63]};
fps_sub     = fps_shifted - {1'b0, fps_divisor};
...
if (fps_iter == 7'd1)
    fps_x100 <= (fps_shifted >= divisor) ? fps_sub[63:32] : fps_shifted[63:32];
```

这个算法里**商是往 `fps_quo` 的低位里移进去的**（`fps_quo` 先装被除数、
再一位一位变成商），而 `fps_shifted` 只是"当前这一步的余数候选"，
它恒小于 `2*divisor`。帧周期是 3e6 量级的数，也就是说
**`fps_shifted[63:32]` 永远是 0** —— 正确的结果在 `fps_quo` 里。

**修法**：
```verilog
fps_x100 <= {fps_quo[30:0], fps_ge};   // 最后一位本拍才定，接在低位后面
```
另外把 `fps_shifted` / `fps_sub` 从 `reg`（块内阻塞赋值）改成 `wire`：
综合器本来就认出"这两个从来没被当时序元件用过"，把它们摆成寄存器再删掉，
报了两条 `[Synth 8-6014] Unused sequential element ... was removed`。
功能上无害，但那条警告说明它们本来就该是线（同一个根因，两处症状）。

顺手加了一道上界保护：帧周期 < 20000 像素时钟（> 3.7 kHz）时不启动除法。
没有真帧时 `meas_fperiod` 可能是个碎值，商一溢出 32 位就是垃圾值。

**为什么它一直没被抓到**：帧率寄存器只在 CSR 块里，而 CSR 块此前
**一行仿真都没有**（像素链测试台不实例化它）。这条和 §6.24 / §6.25 是同一个
教训的下半句：**"综合过、DRC 过、时序过"和"功能对"之间还隔着一次仿真**。

**验收**：新增的 `tb_sdi_cap_regs` 里三档实测（§6.26）：
1080p25 → `FPS_X100=2500`；1080p30 → `3000`；49.5 fps → `4950`（归 50 档）。

### 6.24 读通道 `ARREADY = ~ARVALID`：一读寄存器就死锁

**症状**：PS 读任何寄存器都不返回（驱动第一句读 `ID` 就卡住）。

**根因**：

```verilog
assign s_axi_arready = ~s_axi_arvalid;   // 老写法（错）
```

看着像"没人来读时 ready"，但 AXI 的握手条件是 **`ARVALID && ARREADY`** ——
这个写法下两项永远不可能同时为 1，所以 `s_axi_rvalid` 永远起不来。
PS 遵守协议、会一直举着 `ARVALID` 等 `ARREADY`：**死锁**。

写通道没这个问题：`awready = ~aw_hold_v` 是"上一条收下了就不再接新的"，
读通道当时漏了同样的那个"收下一条"的寄存器。

**修法**（和写通道同构）：

```verilog
reg r_hold_v;
always @(posedge s_axi_aclk)
    if (!s_axi_aresetn)      r_hold_v <= 1'b0;
    else if (s_axi_arvalid && s_axi_arready)    r_hold_v <= 1'b1;
    else if (s_axi_rvalid  && s_axi_rready)     r_hold_v <= 1'b0;

assign s_axi_arready = ~r_hold_v;
```

**和 §6.20 的关系**：§6.20 的应答方向错误确实让整条 GP1 死掉，
但它不是唯一原因 —— 两个 bug 叠在一起，只修方向还是读不回来。
一条"寄存器不通"的症状下藏着两个独立故障，这也是为什么这次专门补了
寄存器层的测试台（§6.26），把"通不通"这件事交给仿真而不是板子。

### 6.25 读回的位和写下的位对不上；`ROW_BYTES` 少一半

两条同源：**读多路器（read mux）和写译码各写各的，从来没有对齐过。**

**(a) `CTRL.IRQ_EN` 的位号**

```verilog
// 写：w_hold_d[1] -> r_irq_en          （手册也写 bit1）
// 读：{29'd0, r_irq_en, 1'b0, r_enable}  <- 把 IRQ_EN 放在了 bit2
```

于是软件写 `0x3`、读回 `0x5`。**自查寄存器读回值会以为配置没生效。**
修成 `{29'd0, 1'b0, r_irq_en, r_enable}`，以手册/写通道为准。

**(b) `ROW_BYTES` / `FRAME_BYTES` 少一倍**

```verilog
// 老写法（错）
wire [32:0] row_bytes_x   = {17'd0, meas_w} << 1;
wire [32:0] frame_bytes_x = {hw_prod, 1'b0};
A_ROW_BYTES:   rdata_c = row_bytes_x[32:1];
A_FRAME_BYTES: rdata_c = frame_bytes_x[32:1];
```

先左移一位、读的时候又取 `[32:1]` 移回来 —— **两次移位互相抵消**：
读出来是 `MEAS_W`（1920）而不是 `2*MEAS_W`（3840），
`FRAME_BYTES` 同样少一半。这两个寄存器就是给软件分行/分帧用的
（1080p30 每行 3840 字节），少一半直接让软件按错误步长切帧。

修法：按真实宽度算再原样截断 —— `{15'd0, row_bytes_x}`（17 位够）
和 `frame_bytes_x[31:0]`。

**为什么它一直没被抓到**：同上，CSR 没有仿真；而且这两个寄存器
"看起来像常数"（1920 和 2073600 都是合法数字），肉眼读代码很难发现少一倍。

### 6.26 CSR 这一层终于有仿真：`tb_sdi_cap_regs`

`sim/tb_sdi_cap_regs.v`（加到 `run_bench.ps1`，`-Only REGS` 可单跑）。
它用一个**真实的 AXI4-Lite 主模型**（VALID 举两拍、等 BVALID/RVALID 回来才撤
READY、每个等待都带超时并报 FAIL 而不是把仿真挂住），覆盖：

| 组 | 查什么 |
|---|---|
| 1 | `ID`/`VERSION` 魔数；RO 寄存器写不进去 |
| 2 | `BUF_ADDR_L/H`、`RING_BYTES`、`CTRL` 下发到 `cfg_*` 端口；`REARM` 恰好 1 拍脉冲 |
| 3 | `FPS_X100 = PIXCLK_HZ*100/MEAS_FPER`：25.00 / 30.00 / 49.5 三档 + `EXP_FPS` 对比 |
| 4 | `MEAS_W/H` → `ROW_BYTES`/`FRAME_BYTES` 的乘法（1920×1080 → `0x3F4800`） |
| 5 | `STATUS` 每一位、`WR_IDLE`、各计数器透传 |
| 6 | `INT_STATUS` 写 1 清零（含"原因还在的位会被当场置回"）、`ERR_STAT` 只读、IRQ 屏蔽逻辑 |
| 7 | `sdi_status_bus` → `RX_MODE`/`RX_RATE`/`RX_FAMILY` 的位映射 |
| 8 | 复位后帧周期是碎值时 `FPS_X100` 保持 0（上界保护） |

结果：**52 项检查全过**。这个测试台第一次跑就把 §6.23 / §6.25 两条抓出来了 ——
其中 `CTRL` 那条是它第一次跑就报的（写 3 读 5），
`ROW_BYTES` 那条把 1920/3840 的差别直接摆在了日志里。

## 六点五、已知限制（不是没做完，是刻意接受的）

### 复位 / 重配置 PL 之前必须判空，判空信号是 PL 自己报的

厂商《PS-PL AXI HP 接口：事务计数与复位语义》明确写了：

- PS 侧**不提供在途事务计数**（没有 AFI，也没有 `RCOUNT`/`RACOUNT`），
  AXI 协议本身也不定义这类信号
- AXI 不要求"复位时把在途事务做完"。任一侧在非空闲时被复位，另一侧会一直等
- 凡是只动 PL 的操作（PL 重配置、PL 逻辑复位）**都必须先排空**
- 官方推荐：给 PL master 加"使能输入 + 忙/闲状态输出"，由它决定何时可复位

所以本设计加了一个 `idle` 输出：

```verilog
// sdi_stream_wr.v
assign idle = (inflight == 0) && (state == S_IDLE);
```

单 bit，**`clk_100m` 域**产生（AXI 主机现在跑在 `clk_100m`，见 §3.2），
两级同步到 `fclk0_clk`（`sdi_cap_cdc #(.W(1))`），
暴露在 **`WR_IDLE = 0x74` 的 bit0**。软件侧 `sdi_cap_wait_drained()`
轮询它，要求连续 3 次都是 1 才认（单 bit 跨域最坏可能晚几个周期）。

`idle` 的语义是"**没有在途 AXI 事务**"，不是"FIFO 空"。这两件事必须分开，
因为本设计的写帧器只在水位 ≥ 16 拍（一个突发）时才起突发：

```
停掉像素源之后，FIFO 里会**永远**剩下 0~15 拍（最多 120 字节）
—— 不够一个突发，所以没人去写它。等 FIFO 空就等于永远等不到 idle。
```

实测（`docs/AXI速率实测.md`）：停流后 **35 ~ 93 拍**（@100 MHz，0.35~0.93 µs）
`idle` 拉高、`inflight` 归零，此时 FIFO 里剩 0~15 拍；
`idle` 之后再等 200 拍，**一拍都不再发出**（测试台逐拍核对）。

`sdi_cap_stop()` 现在会**关使能之后等排空**再返回。

> ★ 还有一个只有在真机上才看得到的边界 ★
> 判空握手管得住"AW/W 已经没有在途事务"，但管不住 **B 通道上正在回来的
> 写响应**。厂商文档（2026-10-12）说得很直白：AXI 不保证复位时把在途事务做完，
> 任一侧在非空闲时被复位，另一侧就永远等。所以正确的顺序是：
> 停数据 → 等 `idle` → 等最后一拍的 `BRESP` → 再动 PL 的复位。
> 本设计的 `inflight` 是在**收到 BRESP 之后**才减的，
> 所以 `idle == 1` 已经蕴含"最后一个 BRESP 已经回来了"。
> 这是把厂商那句"PL 必须自己知道什么时候可以复位"落成一个信号的关键：**数在 PL 里，不在 PS 里**。

> 这不是厂商私有要求，AMD 自己的说法一致（Zynq UltraScale+ MPSoC Restart
> solution）："For PL IPs that are AXI masters, user must provide the
> necessary code to stop and complete all AXI transactions from the master
> as well as to reset it."

> 只有 1 bit 是安全的。多 bit（比如把 6 位 `inflight` 整体跨过去）不行，
> 那正是下面 `sdi_status_bus` 那一类问题。

### 本设计属于厂商文档里的"设计2"

`pl_reset_n = ps_fclk_rst_n & clk_wiz_locked`，其中 `ps_fclk_rst_n`
是 PS7 的 `FCLK_RESET0_N`（**复位取自 PS**），`clk_wiz_locked` 来自板载晶振
经 `clk_wiz_0`（**时钟取自管脚/GT**）。

按厂商文档，PS 复位会把 PL 连带复位，设计2 这一档**不需要额外动作**。
比设计1 安全。

不过厂商也注明：设计1/2/3 的分档**只适用于用 `proc_sys_reset` 的接法**。
本设计是两级信号直接相与、没有复位同步器，这是已知限制：
`ps_fclk_rst_n` 和 `clk_wiz_locked` 对 `cam_clk` 都是异步的，
释放沿存在亚稳态窗口。实际影响很小（复位释放后寄存器全是确定的 0），
但严格来说应该给每个时钟域各加一个两级复位同步器。

### `sdi_status_bus` 是没有同步器的跨域多比特总线

`rx_sdi.v` 里 `sdi_status_bus` 产生在 `sys_clk_inst0` 的 27 MHz 域
（`RX_*` / `FREQ_CNT` / 位率检测都在那里），
`sdi_cap_regs` 却直接在 **FCLK0 50 MHz** 域读它，中间没有同步器。

```verilog
// sdi_cap_top.v
.sdi_status_bus (sdi_status_bus),   // <- 27 MHz 域
// sdi_cap_regs.v
.s_axi_aclk     (fclk0_clk),        // <- 50 MHz 域，直接用
.sdi_status_bus (sdi_status_bus),
```

**风险**：多位总线跨域，理论上可能读到亚稳态或撕裂值。

**为什么先这样**：

- 全部是**只读的上报量**（`RX_MODE` / `RX_FAMILY` / `RX_RATE` / `locked`），
  读错了最多让 `MEAS_*` 和 `FPS_X100` 显示错，**不会写坏任何数据**。
- 帧率是用 `fps = pixclk_hz / meas_fperiod` 现算的，
  `meas_fperiod` 又是在 `cam_clk` 域数的（`sdi_cap_meas` 里），
  那条路径是干净的。
- 这是厂商参考工程的做法，改了反而和厂商行为不一致。

**上板后怎么判**：连读 `FPS_X100` 与 `RX_*` 各几十次，看有没有跳变。
如果确实跳变，加一个握手式（脉冲 toggle + 数据保持）的 CDC：
数据侧用寄存器锁住，源域翻 toggle，两级同步后用同步过的 toggle 当采样使能。
`sdi_cap_cdc_pulse` 已经有这个原语，搬过来即可。

### 帧率只上报，不转换

`EXP_FPS` 写了 25 或 30 都**不会**让硬件只收那个帧率、也不会做帧率转换。
它只是让软件能在 `FPS_MATCH` 里看到实测值和自己声明的是否一致。
需求里的"PAL→1080P25、NTSC→1080P30"在本实现里就是**帧率识别**，
识别结果交给软件。

### 环形缓冲回绕时旧帧会被覆盖

PL 从不停止写。软件读得比 PL 写得慢，旧数据就被覆盖，
此时 `ERR_STAT.FIFO_FULL` 会置位。判据：

| 现象 | 含义 |
|---|---|
| `ERR.FIFO_FULL = 0`，`FRAME_CNT` 在涨 | 没丢数据 |
| `ERR.FIFO_FULL = 1`，`BEATS` 速率低于 `PIXCLK_HZ/2` | 软件读太慢，丢过数据 |
| `ERR.AXI_RESP = 1` | 写响应不是 OKAY，去查 `BUF_ADDR` 配错没有 |

### `WR_ADDR` 在回绕那一发之后停在环尾

它的语义是"刚写完那笔的末尾地址"。回绕那一发写完之后它等于
`base + ring_bytes`，下一发才回到 `base`。软件取帧用 `FRAME_ADDR`，
不要拿 `WR_ADDR` 当"当前正在写的位置"。

### 7.3 与厂商原工程的对比

厂商原工程 `fpai_demo_fpga`（不含 NPU）：LUT 21.0%、BRAM 28.9%、

但**余量只有 0.847 ns 这一件事需要盯住**：

- `cam_clk` 的兜底时钟已从 200 MHz 降到 100 MHz（§3.5），
  这不是审美选择，是 **200 MHz 关不掉** —— 光时钟路径就 4.239 ns，
  周期 5 ns 下留给数据的时间不够
- 环算术改成递减计数器（§6.9），把两条 32 位 carry chain 从
  "能不能起突发"的判断路径上拿掉了
- `clk_out1_clk_wiz_0`（也就是 `cam_clk` 的兜底分支）余量 +4.358 ns，
  是真正决定 1080p30 能否跑满的那个域

### 7.4 尚未验证的部分

上表只说明**综合和实现做完了、时序关得上**，不说明**功能对**。
FIFO 在硬件上的落点原来是个未解决疑点，见 §6.13；现在已经用
**综合后网表 + UNISIM 原语模型**的门级仿真（64 bit 链路，2026-10-15 重跑）定案：
FIFO 确实落在块存储上（布线后网表探针见 §6.13：`u_px_fifo` = 2×`RAMB36E1`），
存取的数据与行为级 RTL 完全一致，吞吐同为 **150.91 MB/s**，数据校验 0 错误。

但**上板仍然必须验**，因为仿真到底替不掉板子。
