# FPGA SDI 采集卡 · 调研与选型

调研日期 2026-10-14。结论先行，然后是清单和依据。

---

## 一、一句话结论

**这个需求不需要买 IP，也不需要从零写 SDI 接收器。** 本工程复用的是已经在这块板上
跑通的厂商 SDI 接收链（Xilinx `smpte_sdi` PG071 v3.0 + 复旦微的 `frame_convertor`），
自研只写 **5 个模块**（采集核 / 写帧器 / 寄存器 / CDC×2），约 1 400 行。

调研过程中**核实并推翻了 6 条常见前提**，写在第二节，因为照着错的做会直接走弯路。

## 二、先更正 6 条前提（都经过核实，不是推测）

| # | 常见说法 | 核实结果 |
|---|---|---|
| 1 | "Avnet 的 SMPTE SDI IP" | **Avnet 不是厂商**。SMPTE SDI 是 AMD/Xilinx 自研 LogiCORE，文档号 **PG071**。对全部 8 份 AMD SDI 文档 grep "Avnet" **0 命中** |
| 2 | "PG291" | PG291 是 **Clock Verification IP**，与 SDI 无关。SDI 文档号是 **PG071** |
| 3 | "IP 版本 v3.0 / v4.1" | 只有 **v1.0** 和 **v3.0**（v3.0 发布于 2018-02-02），**没有 4.1** |
| 4 | "`ZipCPU/sdidelay`" | **ZipCPU 没有任何 SDI 项目**。遍历其 52 个仓库，无一涉及 SDI，他的视频项目全是 HDMI |
| 5 | "`hamsterworks/sdi`、`azonenberg/openlogic`、`Attie/sdi`" | **全部 404，不存在** |
| 6 | "1080p = 2200 × 1125" | **只在 29.97/30/59.94/60 时成立**。**1080p25 是 2640 × 1125**，24 是 2750 × 1125。这是 SDI 里最容易搞错的一条 |

另外两条概念性澄清：

- **PAL/NTSC 不是 HD-SDI 的概念。** PAL（720×576/50Hz）、NTSC（720×486/59.94Hz）
  属于 **SD-SDI / SMPTE 259M**。HD-SDI（SMPTE 292M）里只有 1080p25/30/50/60。
  "PAL→1080P25、NTSC→1080P30"在实现上就是 **HD-SDI 输入 + 帧率映射**，PAL/NTSC 只是一层业务标签。
- **SMPTE 2042M 是 VC-2 视频压缩标准，与 SDI 无关。** SDI 那边是 **2048-2**（2048×1080 图像格式）。

> 关于 TDN / MBN：在 AMD 官方文档、厂商 IP 文档、公开标准摘要中**均未检索到**这两个术语，
> 无法证实其为 SMPTE 术语。**不建议写进设计文档**，除非拿到 SMPTE 标准原文核对。

## 三、可直接用的 IP（推荐优先）

| IP | 文档 | 器件 | 帧率覆盖 | 许可 |
|---|---|---|---|---|
| **SMPTE SD/HD/3G-SDI** (PG071) | [PG071 v3.0](https://docs.amd.com/v/u/en-US/pg071-v-smpte-sdi) | K7/V7/**Zynq-7000**/Artix-7/KU/UV | **1080p 23.98/24/25/29.97/30/50/59.94/60 全覆盖** | 随 Vivado 免费提供 |
| SMPTE UHD-SDI RX Subsystem (PG290) | [PG290](https://docs.amd.com/v/u/en-US/pg290-v-smpte-uhdsdi-rx-ss) | **UltraScale+ / Zynq US+** | 同上 + 2048×1080 | 随 Vivado |

**本工程用 PG071**，因为器件是 Zynq-7000；PG071 **不支持** Zynq UltraScale+。

**关键点：PG071 本身不输出 AXI4-Stream**，它输出 native 20-bit（Y/Cb/Cr 各 10 bit），
要串两级 IP 才有 AXI4-Stream：

```
PG071 (native 20bit) ──► PG179 SDI RX to Video Bridge ──► PG043 Video In to AXI4-Stream
```

本工程**没有走这条官方三段链**，而是直接用厂商已经接好的 `frame_convertor.v`
取 8 bit Y'CbCr 4:2:2 —— 少两级 IP、少两个 FIFO、带宽还减半。理由见
[设计说明 §3.2](repos/sdi-psddr/FPGA%20HD-SDI%20to%20PS%20Video%20Capture%20Card/docs/设计说明.md)。

| IP | 文档 | 器件 | 备注 |
|---|---|---|---|
| SDI RX to Video Bridge | [PG179](https://docs.amd.com/v/u/en-US/pg179-sdi-rx-video-bridge) | Zynq-7000 等 | 从 TRS 提取显式同步 |
| Video In to AXI4-Stream | [PG043](https://docs.amd.com/v/u/en-US/pg043-v-vid-in-axi4s) | Zynq-7000 等 | 官方 AXI4-Stream 入口 |
| **AXI VDMA** | [PG278](https://docs.amd.com/v/u/en-US/pg278-v-frmbuf) | — | 帧缓冲官方标准做法 |

### 时钟与数据通路（XAPP1290 原文表）

| SDI 模式 | 数据流数 | word 宽度 | userclk | stutter 节拍 |
|---|---|---|---|---|
| SD-SDI | 1 | 20 bit | 148.5 MHz | 5/6（≈27 MHz） |
| **HD-SDI** | **2** | **20 bit** | **74.25 或 74.25/1.001 MHz** | 1/1 |
| 3G Level A | 2 | 20 bit | 148.5 MHz | 1/1 |
| 3G Level B | 4 | 20 bit | 148.5 MHz | 2/2 |

**两条对本项目直接有用的结论**：

1. **RX 侧参考时钟可以本地自由振荡**，不必与输入位率匹配 —— 所以只收 HD-SDI 时，
   一路 148.5 MHz 就够，板上 J27 那条 148.5M 选通是对的。
2. TX 侧才需要精确匹配 —— 本项目**没有 SDI 输出**，不涉及。

## 五、开源项目（诚实结论：没有可复用的 SDI 接收 RTL）

用 GitHub Search API 做了系统穷举（`sdi in:name`、`smpte in:name,description` 等十余组查询）。
**结论：不存在可用的开源 HD-SDI 接收器 RTL。**

原因很直接：SDI 物理层极难做——要让 GT 出正确的 10-bit word，需要精确的参考时钟、
QPLL 配置、CPLL 分频比、RX 过采样系数和 reset 序列控制逻辑，这必须读原厂 transceiver
手册级别的代码来写。开源社区基本都**绕开这一点，改用外置解串器芯片**。

## 六、SMPTE 292M / HD-SDI 技术事实（可核查）

### 6.1 位率（AMD 官方原文）

| 制式 | 位率 | 关联帧率 |
|---|---|---|
| SD-SDI (ST 259M) | 270 Mb/s | PAL 50 / NTSC 59.94 |
| **HD-SDI (ST 292M)** | **1.485 Gb/s** | 1080p25/30, 720p30, 1080i50 |
| **HD-SDI (ST 292M)** | **1.485/1.001 Gb/s** = 1.4835 | 1080p23.98/29.97, 1080i59.94 |
| 3G-SDI (ST 424/425) | 2.97 Gb/s | 1080p50/60 |
| 3G-SDI | 2.97/1.001 = 2.9670 | 1080p47.95/59.94 |

叫"1.5 Gb/s"是因为 1.485 ≈ 1.5。

### 6.2 精确行/帧结构（PG290 Table A-1）—— 最容易搞错的地方

| 分辨率 | 总水平样点 | 有效水平 | 总垂直行 | 有效垂直 | 帧率 | 位率 |
|---|---|---|---|---|---|---|
| 1920×1080p23.98 | **2750** | 1920 | 1125 | 1080 | 23.98 | 1.485G |
| 1920×1080p24 | **2750** | 1920 | 1125 | 1080 | 24 | 1.485G |
| **1920×1080p25** | **2640** | 1920 | 1125 | 1080 | **25** | **1.485G** |
| **1920×1080p29.97** | **2200** | 1920 | 1125 | 1080 | **29.97** | **1.485G/1.001** |
| **1920×1080p30** | **2200** | 1920 | 1125 | 1080 | **30** | **1.485G/1.001** |
| 1920×1080p50 | 2640 | 1920 | 1125 | 1080 | 50 | 2.97G |
| 1920×1080p59.94/60 | 2200 | 1920 | 1125 | 1080 | 59.94/60 | 2.97G |
| 1280×720p25 | 3960 | 1280 | 750 | 720 | 25 | 1.485G |
| 1280×720p30 | 3300 | 1280 | 750 | 720 | 30 | 1.485G |

**规律**：24fps 系 = 2750；**25/50 系 = 2640；30/60 系 = 2200**。垂直总行数恒为 **1125**。

### 6.3 25 vs 30 / 29.97 vs 30 怎么区分

**位率本身就能区分两个家族**（PG071 原文）：

> *"The transport detector also determines the frame rate of the transport signal. This feature
> depends on the `rx_bit_rate` input in HD-SDI and 3G-SDI modes to distinguish between the
> N/1 and N/1.001 frame rates."*

- 锁定在 **1.485 Gb/s**（整数）→ **25/50 Hz 家族**
- 锁定在 **1.485/1.001 Gb/s**（非整数）→ **23.98/29.97/59.94 家族**

家族内靠视频格式 ID + 计数区分 25 vs 50、29.97 vs 30。
**检测延迟**：*"It can take the transport format detector up to two video frames."*

帧率编码（PG071 Table 3-2，与 SMPTE ST 352 VPID picture rate 字段一致）：
`0000`None `0010`23.98 `0011`24 `0100`47.95 `0101`25 `0110`29.97 `0111`30
`1000`48 `1001`50 `1010`59.94 `1011`60

### 6.4 格式 ID（PG071 Table 3-1）

```
rx_t_family (4-bit)
0000  SMPTE ST 274      1920x1080
0001  SMPTE ST 296      1280x720
0010  SMPTE 2048-2      2048x1080
0011  SMPTE ST 295      1920x1080
1000  NTSC               720x486
1001  PAL                720x576
1111  Unknown
```

**嵌入同步**：TRS = EAV + SAV。PG071 暴露 `rx_trs` / `rx_eav` / `rx_sav`
三个独立输出，每个 pulse 恰好一个 sample 宽。

> ⚠️ **注意**：本工程复用的厂商 `frame_convertor.v` 用的是 `rx_ds1a` / `rx_ds2a`
> （10-bit 字），不是 `rx_eav`/`rx_sav`，其 vsync 由 `rx_eav` + `rx_ds1a[7]` 合成。
> 格式 ID 和行宽 `hend` 已按 `rx_t_family` 自适应 1920/1280/720/2048。

### 6.5 物理层

- BNC 连接器，75 Ω 同轴
- **均衡器和驱动器在 FPGA 之外**（PG071 Feature Summary 原文）
- 本板板载：**LMH0344** 均衡器（125 Mbps~2.97 Gbps）/ **LMH0302** 驱动器
- PG071 本身**不描述 NRZI / 8b-10b**——这部分由 GTX/GTH user guide 定义。
  7 系列 GTX 在 SDI 应用中启用 8b/10b。

## 七、带宽核算（用于选型核对）

1080p Y'CbCr 4:2:2，16 bit/px 装进内存：

| 帧率 | 单帧 | 带宽 |
|---|---|---|
| 1080p25 | 1920×1080×2 = **4.15 MB** | 104 MB/s |
| 1080p30 | 4.15 MB | **124 MB/s** |
| 1080p60 | 4.15 MB | 249 MB/s |

- **PL → PS DDR**：GP0 单通道即可（实测余量 4×，见设计说明 §3.3），不需要 HPC
- **出网**：千兆在 1080p30 下够用；**1080p60 不够**，需压缩或 2.5G/10G
- **PCIe Gen3 x4**（≈3.9 GB/s）是常见商业方案

## 八、选型结论

| 方案 | 评价 |
|---|---|
| **复用板上的厂商 SDI 链 + 自研采集卡（本工程）** | ⭐ **采用**。硬件现成、IP 已在板上验证过、只写 5 个模块 |
| 官方 PG071 → PG179 → PG043 → VDMA 三段链 | 更"标准"，但多两级 IP、两个 FIFO，且要重新验证 |
| 外置解串器（GS2971A 之类） | 硬件上没这个芯片，且板上已有 LMH0344，纯属倒退 |
| 自写 SDI 接收 RTL | **不可行**。物理层必须读原厂 transceiver 手册 |
| 买第三方 IP | 本项目规模用不上 |

## 九、厂商自己的 SDI→PS 通路长什么样（2026-10-15 取证）

写下来不是为了抄，是因为**两边的接口模型根本不同**——不知道这一点，很容易按偏移"对上号"而改错。

**来源**（都是公开可取的）：厂商 ModelScope 仓库 `AIBS/fpai_reference_design`，分支 `func_icraft3.36`，配套 SDK Icraft 3.36.1。

| 文件 | 体积 | 里面是什么 |
|---|---|---|
| `deps/modelzoo_utils/include/pipeline/io/input/sdicamera.hpp` | 13,168 B | **PS 侧怎么跟 PL 的 SDI 块说话**：寄存器读写、`take()` / `wait()` |
| `deps/modelzoo_utils/include/pipeline/actor/sdi_input.hpp` | 12,849 B | 取帧 actor：u-dma-buf 槽位 → 写目标地址 → 触发 → 等 done |
| `.agents/skills/fpai-ref-design-integrate-model/references/profile-30tai.md` | 3,796 B | 30TAI（ZG330）档：多路 PLIN 时 `CAMERA_COUNT` 常为 2；相机/显示/PS-DMA 缓冲对齐 **128 B** |

**厂商的取帧协议**（寄存器基址 `0x4008_0000`；**这套地址不适用于本工程**，我们的 PL 是自己写的、寄存器在 `0x8000_0000`）：

| 偏移 | 作用 |
|---|---|
| `+0x04` | 写 `1` ⇒ 触发一次取帧 |
| `+0x50` | 目标地址，**单位是 8 B 字**（代码写 `addr >> 3`） |
| `+0x58` | bit0 = done、bit2 = error；出错时软件走 `+0x70`（软复位请求）→ 等 `+0x74` bit0（复位完成） |
| `+0x5c` / `+0x60` / `+0x64` / `+0x68` / `+0x6c` / `+0x78` / `+0x7c` | 裁剪 x0/x1、y0/y1（各 16 bit）、相机宽/高、水平/垂直步进、帧字节数、格式选择（YUV422 时 = 1）、YUV422 行像素数 |
| `+0x18` | 写 `1`（含义未取证） |
| `+0xB4` | bit0 = VTC 使能（视频时序控制器，服务 HDMI 那条路） |

时序是**一问一答**：PS 从 u-dma-buf 池取一个槽 → 写目标地址 → 触发 → PL 把**一帧**搬到那个地址 → PS 轮询 done/error → 出错只把这一条消息标成 `invalid_ps_frame`，整条链不重启（除非软复位）。

**与本工程的差别（关键）**：

| | 厂商参考实现 | 本工程 |
|---|---|---|
| 谁决定往哪写 | PS **每帧给地址**（`+0x50`） | PL 自己按环形缓冲推进，PS 只读 |
| 节奏 | 每帧一问一答（PS 不取就不搬） | **连续 push**，收到就写 |
| 帧边界 | 没有这个概念（一帧一个地址就够了） | vsync 标记在数据流里，暴露成 `FRAME_ADDR` |
| 格式判断 | **也不判断**（缩放/裁剪是 PS 下发的参数，搬来的就是配好的格式） | 完全不判断，格式解释全归软件 |
| 地址单位 | 8 B 字（`>>3`） | **字节地址**（`FRAME_ADDR` / `WR_ADDR` 低 32 位） |

两条结论：

1. 厂商的 PS 侧软件（`sdicamera`）**不能**直接套在本工程的 RTL 上——它要的是"给地址取一帧"的 PL。要复用它的 pipeline，得写一个从环形缓冲取帧的 actor；反过来在 PL 里补一套 take/done 协议也可以，但本工程选了连续 push + 软件轮询，因为它满足"不判断格式、不丢帧、不切帧"的要求（见 `设计说明.md` 第 1 节）。
2. **偏移别跨设计对号**：本工程 `0x50` 是只读的 `FRAME_ADDR`（字节地址），厂商 `0x50` 是只写的目标地址（8 B 字）；基址也不同（`0x8000_0000` vs `0x4008_0000`）。

**厂商位流本体：拿不到。** 同一份 README 文末给了 30TAI（悟净）两份 `ver 25122301` 参考实现的直链（单路 PLIN+pHDMI、单路 PLIN+VPU 编码 MIG_axi），实测**两条都返 401**（需要下载站账号）。所以"厂商位流里那条 SDI 链"只能当对照，不能当本工程的上板件。

> 同一份协议在 wiki 的《NPU调用链》第二节也有登记（软件视角，含 `>>3` 的解释更正）；本节的差别表是本工程独有。
